# Switchboard 2: the v2 theme and the classic theme (D131)

Switchboard 2 ships a new UI, the **v2 theme** (Direction D v3: `docs/design/v2-prototype.html`), as the default, and keeps the 1.x UI as the **classic theme**. Both are one app: the same server, API, `/hub` events and data. Plan: `docs/design/v2-plan.md`; decisions: `docs/decisions.md` → D131; every lane's assumptions: `docs/design/v2-decisions.md`.

## Two themes

- **Which one shows:** this browser's own choice (`localStorage['switchboard.ui.theme']`), else the service's default (`ui.theme` in `GET /api/settings`, default `v2`; `SWITCHBOARD_UI_THEME_DEFAULT` sets another until it is stored). Each phone is a browser with its own choice.
- **No flash:** `src/web/main.tsx` reads the settings (the same read as the pane state, D41) and the stored choice before the first render, and loads the v2 code first when v2 is the one shown. `<html data-ui="v2|classic">` is set before anything paints.
- **Switching** (`src/web/theme.ts` → `themeStore.choose`) swaps the whole UI at once, without a reload. `src/web/Root.tsx` first replaces the address with the other UI's address of the same page (`src/web/v2/routes.ts` → `toV2Path` / `toClassicPath`), so the page stays where both have it.
- **Where:** classic Settings → **Appearance** (`src/web/views/settings/AppearanceSection.tsx`) and v2 Settings › Appearance (`src/web/v2/settings/ThemeRow.tsx`); also the ⌘K palette ("Switch to the classic theme"). Either may also make the current theme the default for new browsers (`PUT /api/settings { "ui.theme" }`).
- **Links:** every classic address still opens its page in v2 (push notifications, paired computers and bookmarks use them): the v2 shell replaces it with the v2 address (`/sessions/a/diff` → `/agents/a/changes`, `/inbox` → `/needs-you`, …).
- **Tests:** the E2E servers default to classic (`tests/helpers/server-process.ts`), so the classic specs are unchanged; a v2 spec opts in with `V2_SERVER_ENV` or `useV2(page)` (`tests/e2e/v2-world.ts`).

- **`shared/agent-row.tsx`**: `AgentRow` (chat-style row), `AgentCard` (Working now), `ActivityLine`, `AskPreview`, `AgentComputerTag`, `UnreadDot`, `DraftMark`; pure `agent-line.ts` (`agentStatusOf`, `agentLine`, `agentName`).

- **`shared/Board.tsx`** (pure part `board-model.ts`): the one board, columns **Needs you · Working · Ready for approval · Done**, lanes and cards. The Agents board (grouped by Project or Folder; teammates are the Crews pages', not on it) and a project's Board view both draw with it. - **`shared/open-agent.ts`**: `useOpenAgent()` opens an agent the prototype's way from a card or row that peeks (Home's Working now and Done today, both boards, a project's steps, a teammate's Open chat, an agent hit in Search): the peek sheet on a desktop or tablet, the agent's page on a phone. ## Usage warnings

The server fires a Max usage warning once per window when the 5-hour window, the weekly limit or a model's weekly limit reaches the developer's **Warn at** (`usage.warnAtPct`, default 90 %; `docs/usage.md`) and lists it as `usageWarnings` on `GET /api/system` and the `system` event until the window resets. v2 shows each one (fix after 2.0):

- **A toast**, once per window and reset in this browser: `Claude ‘Work’ — 5-hour window at 92% · Resets 15:40` with **View usage** (Settings › Usage & accounts). The "shown" memory is classic's (`localStorage['switchboard.usageWarningsShown']`, `useFreshUsageWarnings` in `src/web/toast/useUsageWarnings.ts`), so switching themes never repeats one. Like classic it is only a toast: no sound, no OS notification, no push, nothing paused.
- **A Needs-you alert** ("Usage warning", `shared/usage-warning-model.ts` via `usageAlerts`), dismissible with OK (per browser, like the other usage alerts). It goes by itself when the window resets or that window's use, as read now, is below the threshold it reached.
- **The status pill** turns amber at Warn at (not a fixed 90 %), and so does every account's 5-hour and weekly bar in its popover (`statusPill(…, warnAt)`).
- **Settings › Usage & accounts → Usage warnings → Warn at Max usage** sets it (the same setting and choices as classic's Notifications & usage; `shared/warn-at.ts`). A change made from a classic page shows in the pill after a reload.

## Helpers fold

A long session collects hundreds of finished helpers (subagents, Workflow agents). The v2 agent view lists only the helpers that are **active** (working, waiting, starting, paused; an async helper the main agent still waits on counts, though its row ended at its launch) and those that **finished, failed or stopped within the last 10 minutes** (`RECENT_HELPER_MS`, `agent/helpers-model.ts`). Older ones fold under one row, **Show N helpers finished earlier**, which expands inline 50 at a time (**Show 50 more (N left)**) and collapses again; the expanded state belongs to that list in that agent view and is not remembered. Order: active (newest activity first), then the recent ones (newest end first), then the folded ones (newest first). A helper that becomes active again leaves the fold by itself.

- **Where:** the side panel's Helpers (its summary says "2 active"), the Helpers tab (also in the peek), the agents overview (**Show N finished earlier**: a helper or a whole Workflow run counts one; a run that ended over 10 minutes ago folds as one row with its agents) and the Timeline (the lanes of folded helpers become one summary lane **N earlier helpers**, their blocks drawn together; a click shows their own lanes). The Helpers tab's count in the header and the peek counts the active helpers only. The chat's in-line "N helpers finished" threads are unchanged.
- **The clock:** the 10-minute boundary moves live, but only when something can fold: one timer at the moment the next recent helper turns 10 minutes old (never sooner than a minute after the last tick), and a new session payload catches the clock up at most once a minute (`useFoldClock`, `agent/HelpersFold.tsx`). No timer while nothing can fold.
- **The times** come from `Agent.startedAt` / `updatedAt` / `endedAt` (additive, `docs/handoff/contracts/local-api.md` → *Helper times*); a Workflow's agents use their run's end once the run ended. A helper or run cut off without an end time (stopped, its process ended) counts from when it was last seen; one with no time at all (an older paired computer) is folded.
- Tests: `tests/web/v2-helpers-fold.test.ts`, `tests/e2e/v2-helpers-fold.spec.ts` (57 helpers; desktop and 390 × 844).

## Projects: the Graph view

A project's **Graph** (`src/web/v2/projects/GraphView.tsx`; layout `graph-layout.ts`, renderers `graph-parts.tsx`; Fixes after 2.0 → *The Project graph, redrawn*) draws its steps left → right by dependency depth (a step one column right of its furthest dependency), with a final node ("All done", or where the work is combined) after the last column.

- **Lanes:** when the steps spread over two or more repositories, each repository gets a tinted band with its badge, name and "done/total"; a step with several repositories or none sits in the neutral **Several repositories** lane. Inside the lanes, barycentre sweeps keep the order with the fewest crossings, and up to five repository lanes every lane order is tried (ties: the neutral lane last, then the plan's order). A lane keeps its colour (its place in the plan's repositories) whatever order it is drawn in. Cards are a fixed 236 × 104; edges are cubic curves from a card's right side to the next card's left side, so they stay inside the canvas.
- **Cards:** a ring (time so far against the estimate; full when done) with the state's icon, the key, a repository chip, ⋯, a two-line title, a line with the state (working: the time so far and the run session's model when the session list knows it; waiting: what it waits on; stopped: open to restart; done: how long it took) and, while working, a thin bar of the time so far against the estimate. The tone is the state, not a filled card: working (accent), ready (teal: a mix of the blue and green tokens), waiting (grey), needs you / stopped (amber), ready for approval (violet), failed (red: blocked, or its agent failed, D139), done (green, dimmed).
- **Header:** the % done ring, "N of M done · K working · J need you", a bar by state with counts, and **Critical path** (on by default, per browser: `localStorage['switchboard.v2.projectGraph.critical']`): the longest chain of steps by what is left of them (the core's time-left rule: estimate, or 30 min without one; running: estimate less the time so far), its not-done steps and edges highlighted.
- **Canvas:** Fit by default, + / − / Fit top right, ⌘/ctrl-wheel (and a trackpad pinch) zooms around the pointer, a drag on empty canvas pans. The **minimap** (bottom right; a click or drag moves the view) shows on a desktop only while some steps are outside the view (`contentOutside`), so a fitted graph has none; on a phone it shows only when **Map** (next to Fit) is pressed, and Fit then keeps its corner free. Zoom 0.3–2.5 (Fit may go lower for a big project). Hover or focus a step: it, everything it waits on and everything that waits on it light up, the rest dims; a tooltip gives the key, title, state, estimate, dependencies and whether it is on the critical path.
- **Steps:** a click opens the step's agent, or its details when it stopped or failed (D139); ⋯, a right-click, a long press (touch) or the context-menu key (or Shift+F10) open the step menu; Tab moves between steps, Enter opens.
- **Phones:** the view switch offers Steps and Graph (Steps unless Graph was chosen; `localStorage['switchboard.v2.projectView.phone']`, apart from the desktop's choice). A canvas under 560 px opens at 55 % centred on the first working step (else the first not-done one) instead of fitting, and a resize (the address bar) never resets it; the canvas is 70 % of the screen's height, the minimap (Map) 120 × 62. Two fingers pinch (around their midpoint, which also pans), one drags, a double tap on empty canvas zooms in ×1.6 (Fit from 1.4 up).
- **Motion** (none under `prefers-reduced-motion`; the travelling dots are not even drawn then): working cards breathe (a gradient border, a spinning ring), dots travel along edges into working steps (three per edge, SVG `animateMotion`), a needs-you icon nudges, a check pops when a step becomes done, new edges draw in, new cards fade in, cards glide to new places and colours cross-fade.
- **What's new:** the v2 tour `project-graph` (2.4.2; `docs/tutorial.md` → *Two themes*).
- Tests: `tests/web/v2-project-graph.test.ts` (layout, lanes, crossings against the classic layout, bounds, hover path, fit / zoom / pinch / double tap / the phone's opening view, when the minimap shows and its maths, critical path), `tests/e2e/v2-project-graph.spec.ts` (screenshots in `test-results/v2-project-graph-*.png`).

## Settings

`/settings[/:section[/<Advanced page>]]` (`src/web/v2/settings/`). The sections, in this order: **Usage & accounts · Rules for every agent · Appearance · Computers · Phones · Advanced** (`V2_SETTINGS_SECTIONS`). A desktop or tablet shows them on the left (`/settings` opens Usage & accounts); a phone shows the list and drills down.

- **Advanced** is a page per classic Settings section (and the classic Code projects and Connections pages), `/settings/advanced/<key>`, listed under headings (`settings-map.ts` → `ADVANCED_GROUPS`): **Agents** (AI engines & models, Agents & separate copies, Schedules, Notes checks, Background apps, Embedded tools, Connections) · **Projects & code** (Folders, Code projects, GitHub, CI & change requests, Jira) · **Accounts & devices** (Accounts / Computers / Phones: every option, Claude Code service) · **Notifications** (Notifications & prices) · **App** (Updates, Start at login, Clean-up, What's new tours, Setup wizard). Classic addresses still land on their page (`classicSectionTarget`).
- **Search** at the top of every Settings page finds single settings by label, help text and other words (`settings-index.ts` → `SETTINGS_INDEX`, `searchSettings`): exact label, then label prefix, then label words, then keywords, then help text. The query is in the address (`?q=`); ↑ / ↓ / ↩ open a result, Esc clears. A result opens its page with `?setting=<id>`, which scrolls to the row and highlights it for 2 s (`useSettingFlash`). ⌘K lists the same settings as its **Settings** group.
- **Adding a setting row:** give it an anchor (`data-row`, or a `data-testid`) and add an entry to `SETTINGS_INDEX` with its label, help text and a few other words people may type; `tests/e2e/v2-settings-search.spec.ts` checks every entry's anchor and label on its page. A new Advanced page needs a place in `ADVANCED_GROUPS` (a unit test checks every page is in exactly one group).

## How to add a v2 page

1. Find the area folder (or ask the orchestrator for a new route: routes are lane F's). Export the page from its `index.tsx`; the router already mounts it.
2. Use the words in `glossary.ts` (add any missing word there), the base components, `useV2Router()` / `<V2Link>`, and the shared modules above. Read data with the existing API clients and hub hooks.
3. Style under `.sb2` with `--v2-*` tokens; check light and dark, 390 × 844, 768 and 1280+; status as icon + word + colour; 44 px targets; reduced motion.
4. Test: pure logic in `tests/web/v2-<area>.test.ts` (no JSX / DOM imports there: the Node typecheck has no DOM), E2E in `tests/e2e/v2-<area>.spec.ts` with `tests/e2e/v2-world.ts`, headless, no `channel`.
5. Record any decision you had to make in `docs/design/v2-decisions.md`.

## Switching themes (for users)

Switchboard 2 opens in the **v2 theme**. The 1.x look is still there as the **Classic theme**, with the same agents, data and settings: only the screens differ.

- **In v2:** Settings › **Appearance** › Theme → **Classic**. Or press ⌘K and type "classic".
- **In Classic:** Settings → **Appearance** → **v2**.
- The switch is instant (no reload) and keeps you on the same page where both themes have it.
- Each browser and each phone remembers its own choice. "Make it the default for new browsers" also makes it the default of this Switchboard for browsers that have not chosen yet.
- Old links (notifications, bookmarks, paired computers) work in both themes.
