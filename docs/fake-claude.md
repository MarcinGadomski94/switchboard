# tools/fake-claude (M1.2)

A stand-in for the `claude` CLI 2.1.283 that replays the M0 recordings in `tools/fake-claude/fixtures/` (`docs/spike-m0.md`). Tests never call the real CLI; they start this instead, through the same configurable command the SessionSupervisor uses.

## Starting it
- **Argv prefix (every OS):** `fakeClaudeCommand()` in `tools/fake-claude/command.ts` returns `[process.execPath, <repo>/tools/fake-claude/main.ts]`. As a `SWITCHBOARD_CLAUDE_BIN` value use `fakeClaudeBinEnv()` (the same list as a JSON array, `docs/configuration.md`). Always `spawn(..., { shell: false })`.
- **Directly (macOS/Linux):** `tools/fake-claude/main.ts` has a `#!/usr/bin/env node` shebang and the executable bit; Node ≥ 24 runs the TypeScript directly.
- Test helpers: `tests/helpers/fake-claude.ts` (`spawnFake`, `runFake`, `makeFakeEnv`, the supervisor's `BASELINE` flags).

## Argv surface
Accepted: every flag in `fixtures/manifest.json` argv (scenarios and textRuns): `-p/--print`, `--input-format text|stream-json`, `--output-format text|stream-json`, `--verbose`, `--model`, `--max-turns <n>`, `--permission-mode <acceptEdits|auto|bypassPermissions|default|dontAsk|manual|plan>`, `--permission-prompt-tool`, `--allowedTools` (`--allowed-tools`), `--settings`, `--include-hook-events`, `--forward-subagent-text`, `--replay-user-messages`, `--session-id`, `--resume`, `--fork-session`, `--name`, one positional prompt; `--flag=value` works too. Plus:
- `--effort <level>` (D31, *Model and effort* below): `low`, `medium`, `high`, `xhigh`, `max` are taken; any other value writes `Warning: fake-claude: unknown effort level "<x>" (…); using the default` to stderr and is ignored (the CLI only warns too).
- `--teleport <id>` (D25, *Teleport* below). Mixed with `--resume`, `--session-id` or `--fork-session` → `error: --teleport cannot be combined with …` on stderr, exit 1 (the fake's own guard: the real CLI's answer to the mix was never probed).
- `--version` / `-v` → `2.1.283 (Claude Code)`, exit 0.
- `auth status [--json|--text]` → no output, exit 0; exit 1 with `FAKE_CLAUDE_SIGNED_OUT=1`. Callers rely on the exit code only (the real output was never captured).
- `agents [--json] [--all] [--cwd <dir>]` → the live sessions from `<CLAUDE_CONFIG_DIR>/sessions/*.json` whose pid is still running: `[{pid, cwd, kind, startedAt, sessionId, name, status}]` (M0.1 field order). `--cwd` keeps one canonical cwd; `--all` is accepted and changes nothing.
- Anything else → `error: unknown option '<flag>'` on stderr, exit 1. Without `-p` → exit 1 (no interactive mode).

Values that change behavior: `--model` / `--effort` (D31: reported in `get_settings` and, for `--model`, in `system/init.model`), `--input-format stream-json` (multi-turn over stdin), `--output-format` (NDJSON vs. final text only), `--permission-prompt-tool stdio` (only with stream-json input: questions and permission requests go to the host), `--permission-mode` (reported in `system/init`), `--max-turns`, `--replay-user-messages`, `--include-hook-events` (without it only `SessionStart` hook lines are emitted), `--forward-subagent-text` (without it subagent text/thinking lines are dropped), `--session-id` / `--resume` / `--fork-session`, `--name`. The rest are accepted and ignored.

## Scenarios
Every `manifest.json` scenario name, plus three built-ins:
- `default`: `multiturn` turn 1 (reply `OK`). Also the fallback once a scenario's recorded turns are used up.
- `hang`: the turn starts (`system/init`, replay) and never produces a result. An interrupt ends it with `[Request interrupted by user]` + `result/error_during_execution` (`aborted_streaming`, the `interrupt` recording) and the process stays alive; SIGINT does the same and exits 0. **EOF does not end it** (a turn that never finishes keeps the process alive, like a real long turn), so a supervisor that dies leaves a live process behind (M2.4).
- `crash`: the turn starts, then the process exits 1 unasked: no `result`, no `cost-state`, and the live-process file stays behind (like a killed CLI).

Selection: the `k`-th stdin user message plays turn `k` of the current scenario. A `[fake:<scenario>]` token in a message switches the scenario and restarts at its turn 1; an unknown name exits 1. `[fake:write <path>]` plays the `tx-main` Write turn with `<path>` (relative to the cwd; paths that leave the cwd exit 1 and write nothing) and **really writes** `written by fake-claude\n` there (`tool_use_result.type` `create` or `update`), for Diff tests. Replayed fixture tool calls never touch the disk. `[fake:tool <Name> {json}]` (M7.2) plays the same `tx-main` tool turn with `<Name>` called with that JSON object as its input (e.g. `CronCreate`, `ScheduleWakeup`, `CronDelete`, `Workflow`) and the invented tool result `fake-claude: <Name> done` (those tools' real results were never recorded); the JSON must not contain `}]`, and a token whose input is not a JSON object exits 1. `[fake:fire <n> <ms>]` (M7.2): after that message's turn the fake runs `n` turns of its own (≤ 100), one every `ms` (≥ 10), with no stdin message behind them and no replay echo (the `default` turn; the transcript gets the prompt `fake-claude: scheduled firing`), like the CLI firing a `/loop` cron job or wake-up; EOF or the process ending stops the rest. `[fake:worktree-add <repo> <branch> <path>]` (D38): the same `tx-main` tool turn as a `Bash` call `git -C <repo> worktree add -b <branch> <path>` (absolute paths, quoted when needed), and the fake **really runs** it (`git worktree add -b <branch> <path>` in `<repo>`, from its current HEAD, argv only), like an agent following the answers block's worktree instruction; the tool result is git's stdout + stderr (`is_error` and `Exit code <n>` when git failed). `<repo>` and `<path>` are relative to the cwd and must stay inside it (else exit 1, nothing run); a malformed token exits 1 (`tools/fake-claude/worktree.ts`). `[fake:say "<json string>"]` (D20): the `default` turn with its reply text (the main agent's text blocks, the `result` and the transcript) replaced by the JSON string's value, e.g. Markdown or raw HTML for chat rendering tests; newlines are written `\n` inside the string, so the token fits on one line; an argument that is not one JSON string exits 1. It does not change the scenario or its turn counter.

**Context size and compaction (D49).** Two tokens that go with any turn and change neither the scenario nor its turn counter. A malformed one exits 1.
- `[fake:usage <tokens> [<window>]]`: every main-agent assistant line of the turn has a usage whose `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` is `<tokens>` (input at most 3, the rest split between cache read and cache creation; `iterations` dropped). With `<window>`, the result's `modelUsage` entries report that `contextWindow` (else the recorded 200 000). Without the token, the recorded usages play (the default turn: 47 780).
- `[fake:compact <auto|manual> <pre> [<post>]]`: right after the turn's `system/init`, a `system/compact_boundary` as CLI 2.1.284 streams one (read in its code, never recorded): `{type, subtype, session_id, uuid, compact_metadata: {trigger, pre_tokens, post_tokens?}}`. The transcript gets the CLI's boundary entry (`content: "Conversation compacted"`, `level: "info"`, `compactMetadata` camelCase, `parentUuid: null`, `logicalParentUuid` = the previous chain tip); later lines chain onto it.

**Held turns (D44).** `[fake:hold <seconds>]` (decimals allowed, at most 600): the `default` turn, held `<seconds>` after its start (`init`, the thinking ticks, its replay) and before its reply, like a model that thinks for a while without calling a tool. A message written meanwhile has no tool boundary to be absorbed at (*Replay rules* → *Messages written while a turn runs*), so it waits for the turn's `result` and runs as its own turn. An interrupt or SIGINT during the hold ends the turn like `hang` (`[Request interrupted by user]`, `aborted_streaming`); EOF does not shorten it. A malformed token (`[fake:hold]`, `[fake:hold soon]`) exits 1. It does not change the scenario or its turn counter.

**Background work (D30).** Built on the `bg-bash` recording (the D30 probe of 2026-09-28, CLI 2.1.283 on Haiku: a `Bash` with `run_in_background: true`, its `system/task_started` (`local_bash`) and the `tool_result` `Command running in background with ID: <id>. …` with `tool_use_result.backgroundTaskId`, the turn's `result`; about 5 s later `system/background_tasks_changed`, `system/task_updated` (`completed`), `system/task_notification` `{task_id, tool_use_id, status, summary, output_file}` and a turn of the CLI's own, opened by `system/init`, whose `result` has `origin.kind: "task-notification"`; no `user` line carries the notification on stdout, even with `--replay-user-messages`). `[fake:bg-bash]` replays it as one turn, at once. The timed tokens:
- `[fake:background <seconds> <cmd>]`: the recording's first turn with `<cmd>` in place of the recorded `sleep 5; echo done` (everything up to the closing `]`, so the command cannot contain one) and a fresh task id; the turn ends with the task still running. `<seconds>` later (decimals allowed, at most 3600) the rest follows as the CLI's own turn: the task's `system/task_notification` (same `tool_use_id`, `status: completed`, summary `Background command "<cmd>" completed (exit code 0)`) and the recorded follow-up turn (`init`, reply `FINISHED`, `result` with `origin.kind: "task-notification"`). Its ids match the first turn's.
- `[fake:background-gh <seconds>]`: the same with a GitHub Actions wait (`GH_WAIT_COMMAND`: `for i in $(seq 1 60); do gh run view 4242 --json status --jq .status | grep -qx completed && break; sleep 20; done`).
- `[fake:wakeup <seconds>]`: the `tx-main` tool turn as `ScheduleWakeup` with `{delaySeconds: <seconds>, reason: "fake-claude: check again later", prompt: "fake-claude: scheduled firing"}` and the invented result `fake-claude: ScheduleWakeup done` (like `[fake:tool]`); `<seconds>` later a turn of its own (the `default` turn, no replay echo, like `[fake:fire]`). The delay is not clamped to the real tool's 60–3600 s.
- D43 `[fake:workflow <seconds>]`: the `[fake:background]` turn reshaped into a background **Workflow** launch as CLI 2.1.284 streams one (read in its code, not recorded): the `tool_use` is `Workflow` with `{script: FAKE_WORKFLOW_SCRIPT}` (`meta.name` `fake-audit`, `meta.description` `fake-claude: read-only audit of the recorded fixtures`); `system/background_tasks_changed` and `system/task_started` have `task_type: local_workflow`, the description, `workflow_name` and no `is_backgrounded`, and come before the result, as the real call registers its task while it runs; the `tool_result` is the CLI's launch text (`workflowLaunchText`: `Workflow launched in background. Task ID: w<8>\nSummary: …\nTranscript dir: …\nScript file: …` + its hints + `Run ID: wf_<12>` + `\n\nYou will be notified when it completes. Use /workflows to watch live progress.`; the paths, under `/tmp/fake-claude/workflows/<run id>/`, are text only) with `tool_use_result` `{status: "async_launched", taskId, taskType: "local_workflow", workflowName, runId, summary, transcriptDir, scriptPath}`. `<seconds>` later: `task_updated` `completed`, `task_notification` (the call's `tool_use_id`, summary = the description) and the recorded follow-up turn (`FINISHED`).
- D43 `[fake:bg-task <seconds> [<type>]]`: the same turn **without a tool call** (the recording's `Bash` call and its result are left out): only `system/task_started` of `<type>` (default `fake_task`, a type Switchboard does not know; letters, digits, `_`, `-`) with the description `fake-claude: a background task of the CLI`, a fresh `k<8>` task id and **no** `tool_use_id`; `<seconds>` later its `task_updated` / `task_notification` (no `tool_use_id` either) and the follow-up turn.

A malformed token (`[fake:background 5]`, `[fake:wakeup soon]`, `[fake:workflow]`, `[fake:bg-task soon]`) exits 1. A message that arrives meanwhile runs normally; the task's end queues behind it. EOF or the process ending drops what is still pending (nothing more is reported). The notification's own `user` entry (`origin.kind: "task-notification"`) is not written to the fake's transcript.

## Remote Control (D24)
The CLI's side of `docs/remote-control.md`, built to `docs/spike-remote.md` → R.6 (the shapes were read in the CLI's code, never recorded):
- **`initialize`** answers the recorded `ctl-init` payload, which has `remote_control_available: true` (`false` with `FAKE_CLAUDE_REMOTE_CONTROL=unavailable`).
- **`remote_control` `enabled: true`** → `control_response` success `{session_url:"https://claude.ai/code/session_<X>", connect_url:"https://claude.ai/code?environment=env_<X>", environment_id:"env_<X>", bridge_epoch:<n>, bridge_session_id:"cse_<X>"}` with `<X>` = `FAKE` + the session id without dashes, or, with `reattach_session_id: "cse_<Y>"`, `<X>` = `<Y>` (the same claude.ai entry; an id that is not `cse_…` is an error). `bridge_epoch` counts the enables of the process. The bridge is then on. `name` and `keep_session_on_exit` are accepted and ignored.
- **`remote_control` `enabled: false`** → success `{}`; the bridge is off.
- **`[fake:remote-answer <ms>]`** in a stdin user message (the milliseconds are required: `[fake:remote-answer]` alone would be read as a scenario name): when that message's turn opens a question or permission request, "the phone" answers it `<ms>` ms later **if the bridge is on**: the fake writes `{"type":"control_cancel_request","request_id":<id>}`, as the CLI does when claude.ai answers first, and the turn goes on as if the host had answered (AskUserQuestion: each question's first option; any other tool: allowed). If the host answers first, nothing happens; with the bridge off the request stays open and stderr says so. Use it with a scenario token, e.g. `[fake:ask-2q] [fake:remote-answer 1500] Ask me.`; it does not select a scenario or change the turn counter.
- Not modelled: `bridge-session` / `system/bridge_status` transcript lines, messages typed on the phone, the bridge's own lifetime (it ends with the process).

## Model and effort (D31)
The CLI's side of `docs/model-effort.md`, built to what the D31 probe saw on CLI 2.1.283:
- **`initialize`** answers the recorded `ctl-init` payload, whose `models[]` has 11 entries with `supportedEffortLevels` on all but Haiku (`low … max`; Opus 4.6 and Sonnet 4.6 without `xhigh`). `FAKE_CLAUDE_MODELS=none` removes `models`.
- **`set_model {model}`** → `{subtype:"success", request_id}` (no `response`, as the CLI) for `default`, `null` or a `value` of that list; another name → `{subtype:"error", error:"Model '<x>' not found", error_code:"catalog_unknown"}` (the probed text); a non-string → `set_model: model must be a string` (`invalid_request`); `FAKE_CLAUDE_SET_MODEL_ERROR` → that text.
- **`apply_flag_settings {settings}`** → a bare success; `settings.effortLevel` (a string or `null`, **not checked**, as the CLI) sets the effort, `settings.model` the model; `settings` that is no object → `apply_flag_settings requires \`settings\` to be an object, got <type>`; `FAKE_CLAUDE_EFFORT_ERROR` refuses an `effortLevel` with that text. `set_effort` does not exist (the generic unsupported-subtype error, as the CLI).
- **The echo:** `get_settings` → `{applied: {model, effort, advisor: null, ultracode: false}}` (the probe's shape; `model` = the chosen entry's `resolvedModel`, else the recorded `claude-haiku-4-5-20251001`), and every later `system/init` reports the chosen model (`resolvedModel`) as `model`. `--model` / `--effort` at spawn set the starting values; `FAKE_CLAUDE_LOG` records the argv.
- Not modelled: that a model or effort changes the replies (the recordings play as recorded), PreModelSwitch hooks, org restrictions.

## Replay rules
- **Turns.** A recording is split at each `result`; a later `result` with `origin.kind:"task-notification"` (a background agent finishing) and any lines after the last result stay in the same turn. The leading `SessionStart` hook pair is emitted at spawn: `SessionStart:startup` for a new session, `SessionStart:resume` with `--resume` (an idle resumed process emits only that pair until the first message, `handoff-reattach`).
- **Rewriting.** Every emitted line: the recorded cwd (and its slug inside paths) → the canonical cwd; every recorded `session_id` → the current id; every uuid and API id (`toolu_…`, `msg_…`, `req_…`, object keys included) → a fresh id, consistent inside one turn; `timestamp` → now; `result_index` counts results per process; `system/init.permissionMode` = the reported mode for `--permission-mode` (`manual`/`auto`/none → `default`, as recorded on Haiku), except `perm-auto`, which keeps the recorded `default` so a supervisor sees the mismatch; `init.tools` has `AskUserQuestion` exactly when `--permission-prompt-tool stdio` is on.
- **Replay echo.** With `--replay-user-messages`, the `isReplay` user line carries the message as sent, where it was recorded (else right before the first assistant line). Its `uuid` is the transcript uuid of the prompt, as in the CLI.
- **Messages written while a turn runs (D44).** They wait in the fake's queue and nothing is echoed for them while the turn runs, as in the CLI (`docs/derivations.md` → *Queued messages*: the echo marks the pickup). At the running turn's next **tool boundary** (a main-chain `tool_result` line, e.g. the AskUserQuestion result an answer makes) the turn absorbs every plain message queued meanwhile, as the CLI's mid-turn `queued_command` does (read in the 2.1.284 binary, not recorded): each is echoed right there (`isReplay`) and gets no turn, no `init` and no `result` of its own; the turn goes on as recorded. A message carrying a `[fake:…]` token is never absorbed (it asks for a turn of its own), nothing is absorbed while an interrupt is pending or after one (an aborted turn takes nothing, as in the CLI), and absorbed messages are not written to the transcript (the CLI writes a `queued_command` attachment there, which the fake does not write). Without a tool boundary (`[fake:hold]`, `hang`, a turn that only thinks) the message runs as its own turn after the running turn's `result`: `init`, its echo before the first assistant line, the reply, `result`.
- **Questions and permissions (M0.2).** The `tool_use` and the `control_request/can_use_tool` (fresh `request_id`) are emitted, then playback **blocks** until a `control_response` with that `request_id`. `allow` on `AskUserQuestion` → the tool_result text `Your questions have been answered: "<q>"="<a>", … You can now continue with these answers in mind.` and `tool_use_result {questions, answers}`; `allow` on another tool → the recorded result; `deny` → an `is_error` tool_result whose content is the message verbatim (`tool_use_result: "Error: <message>"`). If the decision differs from the recorded one, the rest of the turn comes from the sibling recording (`perm-allow` ⇄ `perm-deny`, `ask-interrupt` answered → `ask-delay`), otherwise from the default reply. The assistant text after an answer is the recorded one (it does not re-read the answer). Without `--permission-prompt-tool stdio` (or without stream-json input) any turn with a request plays `perm-noflag` instead: `system/permission_denied`, no request.
- **Interrupt** (`control_request` `interrupt`). Idle → only `control_response {still_queued: []}` (`handoff-start`). At a recorded interrupt point (`interrupt`, `interrupt-tool`, `handoff-midturn`, `ask-interrupt`, `sigint`) → the recorded tail with the ack where it was recorded. While a request is open without a recorded tail → the `ask-interrupt` tail aimed at that request: `control_cancel_request`, ack, rejected tool_result, `[Request interrupted by user for tool use]`, `aborted_tools` (the result's `permission_denials` names the open tool). An interrupt that lands while a turn is between wait points aborts it like `interrupt` (`aborted_streaming`). A normal turn never waits: it is emitted at once.
- **SIGINT** → the same tail without the ack, `cost-state`, exit 0. **SIGTERM** → the live-process file is removed, then the default signal death.
- **EOF.** The running turn finishes, then exit **1 if the last `result` was an error** (after an interrupted mid-tool turn or a cancelled question, `handoff-midturn` / `ask-interrupt`), else 0. Messages queued before EOF still run. EOF while a request is open fails it at once like the CLI (`Tool permission request failed: AbortError: Stream closed`, seen in M0.2) and the turn ends with the default reply. EOF at a recorded wait point without an open request (a tool still "running", `hang`) keeps waiting.
- **`--max-turns n`.** A turn that needs more than `n` main-chain model messages is cut before message `n + 1` and ends with `result/error_max_turns` (`errors: ["Reached maximum number of turns (n)"]`); prompt mode then exits 1.
- **Control requests.** `get_usage` / `get_session_cost` → the `usage-ctl` payloads before the first finished turn, the post-turn `usage-turn` payloads after it; `initialize` → the `ctl-init` payload (D24: `remote_control_available` per `FAKE_CLAUDE_REMOTE_CONTROL`); `remote_control` → *Remote Control* above; `set_model`, `apply_flag_settings`, `get_settings` → *Model and effort* above; `set_permission_mode` `auto` → the recorded `auto_mode_model` error, any other mode → `success {mode}` (and later `init` lines report it); any other subtype → `{subtype:"error", error:"Unsupported control request subtype: <x>"}`. Replies use the incoming `request_id`. `rate_limit_event` lines are replayed where they were recorded (the CLI emitted one only in the first turn of each multi-turn recording), not added to every turn.
- **Text mode** (`-p [--resume <id>] "<prompt>"` without `--output-format stream-json`): prints only the final `result` text (+ newline); an error result without text goes to stderr. `-p` with no prompt reads the prompt from stdin.

## Files under `CLAUDE_CONFIG_DIR`
- **Transcript** `projects/<slug(cwd)>/<sessionId>.jsonl` (slug per M0.3; `slugForCwd` in `transcript.ts` is the fake's own copy). Created with the first user message, never at spawn and never by control-only runs. Per message: `queue-operation` enqueue/dequeue, the prompt (`promptSource`/`turnOrigin` `sdk`, `permissionMode`), then each main-chain assistant line, tool_result and interrupt marker with the **same uuid as on stdout**, chained by `parentUuid`, with the CLI envelope (`isSidechain:false, userType:"external", entrypoint:"sdk-cli", cwd, sessionId, version:"2.1.283", gitBranch`). `gitBranch` is read from `.git/HEAD` of the cwd or a parent (worktree `.git` files followed), else `HEAD`. Per turn: `last-prompt` (`leafUuid` = chain tip). A new session with `--name` gets `custom-title` + `agent-name` at its first message and after each turn; resumes never re-append them. Text mode adds `{"type":"mode","mode":"normal"}`. At exit: `cost-state` (the `tx-main` numbers, own `startTime`). Attachment lines are not written.
- **Resume** `--resume <id>`: the file is looked up in the cwd's project folder, then in every project folder (like the CLI); none → `No conversation found with session ID: <id>`, exit 1. New lines go to that same file with the new cwd. If the file's last chain entry is an interrupt marker, the first new message is preceded by the synthetic assistant line (`model:"<synthetic>"`, `No response requested.`, from `handoff-mid`). `--fork-session`: a new id and a new file under the cwd, starting with a copy of the old entries.
- **Live-process file** `sessions/<pid>.json` = `{pid, sessionId, cwd, startedAt, version, kind:"interactive", entrypoint:"sdk-cli", status, updatedAt, name}`; `status` is `busy` during a turn, `idle` otherwise; `name` = `--name` or the cwd's folder name. Removed on a normal exit and on SIGTERM; left behind by `crash` and SIGKILL (and then not listed by `agents`, whose pid check skips dead processes).

## Teleport (D25)
`-p --teleport <id>` does what `docs/spike-remote.md` → *R.3* reads from the CLI's print mode, without a cloud or a network, before anything is printed:
1. **The checkout.** The cwd must be inside a git work tree (`git rev-parse --is-inside-work-tree`), else the wrong-repo refusal (the CLI's `not_in_repo`). It must have no tracked changes (`git status --porcelain --untracked-files=no`; untracked files are ignored, as in the CLI), else the dirty-tree refusal. `FAKE_CLAUDE_TELEPORT=dirty` forces that one.
2. **The session download.** `FAKE_CLAUDE_SIGNED_OUT=1` → not signed in; `FAKE_CLAUDE_TELEPORT=wrong-repo` → the wrong repo (`FAKE_CLAUDE_TELEPORT_REPO`, default `acme/app`); `archived` → an archived session.
3. **The branch.** `FAKE_CLAUDE_TELEPORT=not-pushed` → the branch is not on origin. Otherwise the fake checks out the local branch `claude/<id>` (created from HEAD when missing; `git checkout`, `shell: false`); a git failure (e.g. the branch is checked out in another worktree) is printed as git said it, exit 1.
4. **The local copy.** A fresh session id (a uuid). With `CLAUDE_CONFIG_DIR` set, its transcript (`projects/<slug(cwd)>/<id>.jsonl`) starts with a fixed **remote history** of two exchanges ("Remote history 1: add a /health endpoint to the API." → "Remote reply 1: …", "Remote history 2: push the branch." → "Remote reply 2: pushed claude/<id>."), chained by `parentUuid`, `gitBranch` = the checked-out branch, timestamps a few minutes back; the first message continues that chain. stdout does not replay it (M0.4: stdout never replays history).
5. **Reporting.** The `SessionStart:startup` hook pair, then `system/init` with the fresh id at once, before any message (`FAKE_CLAUDE_TELEPORT=no-init`: only with the first turn, as the CLI does for an idle `--resume`; which one the real CLI does is unknown, P6). Then it behaves as a normal session; a later `--resume <that id>` finds its transcript.

Refusals go to stderr, nothing to stdout, with distinct exit codes (the real CLI's codes were never captured):

| Refusal | stderr (one line) | Exit |
|---|---|---|
| dirty tree | `Git working directory is not clean. Please commit or stash your changes before using --teleport.` (R.3, verbatim) | 1 |
| wrong repo | `You must run claude --teleport <id> from a checkout of <owner/repo>` (R.3, verbatim) | 2 |
| archived | `cloud session <id> is archived and cannot accept new messages` (R.2's text for `--cloud`; the teleport text was never captured) | 3 |
| not pushed | `Failed to fetch branch claude/<id> from origin: fatal: couldn't find remote ref claude/<id>` (the fake's wrapping of git's message) | 4 |
| not signed in | `Not logged in · Please run /login` (the fake's wording) | 5 |

Code: `tools/fake-claude/teleport.ts`; tests: `tests/tools/fake-claude-teleport.test.ts`.

## Not modelled
The CLI's merging of several queued prompts into one turn (`replayMerged`: they would be echoed at once and share a `result`), `command_lifecycle` frames (the CLI writes them only for messages with a `uuid`; Switchboard's have none), interactive TTY mode, `--output-format json`, the `hook_callback` / `mcp_message` control subtypes, real tool execution (except `[fake:write]` and `[fake:worktree-add]`), `/slash` commands, subagent sidechain files, usage error payloads (M9.2 tests the parser with its own payloads), and timing (turns are emitted at once; only wait points take time). SIGINT on Windows is not a catchable signal for child processes, so Windows tests should interrupt over stdin.
