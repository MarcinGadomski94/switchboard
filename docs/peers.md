# Switchboard peers (D48)

"Ultimately, any Switchboard should be able to connect to any other Switchboard." (developer, D48). Each install can **serve** (an optional peer listener on its Tailscale address) and **connect** (to every machine it paired with). There is no "host" or "client" build: the Mac and each Windows PC run the same Switchboard.

Code: `src/core/peers.ts` (ids, addresses, codes), D65: `src/core/takeover.ts`, `src/server/takeover/`, `src/server/api/takeover.ts`, `src/web/takeover/`, `src/core/peer-wire.ts` (namespacing), `src/server/peers/` (the service, the listener, connections, pairing, tokens), `src/server/api/machines.ts` (routes and forwarding), `src/web/views/settings/MachinesSection.tsx`; P4: `src/core/hooks.ts`, `src/server/hooks/`, `src/hook/sb-hook.ts`, `src/server/api/hooks.ts`, `src/web/views/settings/MachineHooks.tsx`. Rulings: `docs/decisions.md` → D48. Choices where the rulings are silent: `.loop/questions.md` → *D48 · Switchboard peers*.

## Machines and pairing (P1)

- **This machine** has a random **machine id** (12 characters, `a-z2-7`, made once and kept in the settings table as `peers.self`) and a **name** (the host name without `.local`). The id is the namespace other machines use for its ids.
- **Peer listener** (Settings → Machines → *Peer listener*, off by default): a second socket that serves only the peer API. It binds only the machine's **Tailscale IPv4** (`tailscale ip -4`, the first IPv4 line; with the default command the macOS app's CLI `/Applications/Tailscale.app/Contents/MacOS/Tailscale` is tried when `tailscale` is not on `PATH`) or an address typed in the settings, which must itself be a Tailscale address (100.64.0.0/10). Port **13002** unless changed (never the UI's port). When no address is found, or the bind is refused, the row says why and nothing listens. The UI listener stays on 127.0.0.1 exactly as before.
- **Pairing** (both on Settings → Machines):
  1. On machine A (listener on): **Allow a new peer** shows a one-time code `XXXX-XXXX` (8 characters of Crockford base32, 40 bits), valid **10 minutes**, **single use**, burned after **5 wrong tries**, held in memory only (a restart forgets it; a new code replaces the old one). Typed codes are read leniently (case, spaces, `O`→`0`, `I`/`L`→`1`).
  2. On machine B: **Add machine** with A's address (`100.x.y.z`, optionally `:port`) and the code. B sends `POST /peer/v1/pair` `{ code, id, name, address, token }` to A: its own id and name, its own listener address (or `null`), and a fresh token **A** will present to B. A answers `{ id, name, token }` with a fresh token **B** will present to A.
  3. Each side stores the other's id, name, address, the token it **presents** (`outbound_token`) and only the **sha256** of the token it **checks** (`inbound_token_hash`), in the `machines` table (migration 0016).
  - **One pairing works both ways** (ASSUMED D48-both-directions): A can call B as soon as it knows B's address. When B's listener is off at pairing time A shows B as **no address**; B tells its address with every hello (`POST /peer/v1/hello` `{ address }`), so switching B's listener on later is enough.
  - Pairing again replaces both tokens (the old ones stop working). Names are local tags: renaming a machine changes only this side.
- **Remove** revokes: the machine's row (and its tokens) goes, its streams close, and the other machine is told (`DELETE /peer/v1/pair`, best effort) so it forgets this one too.
- **Connections** (`src/server/peers/client.ts`): per paired machine with an address, `POST /peer/v1/hello`, then `GET /peer/v1/api/sessions` (the cache), then the event stream `GET /peer/v1/events` held open. States, retries, Reconnect now and the log: *Connection states* below (fix · peer reconnects, 2026-10-01; before it a drop was `offline` at once and the backoff doubled from 1 s to 60 s, unseen). Settings → Machines follows the `/hub` event `machineState` live (a 15 s reload is the fallback; it polled every 3 s before).

## Connection states (fix · peer reconnects)

Developer report, 2026-10-01: a remote session said "<machine> is offline — reconnect to continue" with no way to reconnect, no sign of the retries going on in the background, and it sometimes came back by itself. Long-lived streams over a relayed Tailscale path (DERP, "direct connection not established") drop more often than direct ones; every drop blocked all interaction at once. Ruling: `docs/decisions.md` → *Fix: peer reconnects*; choices: `.loop/questions.md` → *Fix · peer reconnects*.

| State | When | Reads | Actions |
|---|---|---|---|
| **online** | the event stream is open | live | sent |
| **reconnecting** | the stream dropped, or this service just started, and the **grace period** (20 s) has not run out | the cache and the snapshots, at once | **held** until it is back (at most 10 s, or the end of the grace), then sent; still away → 502 `peer-unreachable` "<machine> is still reconnecting — try again in a moment" |
| **offline** | not reached within the grace period | the cache and the snapshots | refused at once: 502 `peer-unreachable` "<machine> is unreachable — it retries by itself; Reconnect now tries at once" |
| **auth failed** | the peer answered 401 (revoked there) | the cache and the snapshots | refused; pair again |
| **no address** | the peer never told a listener address | — | refused |

- **Retries.** After a drop the first attempt starts **at once**; failed attempts then wait **1 s, 2 s, 5 s, 10 s, then every 15 s** (`RECONNECT_SCHEDULE_MS`, `RECONNECT_MAX_MS`; ASSUMED reconnect-schedule), each wait ±20 % jitter. A successful stream resets the count. Retrying never stops while the machine is paired (also when offline / auth failed / no address).
- **Grace period** (`PEER_GRACE_MS`, 20 s): a drop makes the machine `reconnecting`, not `offline`; only after 20 s without success does it become `offline`. A new connection (this service starting, a new pairing) starts `reconnecting` too. A 401 is `auth failed` at once.
- **Stall detection** (`PEER_STALL_MS`, 25 s): every chunk on the stream (events and the peer's `: keepalive` every 10 s) re-arms a timer; a stream with nothing for 25 s (2.5 keepalives; ASSUMED reconnect-stall) is cut and reconnected (`stalled`), instead of waiting for TCP to notice a dead relayed path. The hello and the stream's answer have a 15 s limit each.
- **Why it failed.** Each failed attempt (and each drop) records its kind and when: `refused` (nothing listens: Switchboard not running there or its listener off), `timeout`, `route` (DNS / no route: Tailscale down, the address changed), `auth` (401), `http` (another status), `reset` (the connection was cut), `ended` (the other side closed the stream), `stalled`, `restart` (this service reconnected on purpose: a new address, a refused token) or `other`, in plain words (`peerFailureText`), plus when the next attempt starts. **Hint:** when the last 3 or more failures were all timeouts, the status says "Check that <machine> is awake and on Tailscale." (`connectionHint`).
- **Reconnect now** (`POST /api/machines/{id}/reconnect`, Settings → Machines rows, the session header note and the composer note): cuts any wait and tries at once; when an attempt already runs it waits for that one (never two at once). It answers `{ outcome, machine }` when the attempt is over (`outcome` `online` on success, else the state it left). A machine reaching us (its hello) also cuts the wait (D48-hello-wakes), so a peer that comes back usually reconnects on its own within a second.
- **What `GET /api/machines` and `machineState` carry** (additive `Machine.connection`): `attempt` (failed attempts since it was last online), `trying`, `nextAttemptAt`, `graceUntil` (while reconnecting), `lastFailure` `{ kind, message, at }` and `hint`. The `/hub` event `machineState` (this machine's only, never on the peer stream) carries the whole `Machine` on every change: a state change, an attempt starting or failing, a pairing, a rename, and a removal (`removed: true`).
- **The UI** (`src/web/components/MachineStatusNote.tsx`, `machine-status.ts`, `src/web/api/useMachines.ts`): the state is read live everywhere it shows, so a block lifts the moment the machine is back.
  - **Reconnecting:** the session header and a note under the composer say "Reconnecting to studio-pc… · attempt 3 · next try in 8 s" with a spinner; nothing is disabled (a message, an answer or a Pause is held by the service until it is back). The machine tag reads "studio-pc · reconnecting…".
  - **Offline:** "studio-pc is unreachable · retrying in 8 s" + **Reconnect now**, the last error with its time ("Last error 14:05:09: connection refused — …") and the hint; the composer, question cards, Pause / Close and the model picker are disabled as before (D48-cache-persist). While Reconnect now tries it spins and is disabled; a failure shows "Not reached: <reason>" next to it. The tag reads "studio-pc · unreachable" (and "· auth failed", "· no address").
  - **Settings → Machines:** each row's state (with a spinner while reconnecting or trying), the same status line, last error and hint, and **Reconnect now**.
  - The schedules table, the loop cards and the New-session form's Machine row follow the state too (a reconnecting machine can be chosen there; its calls are held).
- **The service log** (stdout / stderr; for the installed service `<dataDir>/logs/service.log`, `docs/service.md`) has one line per change, with the machine's name and id and never a token: `switchboard peers: studio-pc (abcd…): online → reconnecting (the connection was cut (…))` (warn), `… attempt 3 failed (connection refused — …); next try in 5 s` (info; every attempt while reconnecting, then the first five and every 20th), `… reconnecting → offline (…; 4 failed attempts)` (warn), `… offline → online after 9 failed attempts` (info), `… Reconnect now` (info).
- **Tuning / tests:** `SWITCHBOARD_PEER_GRACE_MS`, `SWITCHBOARD_PEER_STALL_MS`, `SWITCHBOARD_PEER_HOLD_MS` (100–600000 ms; test servers use a 3 s grace). `SWITCHBOARD_PEER_TEST_HOOKS=1` (tests only) adds `POST /api/test/peers/drop` (cuts the peers' open streams to this machine) and `POST|DELETE /api/test/peers/outage` `{ ms }` (stops this machine's peer listener for a while: connection refused), so the two-process tests simulate drops without a real network.
- **Not done:** showing whether Tailscale reaches the peer directly or through a relay (`tailscale status --json`) is left open (OPEN reconnect-tailscale-path).

## The peer API (listener)

Served only on the peer listener (`src/server/peers/listener.ts`), never on the UI port:

| Route | Auth | What |
|---|---|---|
| `POST /peer/v1/pair` | the one-time code | the exchange above; 403 `{ error: "pairing-refused", reason: no-code \| expired \| wrong-code \| too-many-tries }` |
| `POST /peer/v1/hello` | bearer | `{ id, name, version }`; the caller's `{ address }` is remembered |
| `DELETE /peer/v1/pair` | bearer | the caller removed us: forget it too (204) |
| `GET /peer/v1/events` | bearer | Server-Sent Events: this machine's `sessionUpdated`, `event`, `questionBatch`, `activity` and `inboxChanged` (its own count), never a peer's; `: keepalive` every 10 s |
| `GET/POST/PUT/DELETE /peer/v1/api/*` | bearer | the allow-listed local API (below), answered as the local UI would get it |
| `POST /peer/v1/sidebar` | bearer | D71: the shared sidebar layout's exchange (*Shared sidebar layout (D71)* below); merged only while this machine's switch for the caller is on; body limit 8 MiB |

Guard (first hook, every request and every 404): `Host` must be exactly `<bound address>:<port>` (403 `forbidden-host`); any `Origin` header is refused (403 `forbidden-origin`: no browser page ever talks to it); every route but the pairing exchange needs `Authorization: Bearer <token>` whose sha256 matches a paired machine's inbound hash (constant-time; 401 `unauthorized`). The UI cookie is no credential here. Bodies are limited to 1 MiB.

## Remote sessions: the proxy (P2)

A paired machine's sessions show and work here as if they were local: the sidebar lists them with a **machine tag** (`MachineTag`: the machine's name, "· unreachable" while it is not online), and the whole session view (chat, question cards, queued messages (D44), D50 Stop and Stop background tasks, pause / resume, model and effort, title, close / reopen, Remote Control, Diff, Artifacts, Timeline, subagent chats, background tasks) is the same view on the same routes. Nothing in the views knows about peers beyond the tag.

- **Remote ids.** A peer's session id, question batch id and Inbox item id become `r~<machine id>~<the peer's id>` (`remoteId`; local ids are UUIDs and never start with `r~`), so they never collide with local ones and the service knows where a request belongs. The mapping is `src/core/peer-wire.ts`: sessions (and their loops), session details (events, questions, artifacts), events (an AskUserQuestion call's `payload.requestId`, which is its batch id), questions (batch and session ids; the question id stays raw: an answer names it), Inbox items (id, session, questions), and the `/hub` events `sessionUpdated`, `event`, `questionBatch`, `activity`. A peer's session and Inbox item carry `machine: { id, name, state }` (additive; `null` on this machine's own sessions).
- **Lists.** `GET /api/sessions` adds the paired machines' **open** sessions as last known (cached from each connection: the list at connect, then every `sessionUpdated`; a closed one leaves the cache), with `machine.state` telling whether they can be reached now. `GET /api/inbox` adds the **reachable** machines' items (an unreachable machine's items cannot be answered, so they are not shown). Nothing waits on the network: both read the caches.
- **Forwarding.** Every `/api` route runs one `preHandler` first (`registerPeerForwarding`): when its `:id` or `:batchId` param is a remote id, the request goes to that machine's peer API with the id made raw (`/peer/v1/api/sessions/<id>/…`), and the answer comes back mapped (by method and path, `peerAnswerKind`). An unknown machine is 404 `not-found`; an unreachable one 502 `peer-unreachable` (with the reason); a refused token 502 `peer-auth-failed`; every other answer (a 409 refusal, a 422 with fields, a 403 `peer-forbidden` for a route the peer API does not serve) is passed on as it is. Time limits: 30 s, 180 s for a start, the branching preflight and the hooks.
- **Live events.** Each connection's event stream is published on the local bus, mapped, so every open page gets them over its own `/hub`. A peer's `inboxChanged` becomes a local one whose `count` is this machine's items plus the reachable peers' (after the peer's Inbox is fetched again). A peer's `questionBatch` goes out once its Inbox item is cached, so the toast, the chime and the OS notification (M3.4) fire for remote batches exactly as for local ones. A machine's state change re-publishes its cached sessions, so the tags follow.
- **No echo, no chains.** Both machines usually listen and connect to each other: an event that came from a peer is published locally with a mark and never sent back out on a peer stream, and requests the peer API injects (header `x-switchboard-peer`) answer this machine's own data only and are never forwarded (a remote id in a peer's path is refused). So machine A sees B's sessions, never C's through B.
- **Workflow agents (D51).** A peer's session carries its Workflow runs and agents as that machine derives them from its own CLI files (`Session.workflows`, `kind: 'workflow'` agents; agent ids stay as they are); a workflow agent's chat, `GET /api/sessions/{id}/workflow-agents/{agentId}/chat`, is in `PEER_API_ALLOW` and comes back with its events namespaced (answer kind `workflow-chat`). Tested with two processes: `tests/server/peers/workflow-agents.test.ts`.
- **Cut messages (fix, 2026-10-01).** `GET /api/sessions/{id}/events/{eventId}/full` (`docs/chat.md` → *Cut messages*) is in `PEER_API_ALLOW`: the peer reads the whole text from its own CLI transcript (and writes a message back into its own event); the answer's `event` comes back namespaced (answer kind `full-event`). Tested with two processes: `tests/server/peers/long-messages.test.ts`.
- **Continue in a fresh session (D83).** `POST /api/sessions/{id}/fresh` is in `PEER_API_ALLOW`: the handover and the fresh session run on the session's machine; the answer is `wrapped` (`{ session }`), `Session.continuedTo` / `continuedFrom` and the dividers' `linkedSessionId` are namespaced, and this machine's sidebar moves a peer's pin / folder place to the fresh session (`docs/fresh-session.md`).
- **Offline** (ruling D48-cache-persist, 2026-09-29: "keep snapshot but block interaction until reconnection"). Each machine's open sessions are stored as last known (`peer_snapshots`, migration 0018; kind `sessions`), and so are the detail and the whole event list of every session opened here (kinds `detail`, `events`), raw as the peer answered. After a restart of this service an unreachable machine's sessions stay listed, tagged unreachable, and open read-only on that snapshot. **Every interaction waits for the reconnection:** a request to a machine that is not connected is not sent at all; reads of a session's detail and events come from the snapshot, everything else (messages, Stop, pause / resume, model, title, close, answers, Inbox actions, the diff) is refused at once with 502 `peer-unreachable` and the message `<machine> is offline — reconnect to continue`, which the view shows (the header note, a disabled composer with the same line, question cards read-only, Pause / Close disabled, no model picker). The machine keeps running its sessions itself. On reconnection the live list replaces the snapshot (snapshots of sessions no longer open are dropped), and every detail read stores a fresh one. A machine reaching us (its hello) also cuts our reconnect backoff short. Its Inbox items stay hidden while it is unreachable (ASSUMED D48-inbox-offline); while it is only `reconnecting` they stay listed (an answer is held). **Fix · peer reconnects:** all of this applies to `offline` (and auth failed / no address); a machine that just dropped is `reconnecting` first, with reads as above and actions held rather than refused, and the message is now "<machine> is unreachable — it retries by itself; Reconnect now tries at once" (the UI shows its own line with the countdown and **Reconnect now**; *Connection states*).
- **Not proxied** (developer ruling; ASSUMED D48-not-proxied): the peer's settings, folder management, embedded tools, History, the global Artifacts / Solutions views, the terminal handoff (a peer's session header has no "Continue in terminal" / "Attach here": the terminal would be on the other machine), and teleport.

## Starting a session on a peer (P3)

The New-session form has a **Machine** row when at least one machine is paired (D52: for a scheduled run too, see below): "This machine (<name>)" and every paired machine (an unreachable one disabled, with its state). With a peer chosen:
- the **Folder** list, the chosen folder's solutions (the scan), the **Model** row (its reported models and its last choice, D42) and the **Branching** preflight (D40 / D47: run there, against its repos) all come from that machine, through `/api/machines/{id}/api/folders`, `…/models`, `…/solutions`, `…/branching/preflight`;
- **Browse…**, "From a remote session" and "Resume a terminal conversation" are hidden (folder management, teleport and History are not proxied);
- the name check uses that machine's open sessions;
- **Start** posts to `/api/machines/{id}/api/sessions`; the answer is the new session with its remote id, and the view opens it. (`POST /api/sessions` with an additive `machine` field does the same; `machine` naming this machine, or empty, starts here.) The peer's own validation answers (422 fields, 409 refusals) are shown as for a local start.

## A peer's schedules and loops (D52)

Developer request and rulings, 2026-09-29 (`docs/decisions.md` → D52). Code: `src/core/peer-wire.ts` (`peerSchedule`, `peerTerminalLoop`, the answer kinds `schedule`, `schedules`, `terminal-loops`), `src/server/peers/service.ts` (`remoteSchedules`, `remoteTerminalLoops`, `refreshList`), `src/server/api/machines.ts` (forwarding `POST /api/schedules`), `src/server/loops/terminal.ts` + `src/core/derive/terminal-loops.ts` (terminal loops), `src/web/views/ScheduleTable.tsx`, `LoopCards.tsx`, `src/web/modals/NewSessionModal.tsx`.

- **Peer API:** `GET /api/schedules`, `POST /api/schedules`, `POST /api/schedules/{id}/run | pause | resume`, `DELETE /api/schedules/{id}` and `GET /api/terminal-loops` are on `PEER_API_ALLOW`. A peer's request is answered with that machine's **own** schedules and loops only (no chains). The answers are mapped: a schedule's id and its runs' `sessionId` become remote ids and it carries `machine`; a terminal loop's `loop.id` becomes a remote id (its terminal's claude session id stays raw: "Hook into…" names it on that machine, as D48 P4's picker does) and it carries `machine`.
- **Lists, as last known.** Each paired machine's schedules and terminal loops are kept here (fetched when it comes online, when a list read finds them older than 10 s, after every schedule change forwarded to it, and, for schedules, on each `scheduleRun` it sends) and stored as snapshots (`peer_snapshots` kinds `schedules` and `terminal-loops`, key `''`; no migration). `GET /api/schedules` and `GET /api/terminal-loops` add them after this machine's own; nothing waits on the network.
- **`scheduleRun` and `schedulesChanged`** are on the peer event stream (`PEER_HUB_EVENTS`): a peer's schedule saved, paused, resumed or deleted there (ruling D52-peer-edits-live, "push at once": the additive `schedulesChanged` event), or a run starting, being skipped or changing its result, makes this machine fetch that peer's schedules again and then publish the event with the schedule's remote id, so the table and the sidebar badge follow at once. The 10 s staleness refresh and the table's 15 s reload stay as a fallback.
- **Actions.** Run now, Pause / Resume and Delete forward on the schedule's remote id like a session's routes. `POST /api/schedules` goes to a peer when `machine` names it (a new schedule, answered 201 with its remote id) or when `id` is a peer's schedule (an Edit; `machine` naming another machine is 422). Save and Run now take the 180 s limit (a folder scan, a start with worktrees). Retry run on a peer's failed-run Inbox item already went there (the Inbox actions route); **Open fix session** now opens the form on that machine, in the schedule's folder.
- **Offline** (D48-cache-persist): a machine that is not connected keeps its schedules and terminal loops listed from the snapshot, tagged unreachable; every action is refused at once with 502 `peer-unreachable` (fix · peer reconnects: held while it is only `reconnecting`), and the UI disables them with the reason (`<machine> is unreachable`).
- **Loops.** A peer's Switchboard sessions carry their loops as before (`Session.loops`, derived there). **Hooked** terminal sessions now get loops too: the loop tracker also follows the events the hook service imports, and derives a hooked session's loops from its transcript as for an un-hooked one (its scheduled firings are meta lines the chat import skips). **Un-hooked** terminal sessions (listed by `claude agents --json`, not Switchboard's own, not hooked) get loops read from their transcripts on their machine (`GET /api/terminal-loops`, `docs/derivations.md` → *Loop cards* → *Terminal sessions (D52)*). Their cards say why they cannot be opened and offer **Hook into…**, which hooks the session on its machine (D48 P4) and opens it; offline it is disabled with the reason. This machine's un-hooked terminal sessions show the same way (untagged).
- Tests: `tests/core/peer-schedules.test.ts`, `tests/server/peers/units.test.ts` (allow-list), `tests/server/peers/schedules-loops.test.ts` (two processes: full schedule management on A from B, a failed run retried, a terminal `/loop` on A listed on A and B then hooked, the snapshot after A goes away and B restarts), `tests/web/loops.test.ts`, `tests/web/schedule-table.test.ts`, E2E `tests/e2e/peer-schedules.spec.ts`.

## Hooked terminal sessions (P4)

Any Switchboard can follow the `claude` sessions the developer started **by hand in a terminal** on its machine, and a paired machine can do the same through it: the Mac drives a session typed on the Windows PC. It follows `docs/spike-remote-pc.md`'s recommended design; only the unmodified `claude` binary runs, and nothing is scraped from the terminal. Code: `src/server/hooks/` (the service, the installer), `src/hook/sb-hook.ts` (the hook script), `src/core/hooks.ts` (entries, version check, message text, limit), `src/server/api/hooks.ts`.

### Finding the sessions
- `GET /api/terminal-sessions` lists what `claude agents --json` reports as running (`kind` `interactive`), with the name, folder, status (`idle` / `busy` / `waiting` + what for) and start, and whether Switchboard's hooks have reported from it (`hookSeen`) and a wake-up waiter is armed (`waiter`).
- **Switchboard's own sessions are left out**: the CLI's registry entry `<config>/sessions/<pid>.json` says `entrypoint: sdk-cli` (only that file is read; the `.key` files next to it are secrets and are never opened), or the session id belongs to a Switchboard session; their hook calls are answered at once.
- Settings → Machines → **Hook into…** (for this machine, and for every online paired machine through its peer API) lists them; **Hook** opens the session, tagged with its machine when it is a peer's.

### Installing the hooks
Hooks are how Switchboard hears from a terminal session; they go into the **user** Claude settings of that machine (`<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`, `%USERPROFILE%\.claude\settings.json` on Windows), the only place that reaches sessions started anywhere. Only through the explicit **Install hooks** / **Remove hooks** action per machine (developer ruling; it narrows D6's "user settings are never edited" to this action):
- **Backup first:** `settings.json.switchboard-backup-<YYYYMMDD-HHMMSS>` next to the file (no backup when the file did not exist yet; it is then created 0600). The file is written to a temp file and renamed, keeping its mode.
- **Only Switchboard's entries:** each hook Switchboard writes carries `--switchboard-hook` in its command / args; Install replaces exactly those (idempotent: nothing is written, no backup, when they are already current), Remove takes exactly those out (a matcher group, event or `hooks` object left empty goes too) and restores nothing else. A file that is not a JSON object is never changed (the state reads `unreadable`).
- **The entries** (each its own matcher group, appended after the user's own): `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Stop`, `SessionEnd` → `event` (`async`, 30 s: they never delay the terminal); `SessionStart` + `Stop` → `waiter` (`asyncRewake`, 7 days: see *Waiter lifetime*); `PermissionRequest` → `permission` (3600 s). **Windows: exec form**, `{ "command": "<absolute node.exe>", "args": ["<…>\src\hook\sb-hook.ts", "--switchboard-hook", <kind>, <port>, "<token file>"] }`, no shell. macOS / Linux: one command string with every path single-quoted.
- The entries name **this** node (`process.execPath`), **this** checkout's script and **this** UI port: after moving any of them the state reads `outdated` and Install puts the current ones in.
- **CLI version check:** with `claude --version` in the tested range (2.1.284 ≤ v < 2.2.0) the waiters carry the internal `rewakeMessage` ("The developer sent this message from Switchboard:") and `rewakeSummary` ("Message from Switchboard"); otherwise only the documented `asyncRewake`, and the message carries the same words itself (the model then reads it after "Stop hook blocking error…", the terminal shows "Stop hook feedback").
- Changes to the user settings are picked up by running sessions (the CLI watches the file); a session that was already running gets its first waiter at its next turn end.

### The hook script
`node sb-hook.ts --switchboard-hook <kind> <port> <tokenFile>` reads the hook input from stdin and POSTs `{ event, claudePid, entrypoint }` to `http://127.0.0.1:<port>/hook/v1/<kind>` with `Authorization: Bearer <hook token>`. It forwards nothing else of the CLI's environment (never `CLAUDE_CODE_MESSAGING_TOKEN`). **It fails open:** Switchboard down, a wrong token, any answer but 200 → exit 0 with no output, and the terminal behaves as if the hook were not there.
- `event`: answered 204 at once (2 s limit).
- `permission`: held; 200 → the body on stdout (`hookSpecificOutput`), 204 → nothing (the terminal's own dialog decides, as it always can).
- `waiter`: held; 200 `{ message }` → the message on stderr and **exit 2** (the CLI wakes the session with it); 204 (the explicit stop) → exit 0; **anything else is retried** (see *Waiter lifetime*). It is the one hook that does not fail open into exiting: a Switchboard that is down just delays it.

### Waiter lifetime
Fix · hook waiter expiring (`docs/decisions.md`). A waiter must still be there when the developer sends a message to an idle session, however long it idled and whatever Switchboard did meanwhile.
- **7-day `timeout` on the entry.** VERIFIED on the CLI 2.1.285 binary: an async hook without `timeout` is killed after 10 minutes (default `600000` ms) and only re-armed at the next `SessionStart` / `Stop`; the schema takes any positive number (no maximum), the practical ceiling is `setTimeout`'s 2^31-1 ms (about 24.8 days). Switchboard writes `timeout: 604800`.
- **Retries.** The script treats `204` as the only stop (superseded by a newer waiter, the session ended or was unhooked, not a hooked session). A refused or reset connection (Switchboard restarting or updating), `503` (Switchboard shutting down), a bad token, an empty `200` → wait 1 s, 2 s … up to 30 s and long-poll again, for as long as the CLI keeps the hook alive; it also exits when the CLI process is gone. A restarted Switchboard re-creates the session's terminal from the retried call, so the waiter is armed again without a turn.
- **Exactly once.** The host marks a message delivered before it answers the waiter, so a retried long-poll cannot take it twice; a response lost on a connection that dropped in that instant is not redelivered (as before). The rate limit (3 wake-ups a minute) and one waiter per session are unchanged.
- **Old installs: outdated → Update hooks.** Entries without the timeout compare as `outdated` (the state compares the whole entries, so any future change to an entry's options does too): Settings → Machines shows "Terminal hooks: outdated (update them so idle sessions stay reachable)" and **Update hooks** (reinstall: timestamped backup, only Switchboard's entries). A hooked session's header says "Hooks are outdated on <machine> — Update hooks so idle sessions stay reachable" (`hookStatus.hooksOutdated`). A running session's current waiter keeps its old timeout until it re-arms at its next turn.
- **Wording.** `no-waiter`: "No hook listening yet — type anything in that terminal once (the hooks were installed after this session started)". `waiter-stopped` (a waiter was held, or the hooks reported, since Switchboard started, and none is now): "The hook stopped listening (it expired or Switchboard restarted) — it re-arms at the next turn; update the hooks to prevent this".

### Following a session
- **Hook** makes a Switchboard session (`hooked: true`, origin `terminal`, named `term-<name>`, titled with the CLI's session name; no process is ever run for it). Its chat is imported from the transcript (`importTerminalTurns`, the D16 reader): the whole conversation at first, then after every hook event and whenever the file grows (checked every 1.5 s). Status: `run` from UserPromptSubmit, `need` while a permission waits, `idle` after Stop, `done` after SessionEnd (or when `claude agents --json` stops listing it for 15 s).
- **Subagents** (ruling D48-hooked-subagents, 2026-09-29): the session's plain subagents (Agent / Task, background ones too) are imported from `<projects>/<slug>/<session id>/subagents/agent-<id>.jsonl` with `agent-<id>.meta.json` (`agentType`, `description`, `toolUseId`): each becomes an agent (kind `subagent`, its `toolUseId`, so the chat's Agent call opens its chat, D36) with its brief (`agent-prompt`), messages and tool calls, in the agent overview and cards like a supervised session's. Status: `done` once its file ends with an assistant message that ended its turn (`stop_reason: end_turn`), `idle` if the session ended first, else `run`. Read on every sync; the transcript poll also watches these files. **Seam for D51:** workflow agents' files (`subagents/workflows/<runId>/`, `<session>/workflows/`) are not read here (`subagentFiles` lists only `agent-*.jsonl` directly in `subagents/`).
- **Closing** the session unhooks it (the terminal keeps running; held permission calls get no decision; queued messages wait for a later hook); **Reopen** follows it again.
- **Continue in Switchboard** (D72) makes it a Switchboard-run session in place: *Continuing a hooked session in Switchboard (D72)* below.
- **Not available** for a hooked session (the header shows none of them and a note says why; the routes answer 409 `hooked-unavailable`): Pause / Resume / interrupt (D50's Stop and Stop background tasks too: the composer offers neither, Esc does nothing), model and effort, Remote Control, the terminal handoff, and slash commands (a message reaches the model as text, not as a command).

### Live activity and delivery state (D53)
- **The live line.** A hooked session shows the same live activity as a supervised one (the chat line, the sidebar row, the agent cards; `docs/chat.md` → *Live activity line*): a thinking verb from UserPromptSubmit (or the transcript's prompt line), `● <Tool>: <summary>` timed from the transcript's `tool_use` line until its `tool_result`, `Writing…` after a text block, `⏸ Waiting for permission: <tool>` while its PermissionRequest is held, running subagents on their cards, nothing after Stop / SessionEnd. It comes from the transcript (the 1.5 s growth poll, plus a 500 ms poll while a turn runs) and the hook calls; no hook was added (the transcript's `tool_use` line marks a tool's start, so `PreToolUse` is not needed) and no model call is made. Rules: `docs/derivations.md` → *Live activity* → *Hooked terminal sessions (D53)*.
- **Stuck or busy?** While a turn runs and neither the transcript nor any hook call changed for 3 minutes, the line adds `· no activity for 3m` (muted). A long tool or a long thinking block writes nothing either, so the hint only says nothing observable happened; the tool's own clock and the verb still run.
- **What a message waits on** (`Session.hookStatus`): the queued bubble's clock tooltip and a muted line under it say "No hook listening yet — type anything in that terminal once (the hooks were installed after this session started)" (no waiter for an idle session, e.g. one that has not run a hook since the hooks went in, *Limits* 1), "Waiting for the next turn boundary" (a turn runs, or a wake-up is in flight / rate-limited), "Waiting for the session to take it up (delivered to its hook)" (handed to a waiter, not taken up yet) or "Session ended". The header's hooked note adds the no-waiter and ended words, also before a message is sent.
- **Through a peer:** the peer derives it on its own machine; its `activity` events and `sessionUpdated` (with `hookStatus`) reach this machine through the D48 event stream, and the cached session follows the `activity` events, so the sidebar list stays current. The same holds for a peer's **supervised** sessions (VERIFIED D53-peer by `tests/server/peers/live-activity.test.ts`: A's `● Bash` on B's `/hub`, list and detail). A machine that is not online shows no live line; the offline note says why.

### Permissions, plan approval and questions
- The `PermissionRequest` hook's call is **held open**; the request becomes an Inbox item (tagged with the machine for a peer's session) or, for **AskUserQuestion**, a question batch shown as the usual question card in the chat and the Inbox. The terminal shows its own dialog at the same time; **whichever answers first wins**.
- Actions of a hooked session's item: **Allow once**, **Always allow** (only when the CLI suggested rules: its `permission_suggestions` go back as `updatedPermissions`), **Deny** with an optional message to Claude (the Inbox's text field; `{ message }` on `POST /api/inbox/{id}/actions/deny`, at most 2000 characters; empty = the fixed D6 text). A supervised session keeps D6's Allow once / Deny.
- **Plan approval** (ExitPlanMode) is such a permission: Allow once approves the plan, Deny with a message sends feedback.
- **Question cards** (VERIFIED D48-ask-hook, CLI 2.1.284): answering returns `allow` with `updatedInput.answers` (`{ "<question>": "<label or own words>" }`), which the CLI takes as the user's answers.
- **Answered at the terminal first:** the tool's `PostToolUse` (same tool and input) closes the item (a question batch as "Answered in the terminal"), and the held call gets no decision; a turn end (`Stop`) or `SessionEnd` closes every item the session still held; a hook process that goes away (its timeout, the CLI quitting) makes its item stale.

### Replies (the mailbox)
- A chat message to a hooked session shows at once with the D44 clock and waits in the session's mailbox (`pending_messages`, kind `hook-message`, so it survives restarts).
- It goes out to a **live waiter** (the SessionStart / Stop `asyncRewake` hook) **as soon as possible, also while a turn runs** (ruling D48-midturn-policy, 2026-09-29: the CLI folds a mid-turn wake-up into the running turn at the next tool boundary, VERIFIED D48-midturn; a turn that ends before that tool boundary starts the next turn on it), and **once**: every waiting message is marked delivered before the waiter is answered (several go out together, a blank line apart), so no later waiter can take it again. Its bubble keeps the D44 clock until the transcript shows it taken up (the `queued_command` attachment of the fold, or the wake-up's `user` line).
- **One wake-up in flight:** after a wake-up the next waits until the turn that took it up has ended (its UserPromptSubmit, then Stop; after 120 s without that turn, the block lifts). **Rate limit:** at most 3 wake-ups a minute per session; more wait in the mailbox for the window. Together they make the spike's runaway (one message re-delivered after every turn, 52 turns in 50 s) impossible (`tests/server/hooks/service.test.ts`).
- **Waiters:** one per session (a newer one supersedes the older, which ends with no message), held without a server-side time limit (developer ruling: unlimited life; the entry's 7-day `timeout` is the CLI's side, and the script retries), ended by `204` (SessionEnd, the process exiting, unhooking, a newer waiter); Switchboard stopping answers 503, which the script retries. Every terminal session with the hooks has one, hooked or not, so a session hooked later can be woken at once; Switchboard's own sessions get none.
- The transcript's copy of the wake-up (a `user` line or a `queued_command` attachment: `<task-notification>… <system-reminder>The developer sent this message from Switchboard: <text>`) marks the bubble delivered; it shows as the developer's message, not as the raw notification.

### Security (hooks)
- `/hook/*` is served on the UI's loopback listener only (never on the peer listener): Host must be `127.0.0.1:<port>`, any `Origin` is refused, and only `Authorization: Bearer <hook token>` is accepted (the UI cookie is not). The hook token is 32 random bytes in `<dataDir>/hook-token`, 0600 (the data folder is 0700), compared in constant time; it stops other local users and processes from injecting messages or decisions.
- What a hook call can do: report events, hold a permission request for the developer, hold a waiter. Decisions come only from the developer (the Inbox, the question card); messages only from the chat.
- Switchboard reads only the transcripts and the CLI's `sessions/<pid>.json` registry entries, never credentials, the keychain, the `.key` files or `CLAUDE_CODE_MESSAGING_TOKEN`, and runs only the unmodified `claude` binary (`--version`, `agents --json`).

### Limits
1. A session that was running before the hooks were installed gets its first waiter at its next turn end (or when anything is typed once in the terminal); until then Switchboard can follow it but not wake it (`hookSeen` / `waiter` in the picker; D53: the session's header and a queued message say so: "No hook listening yet — …").
2. A message sent while a turn runs is taken up at that turn's next tool boundary (a turn without one more tool call ends first, and the message then starts the next turn); the model may weigh a folded-in message less than a typed one (probe b: Haiku passed it by).
3. In the terminal a wake-up shows as one line ("Message from Switchboard"); the model and the transcript have the text.
4. To the model a wake-up is a system reminder inside a task notification, not a typed prompt.
5. `rewakeMessage` / `rewakeSummary` are internal CLI fields: used only on the tested CLI range, else the plain wording.
6. Workflow agents of a hooked session (`subagents/workflows/…`, `<session>/workflows/…`) are D51's; only plain subagents are imported here.
7. Every tool call that asks for permission on that machine starts one short `node` process (a no-op for sessions that are not hooked), and each terminal session with the hooks keeps one idle `node` waiter.

## Shared sidebar layout (D71)

Developer request D71 (`docs/decisions.md` → *Shared sidebar layout*): paired machines show the same pins, folders, subfolders and order, two-way. The rules of the layout and its storage: `docs/sidebar.md` → *Shared layout (D71)*. Code: `src/server/peers/sidebar-sync.ts` (`SidebarSync`, owned by `PeerService`), `src/core/sidebar-sync.ts` (the wire), `src/core/sidebar-records.ts` (records, merge).

- **Switch per machine:** Settings → Machines → a machine's **Share sidebar layout** (`PUT /api/machines/{id}/sidebar-sync` `{ enabled }`), **off** for every pairing until the developer switches it on (also for pairings made before D71). Stored in the setting `peers.sidebarSync` (`{ <machine id>: { enabled, mergedAt } }`). Each machine has its own switch: a machine only merges and answers records while its own switch for the other is on, so the layout is shared only when **both** are on; with one side on, that side shows **waiting for <machine> to switch it on too**.
- **One item on both machines:** a session is keyed by `<origin machine id>:<session id>` on the wire: machine A's own session `X` and machine B's `r~A~X` are the same item; a third machine's session stays an item too (hidden where it is not listed, as a closed session is). Folder ids are UUIDs, the same everywhere. `collapsed` is each machine's own and never sent.
- **Exchange:** `POST /peer/v1/sidebar` over this machine's outbound connection (the same bearer token and Tailscale-only listener as every peer route; no new event on `/peer/v1/events`, nothing added to `PEER_API_ALLOW`). `{ v: 1, full, folders, places }` → `{ v: 1, enabled, folders?, places? }`:
  - **full** when the switch is turned on and every time the connection comes (back) online: all records both ways, so a machine that was away catches up (deletions arrive as tombstones);
  - **live:** every local change sends the records it wrote to each machine the switch is on for and that is online; a merge that changed something is sent on to the other machines it is on with (never back to its sender), one that changed nothing stops (no echo).
- **Conflicts:** last write wins per item, by hybrid-clock timestamps (`src/core/hlc.ts`; equal clocks — rows from before D71 — by value, the same on both ends): a folder's name, its place (parent + order) and its deletion each on their own clock; a session's place on one. A deleted folder's subfolders and sessions are shown in its nearest live folder above (a session with none is unplaced).
- **First enable: always merge** (developer ruling): the first full exchange with a machine takes the union of both layouts; folders with the same name at the same level (same parent after merging) are combined into the one with the smaller id, top level first and then inside each combined folder; a session placed differently on the two machines takes its **later** placement (rows from before D71 have no time: decided by value, the same on both). `mergedAt` is stored per machine.
- **States** (`Machine.sidebarSync.state`): `off`, `connecting`, `waiting`, `synced`, `unreachable` (catches up when back), `unsupported` (the other machine's Switchboard has no `/peer/v1/sidebar`, 404: "Update <machine> to sync folders"; nothing breaks), `error` (with `error`; tried again at the next change or connect). Changes go out on `/hub` `machineState`.
- **Forgetting** a machine removes its switch and stops the sharing; the layout here stays as it is (D54's trigger still drops the forgotten machine's own sessions' places, which are no longer listed).
- **Limits:** live changes need both machines' listeners on (each sends over its own outbound connection; without the other's listener, its changes arrive at the next full exchange). Tombstones are kept for good (the layout stays small).

## Taking a session over (D65)

"Once Switchboards are connected peer-to-peer, take over a session: e.g. a session running on my Windows PC is stopped there and resumed on my Mac." Rulings: `docs/decisions.md` → D65. Choices where the rulings are silent: `.loop/questions.md` → *D65 · Session take-over*.

- **Two directions, one flow.** A peer's session (a remote id) is taken over **to this machine** (header **Take over to this machine**); this machine's own session is **moved to** a paired machine (header **Move to <machine> ▸**: one reachable machine opens the dialog, several open a small menu). Both are in the sidebar row's ⋯ menu too. The machine whose screen you are on is the **initiating** one: its `TakeoverRunner` (`src/server/takeover/runner.ts`) drives the source and the target through the same operations, local calls for itself and the peer API for the other (`/api/machines/{id}`-style forwarding, `PEER_API_ALLOW`). A session of a third machine cannot be moved by us (no chains of peers).
- **Offered when** the session is open and not moved already, and (a peer's session) its machine is reachable; a demo session (nothing runs it) offers nothing. Refused by the checks: a session that continues in a terminal (attach it first), one that is switching CLI or account, one already being taken over, a conversation the target already has as a session.

### The flow
The dialog's preview is `POST /api/takeover/preview` (nothing changes). **Take over** / **Move** is `POST /api/takeover` → 202 with a run; the dialog polls `GET /api/takeover/runs/{id}` every 400 ms. Steps (`TAKEOVER_STEPS`):

1. **checks** — the source describes the session (`source/inspect`: its repos with branch, remote, uncommitted files, unpushed commits; the conversation's files; queued messages; a hooked terminal's pid), the target judges it (`target/plan`: every repo used, cloned or blocked; the CLI available; the account; a clean checkout; no clash) and any blocker from either side stops here, before anything changed. A hooked session also needs the dialog's confirmation (`confirmStopTerminal`).
2. **stop** — a Switchboard-run session is paused (D7). A hooked session is left running until the capture.
3. **capture** — per repo the **WIP push** (below). A hooked session's terminal `claude` is stopped right after (`HookService.stopTerminal`, below).
4. **transfer** — the conversation's files in 512 KiB chunks (`source/chunk` → `target/chunk`), each file verified by size and sha256 on the target (a damaged file deletes itself and fails the step); a file over **200 MB** is refused up front; names are relative and may not leave the staging folder.
5. **apply** — per repo on the target (`target/apply`): clone if needed, `git fetch` of the temp branch, the real branch checked out (a **worktree session** gets `../<repo>-wt-<session name>` next to the matched repo on the same branch, registered as the session's worktree), fast-forwarded to the pushed tip, the WIP commit undone, the temp branch deleted. Refused with nothing changed when the target's branch has commits the source does not (diverged).
6. **resume** — the conversation is installed where the CLI looks for it, the session is created and spawned (`SessionSupervisor.takeOver`): the same conversation, the chat imported, the divider "Taken over from <machine>", the agent's first message.
7. **finish** — the source session gets `moved_to`, a "Moved to <machine>" note and is **closed** (read-only; `reopen` answers 409); its queued messages are marked handed over; temp branches the target could not delete are deleted from the source; leftovers are reported.

### Code travels through git (the WIP push)
`TakeoverGit.makeWipCommit` fills a **throw-away index** from HEAD (`GIT_INDEX_FILE`), runs `git add -A` there (untracked files in, ignored files out), writes the tree and, when it differs from HEAD's, makes the commit with `git commit-tree -p HEAD` (identity `Switchboard <switchboard@localhost>`, signing off, no hooks). The source's branch, HEAD, index and working tree are **never touched**, so there is nothing to undo there except the temp branch and the remote-tracking ref the push made (both removed). The push is `git push <remote> +<sha>:refs/heads/switchboard/takeover/<id>/<branch>`: the remote is the branch's configured remote, else `origin`, else the only one; with no changes the temp branch points at the branch tip (it still carries unpushed commits and works without an upstream). On the target the remote is the one whose URL **normalises** to the same key (`normalizeRemoteUrl`: scheme, credentials, default port and `.git` dropped, host lower-cased; `git@h:o/r.git`, `https://h/o/r` and `ssh://git@h:22/o/r.git` are one repo). Staged changes arrive unstaged (the WIP tree is flat). Credentials come from each machine's own git configuration; a remote URL is never sent or logged with credentials.

### Matching and cloning
`planRepos` (pure, `src/core/takeover.ts`): the target's saved repo folders and the repos of its saved workspace folders (resolved by the solution names of the session) are the candidates; the one named like the repo wins, then the lowest path. No match: **clone** into the typed path, else next to the target's default folder (a workspace session: into the matched workspace's layout), saved as a repo folder (D14); a path that exists, a worktree path that exists, a branch checked out in another worktree, a dirty checkout a main-checkout session would need, a repo without a remote, or a value that is not safe to pass to git (a branch starting with `-`, a clone URL such as `ext::…`) **block** with the reason shown in the dialog. A workspace session needs a saved workspace folder on the target that holds at least one of its repos.

### Hooked terminal sessions
The dialog's warning and checkbox are required. Switchboard stops **only** the process the live registry (`claude agents --json`, asked fresh) lists with that session's id; if the registry cannot be read nothing is stopped and the take-over fails. macOS / Linux: `SIGTERM`, `SIGKILL` after 10 s; Windows: `taskkill /PID <pid> /T`, then `/F` after 10 s (`src/server/hooks/terminal-stop.ts`). The terminal window and its shell stay open. The stop comes right **after the capture** (so the code and the transcript are final); a failure after it cannot start the terminal's `claude` again, and the run's undo notes say to `claude --resume <id>` there.

### Rollback
`rollbackActions` (pure) lists what to undo for the steps done: on the target the copied files, the restored checkouts (a main checkout is put back on what it had, `reset --hard` + `clean -fd` only undo the restore: its tree was clean before), worktrees made, branches created or moved, clones and their saved folders, the fetch's refs; on the source the temp branches (and a paused session is started again: `respawn` with no message when it was idle, `resume` when its turn was interrupted). The run shows "Undoing the changes…", then "everything was undone" (or what could not be, and why).

### Leftovers
Temp branches are written to the settings key `takeover.leftovers` at the push and removed when deleted, so a crash never loses track of one. After a successful take-over the target deletes them; if that fails the source tries; what is still there is shown in the dialog with **Delete it** (`POST /api/takeover/leftovers/{id}/delete`, through `/api/machines/{id}/api/…` for the other machine's) and listed by `GET /api/takeover/leftovers`.

### Peer API
Added to `PEER_API_ALLOW`: `POST /api/takeover/source/{inspect,stop,capture,stop-terminal,files,chunk,finish,rollback}`, `POST /api/takeover/target/{plan,chunk,apply,abort,resume,close}`, `GET /api/takeover/leftovers`, `POST /api/takeover/leftovers/{id}/delete` (authenticated as every peer route; the long timeout applies). `preview`, the start and the run's status are **not** on the list (a peer never starts a take-over through us). Chunks are base64 JSON under the 1 MiB body limit. Everything the other machine sends that reaches git is validated first (branch, temp branch, repo key, commit ids, clone URL; a clone is `git clone -- <url>`). An operation whose initiating machine never finishes it is rolled back after 30 minutes by the next call about the session.

## Continuing a hooked session in Switchboard (D72)

Developer report, 2026-10-05: a hooked terminal session on the Windows PC could not become a normal Switchboard session, even with its terminal closed (History does not offer D16's move for a conversation that is already a Switchboard session, and the hooked session had no such action). Ruling: `docs/decisions.md` → D72. Choices where the ruling is silent: `.loop/questions.md` → *D72 · Continue a hooked session*.

- **Where:** a hooked session's header (a link in the hooked note, after what stays in the terminal), its sidebar row's ⋯ menu, and its History row offer **Continue in Switchboard** (a peer's only while its machine is reachable). A **closed** (unhooked) hooked session offers it too (developer ruling 2026-10-05): continuing reopens it (D33: the `reopened` line, back in the sidebar), then converts it; only one taken over to another machine is refused (409 `closed`). The action opens a small dialog that asks the service at once (`POST /api/sessions/{id}/continue-in-switchboard`, `docs/handoff/contracts/local-api.md` → *Continue a hooked session in Switchboard (D72)*).
- **Is the terminal's `claude` still running?** (`judgeTerminal`, `src/core/hooked-continue.ts`): the live registry (`claude agents --json`, asked fresh) lists the session → **running**; it does not → **gone**, unless a hook call came less than 15 s ago without SessionEnd and the hook's pid is alive or unknown; the registry cannot be read → **gone** only after SessionEnd or when the hook's pid is dead. Anything else is **unknown** and refused (409 `terminal-unknown`): never taken as gone.
- **Gone:** converted at once. **Running:** 409 `terminal-running` (with the pid); the dialog shows the take-over's kind of warning ("…stops that claude process first (the terminal window and its shell stay open)…") and **Stop the terminal's claude and continue** repeats the call with `confirmStopTerminal: true`: D65's terminal stop (`HookService.stopTerminal`, `src/server/hooks/terminal-stop.ts`: SIGTERM then SIGKILL after 10 s; Windows `taskkill /PID <pid> /T`, then `/F`), then a wait of at most 15 s until the registry no longer lists it. A stop that fails, or a process still listed, answers 502 with the reason and **nothing else changes** (still hooked, messages still queued).
- **Converted in place** (`HookedContinuer`, `src/server/hooks/continue.ts`; `SessionSupervisor.continueHooked`): the transcript's last turns are imported, then the **same record** (id, title, sidebar place, todo list, events, attachments, account / profile) gets `hooked = 0`, `attached = 1`, its canonical cwd, and is resumed with `--resume <claudeSessionId>` in that cwd with the usual injections (D64 standing instruction, D68 `switchboard` todo tools, the account's env), no message (idle). The chat shows the divider **Continued in Switchboard (was a terminal session)** (lifecycle `continued`). Its hook state is released: the waiter gets the explicit stop (204), held PermissionRequest calls get no decision (their Inbox items go stale), the live line ends, and later hook calls for the conversation are answered at once. A spawn that fails puts the record back as it was. No migration.
- **Messages never seen by the model** (developer ruling 2026-10-05, `splitUnseen`): every message still in the mailbox (`pending_messages` kind `hook-message`, never handed to a waiter) goes to the new process as **one** user message; their old bubbles are withdrawn (D50's `withdrawn`), so the chat shows them once, after the divider, with the D44 clock until the CLI takes them up. A bubble **handed to a waiter that never reached the transcript** (the terminal ended first) is **not** sent again by itself: it is marked `notSent` and shows "Not sent: the terminal ended before it took this message up." with **Resend** (`POST /api/sessions/{id}/events/{eventId}/resend`: queued to the session as a new message, the old bubble gives way).
- **Peers:** on a paired machine's hooked session the action runs **on that machine** (`r~<machine>~<id>` is forwarded like every session route; the route is on `PEER_API_ALLOW`, with the long peer timeout); the answer is the session mapped to the remote id.
- **Codex / OpenCode:** hooked sessions are Claude Code only; nothing changes for them.
- **Tests:** `tests/core/hooked-continue.test.ts` (liveness, messages, who offers it, History, the peer API), `tests/web/hooked-continue.test.ts` (the dialog's refusals, the divider), `tests/server/hooks/continue.test.ts` (real processes and fake CLIs: gone → converted with `--resume` and the injections, todos kept, divider, the mailbox message sent; running → 409, confirmed → SIGTERM, waiter and permission released; a handed message → not sent, Resend; closed → reopened and converted; not hooked → 409; a peer's session through the peer API), `tests/server/hooks/continue-refusals.test.ts` (a failed stop and an unreadable registry change nothing), E2E `tests/e2e/hooked-continue.spec.ts` (header and confirmation, History, Not sent → Resend).
