# Plans page (D99, UI lane)

The web UI of Plans (decision D99; the core — storage, scheduler, API, MCP tools, the switch — is described in `docs/plans.md`). Built from the developer's approved clickable mockup. Experimental like Team (D100): everything here renders **only while Settings → Experimental → Plans is on**; while it is off the pages are as they were (the visual specs of the shell, the session panel and Settings pass unchanged). Removal: `docs/plans-removal.md`. Assumptions: `.loop/questions.md` → *D99-UI*.

Code: `src/web/plans/` — `store.ts` (the switch + the plans list, shared), `api.ts` (the calls), `model.ts` (pure rules, `tests/web/plans.test.ts`), `PlansNav.tsx` (nav item, the session's Plan tab), `PlansPage.tsx` (the list), `PlanPage.tsx` (a plan), `PlanGraph.tsx`, `PlanTimeline.tsx`, `PlanDetail.tsx`, `dialogs.tsx`, `plans.css`, the core lane's `PlansSwitchRow.tsx` (Settings → Experimental → Plans) and the Jira lane's `jira/` (mounted here: `ImportJiraDialog`, `PlanJiraPanel`, `PlanEdgeProposals`, `jiraApi`).

## The switch

The page reads `GET /api/plans/state` (always answered) once, again after the hub reconnects, on `planChanged` (coalesced, ≤ 4 a second) and after the Settings row changes the switch; only while `enabled && available` does it read `GET /api/plans`. Off: no nav item, no Plan tab, no What's-new entry; `/plans` and `/plans/{id}` show "Plans is off" with a link to Settings → Experimental. A plan the switch paused shows **paused · Plans was switched off** (the core's `pausedReason`) until ▶ Resume.

## Nav, routes, Plan tab

- **Plans** in the sidebar nav after the others (and after Team), with the number of running plans.
- `/plans` lists plans; `/plans/{id}` is a plan's page (`router.tsx`: views `plans`, `plan`).
- Every session gets a **Plan** strip at the top of its right panel while Plans is on: **Import from Jira…** (this session as the source) and one link per plan it created, with its progress and state. The right panel has no tabs, so this is the "tab" (ASSUMED).

## The Plans page

A card per plan (this machine's first, newest first): title, external key chip, state (`paused · <reason>`, `running · held: <why>`), D120 a red **"■ N stopped"** chip (`plan-summary-stopped`) while items are stopped, ⎇ target → base, the merge-mode text, progress ("4/7 done", bar, "~3h left"). **＋ New plan**: the session whose todos the plan runs (open, non-plain-folder sessions of this machine), title, target branch, base (default `dev`), and the session's open todos as checkboxes (`POST /api/plans`, then `POST …/items { todoId }` per ticked todo); it opens the new plan.

### Import from Jira

**Import from Jira…** on the list opens the Jira lane's `ImportJiraDialog` (`docs/plans.md` → *Jira import and status sync*) **without a session** (D112): under the epic field, **Where it runs** asks for the machine (with a paired machine), the folder (that machine's saved folders, Browse… on this one, the folder's check line), the CLI and account, and the model and effort. These are the New-session form's pickers (`CliPicker`, `AccountPicker`, `ModelChoicePicker`) and data (`folderChoices`, `folderCheckLine`, `AddFolderPanel`); the component is `jira/WhereItRuns.tsx`. D115: a workspace folder no longer asks for its repositories: the Plan section says "The plan's agent picks each item's repositories after the import; an item starts once it has them." (`jira-repos-agent-note`), and an optional, collapsed **Limit to repositories…** (`jira-repos`, never pre-filled) names them instead (every item then works in those). Everything starts on the last import's place, kept in this browser (`jira/place.ts`, `localStorage`). D119: **Sidebar folder** (`jira-where-sidebar`) picks where the plan goes in SESSIONS: "Sidebar root" and the sidebar's folders as an indented tree (this machine's layout, also for a plan on a paired machine; a folder five levels deep is greyed out). Its default is the sidebar folder holding the most open sessions of the chosen working folder (on the chosen machine: its saved folder or the same path; a session in a "Plan · …" subfolder counts for the folder that subfolder sits in, so a new plan goes next to the earlier ones, not inside one; a tie goes to the folder with the most recently active such session); none → the last choice for that working folder (kept with the last place, `sidebarFolders`, per machine and saved folder); otherwise the root. It follows the working folder until the developer picks one by hand. Create plan sends it as `sidebarFolderId`, and the plan's own subfolder "Plan · <plan title>" appears there with the session first (`docs/plans.md` → *The plan's own sidebar subfolder (D119)*). Create plan starts a new session "Plan · <plan title>" there that owns the plan (the Plan section's title as edited, else the epic summary; the dialog's note shows it) (`docs/plans.md` → *Import into a new session (D112)*), and the footer says why it cannot be pressed while no usable folder is chosen. **Use an existing session instead** opens the session picker of before (open sessions not in a plain folder; **Pick a folder instead** goes back), then the dialog with that session. The session's Plan strip opens the dialog with that session, as before. On `onImported` the new draft plan opens. When the source is a workspace session without solutions (D38), the same note and the optional **Limit to repositories…** show (the workspace's solutions, read-only ones left out; the import's `repos` only when some are ticked; D115). **Create plan** never fails silently: while it cannot be pressed the footer says why ("Give the target branch …", a folder that cannot be used), and a refused create shows the server's message next to the button (field errors also under their field). On the plan page of a Jira plan, a collapsible **Jira · <epic>** section under the header mounts `PlanJiraPanel` (sync, refresh, drift notes, activity; D117: on a draft, **Re-read dependencies from Jira** (`plan-jira-reread`) lists what is removed, added, kept and left out (`plan-jira-relink`) before **Apply**, `docs/plans.md` → *Re-read dependencies from Jira (D117)*). D116: with the write sync, the dialog's sync section and `PlanJiraPanel` show **Move to Done when merged into the feature branch** (`jira-done-on-merge` / `plan-jira-done-on-merge`; checked by default in the dialog) and, while it is ticked, the **"Done" transition** name (`jira-transition-done` / `plan-jira-transition-done`, default "Done"; the panel saves it on Enter or when the field loses focus). The panel's box follows the server's answer (`PUT /api/plans/{id}/jira`). The row wraps at phone widths (the checkbox above the name). The activity shows "Moved PROJ-12 to Done (merged into <target>)". `PlanEdgeProposals` sits above the graph (nothing without pending proposals: "PROJ-12 should wait on PROJ-11" with ✓ / ✕); a draft with two or more items has **Propose order** (`jiraApi.askForOrder`), which asks the source session's agent and toasts "Asked <session> to propose the order — suggestions will appear above the graph".

### Deleting a plan

Each card's ⋯ (`plan-row-menu`, outside the card's link, so it never opens the plan; "Actions for <title>"; ↑ ↓, Esc back to ⋯; 44 px on touch screens) has **Delete…** (`plan-row-delete`), and the plan page's header has **Delete plan…** (`plan-delete`). Both ask first in the shared delete confirmation (`DeleteConfirm`, the artifacts' D89 / D111 one, generalised; `plan-delete-confirm`, Cancel focused): "Delete “<title>”? Its items' todos and their sessions stay; only the plan goes." A **running or paused** plan adds "It is running: it is cancelled first and its N running sessions are stopped (they stay in the sidebar); then the plan is deleted." (`plan-delete-note`; N = its items whose session is at work, the clause left out when there are none). Delete calls `DELETE /api/plans/{id}?stop=1`: the server cancels the plan, stops those sessions' turns the way their Stop does, and deletes it (`docs/plans.md` → *A plan*); the sessions and their worktrees stay. After the delete the plan leaves the list at once (other windows on `planChanged`), and the plan page goes to the Plans list. A refusal shows in the dialog. A paired machine's plan is deleted on its machine (forwarded); while that machine is unreachable Delete is off and says why. Code: `src/web/plans/PlanDelete.tsx`. The session a Jira folder import created ("Plan · <title>", D112) is not offered for deletion with it: nothing records that it was made for the plan.

## The plan page

**Header:** "Plans ›", the title, the external key chip, `⎇ target → base`, the state, D120 a red **"■ N stopped"** chip while items are stopped (`plan-stopped`); progress "N/M done", a bar and "~3h left" (`estimatedMinutesLeft`; none while an item is blocked). Chips: **merge mode** ("Merge: agents · hold ⚑ 3165" / "Merge: agents" / "Merge: I merge each one" / "Merge mode: not chosen yet"; click → the mode dialog, Start in a draft), **limits** ("3 at once · 85 %"; click → a small dialog, `PUT /api/plans/{id}`), **Critical path on/off** (page-local, on by default). Buttons: ✎ Edit dependencies (draft, running, paused; not on phones), ⏸ Pause / ▶ Resume, Delete plan… (*Deleting a plan* above), ▶ Start plan (draft with items). A paired machine's plan is read-only here. While new starts are held (usage) a line says why.

**Waiting for repositories (D115):** while items of a plan whose repositories its agent picks have none, a line under the header reads "N items: Waiting for the plan's agent to pick repositories." with **Ask again** (`plan-repos-waiting`, `plan-repos-ask`; `POST /api/plans/{id}/solutions/ask`, a toast "Asked <session> to pick the repositories of N items", a refusal in the page's error line). Their cards and rows say "waiting for repositories" and "no repos yet · ~estimate"; the detail says "Waiting for the plan's agent to pick repositories. It starts by itself once it has them (and the items it runs after are done)." Once the agent's `plan_set_solutions` lands, the items show their solutions in the repo line. Follow-ups 2026-10-20: the line's text is unchanged; when the repositories are not picked in time (or the ask could not be sent) the Inbox also shows **Pick repositories** with Ask again and Open plan (`docs/inbox.md`).

**Tabs:** Graph (default), Timeline, List. The **detail** of the selected item sits under every view.

### Graph

Left to right; layers by the **longest path** (an item one layer right of its furthest dependency), a layer ordered by the mean row of its dependencies (one barycentre pass), ties by plan order (`graphLayout`; no layout dependency). Cards 190 × 86 px, 48 px between layers: a 3 px coloured left border by state, the state icon, key, "⚑ you" on hold items, title, the status line, a mono "repo · ~estimate".

**Click → session (D120).** A click on a card (or Enter on the focused card) opens the item's **run session** when it has one (a paired machine's too: its run session id is `r~<machine>~<id>`, the link form of the other views); its card then carries a small **ⓘ** (`plan-card-details`, bottom right, "Details of <key>") that shows the item's detail under the view. An item without a session (waiting, ready) shows its detail on click, as before. In ✎ Edit dependencies a click still picks the card. Why: the developer asked for one click to the session responsible; the detail keeps its actions (the question card, Merge, Retry) one click away, and a question's Answer and a ready item's Merge in the List are unchanged.

Keys shorten to their number when every keyed item shares one project prefix (`PROJ-3157` → `3157`), as the design shows. Edges are SVG cubic curves with arrowheads; the **critical path** (`criticalPath.itemIds` of the core) is amber with 2 px edges and dashed card outlines; every item without dependents leads (dashed) into the final dashed **◇ "target → base · yours"** node. The legend sits under the graph. A DAG wider than the panel scrolls sideways inside its box (desktop and tablet), with a soft fade on the side that has more; the final node is reachable at the right end.

**Edit dependencies:** a hint line "Click the ticket that must finish first." → "Now click the ticket that depends on X…"; the second click adds "Y after X" (`POST …/edges`). A loop is refused before anything is sent (and on the server's 409 `cycle`) with the toast "Refused: X already waits on Y — that would be a loop". A click on an existing edge removes it. **＋ Add items from todos** picks the source session's open todos not in the plan.

### Timeline

One bar per item, grouped by repository (its first solution, else the plan's one repo, else "all repos"), on a time axis from the plan's start to the last projected end, a **now** line across. Segments come from the core's history `PlanItem.spans` (`plan_item_spans`; an open span is drawn to now): `running` → agent working (run blue), `waiting-you` → waiting on you (amber), `waiting-dependency` → waiting on a dependency (hatched grey), `paused-usage` → paused for usage (red 60 %), `paused-plan` → the same look, titled with the plan's reason ("Plans was switched off") while open, else "plan paused"; then **projected** (dashed): each open item after its dependencies' projected ends, for its estimate, or what is left of it. Summary: "Waiting on you: 8.6 h of 24 · longest: 3165 merge (3 h) · Projected finish: tomorrow 07:30" — the sum of every `waiting-you` span over the sum of working and waiting-on-you time, the longest single `waiting-you` span (named after what the item waits on while open, "merge" for a developer-merged item's last one, else "wait"). Without spans (older data) the segments are derived from `startedAt` / `waitingSince` / `mergedAt` / `doneAt`.

### List

Compact rows (state icon, key, title, status, repo · estimate); D120: a row with a run session opens it (the row's main button, keyboard too) and has an **ⓘ** (`plan-row-details`, 44 px on touch screens) that shows its detail, except a question's row, whose **Answer** does; a row without a session shows its detail. Each row has an inline **Answer** (selects the item: its question card is in the detail) or **Merge** (a ready-to-merge item: the plan's Merge, `POST …/items/{itemId}/merge`, D102; a refusal shows above the rows). It is the phone's layout.

### Detail

The state icon, key, title, status; its worktree branch, **Open session**, **Jira ↗** (only when the plan's external ref carries a `baseUrl` / `url`; the core's ref has only `system` and `key` today), **PR ↗**, and **⚑ I merge this one** (`PUT …/holds`). Then by state: the real **QuestionCard** with **Reply…** (or a permission request's actions), **Merge / Open PR / Send back / Open diff** (D102: a ready-to-merge item, with the agent's latest message; the plan's own Merge step, `docs/plans.md` → *Merge step*; Send back asks for a comment; Open PR until the item has a PR), the reason on a red rule (with **Retry** for a failed item), D120 a stopped item's "Stopped: <the agent's last message, cut>" on a red rule with "Its agent ended its turn without marking its todo done…" and a primary **Open session** (`plan-detail-stopped-open`), the agent's latest message (running), "Starts by itself when X and Y are done." (waiting), "Merged into <target> · checks ✔" (done).

### The merge-mode dialog

"How should finished tickets be merged into the epic branch?" / "You have to choose — there is no default. You can change it while the plan runs." Three options — **Agents merge**, **Agents merge, with hold points** (tagged *recommended*, with a hold checkbox per open item, pre-ticked from the items' `hold`), **I merge each one** — none pre-selected; Start stays disabled until one is chosen. Footer: "Always on: agents merge only into <target> · checks must be green · a second conflict comes to your Inbox." The same dialog changes the mode of a started plan (**Apply**, `PUT …/mode`, holds first).

D99 follow-up 2026-10-15 (`docs/plans.md` → *Plans for anything*): a fourth option, **No merging** ("An item is done when its agent marks it done…", with the same hold checkboxes: the items you confirm). A plan without a target branch offers only that one, pre-selected ("This plan has no target branch: nothing is merged."). An agent mode on `dev` / `develop` / `main` / `master` (or after the server refused the default or a protected branch with `target-forbidden`) shows the warning checkbox "⚠ Agents will merge straight into `dev`" (`plan-mode-ack`); Start / Apply stay disabled until it is ticked, and send `allowProtectedTarget: true`. **＋ New plan**: the target branch is optional ("No target — items finish when marked done"), and plain-folder sessions are listed. The target chip reads "No merge step", "⎇ dev (agents merge — acknowledged)" or "⎇ <target> → <base>"; a held item of a plan without a merge step shows **to confirm** with **✔ Done** and **Send back** in its detail.

## Responsive

Desktop (≥ 1280): as above. Tablet: the same, padding 16 px, the graph scrolls sideways. Phone (≤ 767): the List only (no tabs, no dependency editing), a tap opens the detail full screen with "‹ <plan>"; dialogs are full-screen sheets; no sideways page overflow.
