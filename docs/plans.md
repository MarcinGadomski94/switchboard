# Plans (D99)

A **plan** groups todo items of one session (D68) into a dependency graph ("B after A") and runs them by itself: a scheduler starts every ready item as a todo run (D76) in its own session and worktree, cut from the plan's **target branch** (the epic's feature branch), keeps at most *N* running at once, and moves an item to done once its work is merged into the target under the plan's **merge mode**. When every item is done, the Inbox says "Plan ready: `<target>` → `<base>`" and the developer merges the epic. Since the D99 follow-up of 2026-10-15 a plan is for anything: any target branch (also `dev` or `main`), or none at all (*Plans for anything* below).

Plans is **experimental**: switchable and revertible like Team (D100). Contract → *Plans (D99)* in `docs/handoff/contracts/local-api.md`; the Plans page (web UI) → `docs/plans-ui.md`; removal → `docs/plans-removal.md`; decision → D99 in `docs/decisions.md`; assumptions → `.loop/questions.md` → *D99*.

## The switch

Settings → Experimental → **Plans** (`experimental.plans`), **off by default**, next to Team.

- **Off:** every plan route answers 404 `plans-off` except `GET /api/plans/state` (the switch); the scheduler does not listen to the hub, polls no PR checks and runs no timer; `plans.db` is not opened (on an install that never switched Plans on it does not exist); the `switchboard` MCP helper registers no plan tools. Nothing runs in the background.
- **On:** `<dataDir>/plans.db` is opened (created on first use), the plans whose source session is gone are deleted, the running ones resume (their items' sessions are followed again; work merged meanwhile is picked up), and the plan tools appear in sessions whose helper starts from then on.
- **Switched off while plans run:** every running plan is **paused** with the reason "Plans was switched off" (`pausedReason`, also shown as `held`). Running items are not stopped: their sessions finish their current turn; nothing new starts and nothing is merged or followed. The file is closed and stays on disk.
- **Switched on again:** those plans show **paused** with the reason; the developer resumes each one (`POST /api/plans/{id}/resume`), which clears the reason and starts ready items again.
- **A broken `plans.db`** (not a database, a failed migration) breaks nothing else: `GET /api/plans/state` reports `{ enabled: true, available: false, problem }`, the plan routes answer 503 `plans-unavailable`, the scheduler does not run, the plan tools are not registered, and every other route works.
- Demo mode never starts Plans (it answers "off"), except the README screenshot run (`SWITCHBOARD_DEMO_EXTRAS=1`, `docs/demo.md` → *Screenshot extras*).

## Storage

Everything of Plans is in its own SQLite file, `<dataDir>/plans.db`, with its own migration list (`src/server/plans/db.ts`, `PLANS_MIGRATIONS`) run by the main database's runner (`db/migrate.ts`, the one Team's `team.db` uses). No migration in `switchboard.db` (the earlier, never released `0043_plans.sql` was removed).

Tables: `plans` (title, source session, target / base branch, repos, merge mode, concurrency, usage threshold, start answers, state, external ref, `held_reason`, `paused_reason`; migration 3: `no_merge` and `allow_protected_target`, a missing target stored as `''`), `plan_items` (todo id, key, hold, solutions, stored state, reason, note, waiting-on, run session, branch, the target tip it was cut from, PR url, checks, conflict count, timeline) and `plan_edges`. Items and edges go with their plan. Session ids are plain text (no foreign key across files): the service deletes a plan whose source session no longer exists (at activation and at every scheduling cycle).

## A plan

- Made from a session (`sourceSessionId`) whose folder is a git repository (a repo folder, or a workspace's solution repos); with a target branch a plain folder is refused (409 `not-a-repo`); a plan without a target may come from any folder.
- **Target branch** optional and any branch (D99 follow-up 2026-10-15; it may equal the base); missing, `null`, empty or `none` = no target. **Base branch** default `dev`. **Repos**: a workspace's solution names (default the session's); a repo folder's one repo. D115: a workspace without any (a session without solutions) makes a plan whose repositories its agent picks per item (*Repositories picked by the plan's agent* below).
- **Max concurrency** 1–16 (default 3); **usage threshold** 1–100 % (default 85).
- **Start answers** (`answers`: work type, mode, phase, coordination, notes) default to the source session's; a workspace item's run is a Full start with them (D76-workspace); `notes` are added to every item's brief.
- **External** `{ system: 'jira', key }`: stored and shown only (the Jira lane fills it).
- States: `draft` → `running` ⇄ `paused` → `done` | `cancelled`. Delete is refused while running. D117 follow-up: `DELETE /api/plans/{id}?stop=1` (the UI's Delete) cancels a running or paused plan first (as Cancel), then stops each item run session whose turn is running through the session's own Stop (D50, the supervisor's interrupt; a hooked terminal session cannot be stopped from here and is reported `hooked`), then deletes the plan; it answers `{ cancelled, stopped: [{ itemId, sessionId, outcome }] }`. The sessions and their worktrees stay. Cancel itself still stops nothing; plain `DELETE` is unchanged (204). A paired machine's plan is deleted on its machine, which stops its own sessions.

## Items and dependencies

- An item is an existing todo of the source session (`todoId`), or a new todo added to its list (`todo: { title, description, plan, priority, estimateMinutes }`). A done todo cannot be planned. At most 100 items.
- Optional ticket **key** (`PROJ-123`): the run branch becomes `PROJ-123-<slug>` (else `todo/<slug>`, D76's form; `-2`, `-3`, … when taken).
- **Hold** (agents-with-holds: the developer merges this one), **solutions** (a subset of the plan's repos; empty = all of them; D115: in a plan whose repositories are picked per item, the workspace's writable solutions it works in, and empty = not picked yet), **after** (ids or keys it runs after).
- A dependency that would close a **cycle** is refused (409 `cycle`, naming the loop).
- View states: `waiting` (D115: also "Waiting for the plan's agent to pick repositories"), `ready`, `running`, `question` (its session waits in the Inbox), `stopped` (D120: its agent ended its turn without finishing, "Stopped — needs you", red; *Stopped items (D120)* below), `needs-you` (D124: its agent ended its turn waiting for the developer, "Needs you", amber, the ask as its reason; *Needs-you items (D124)* below), `ready-to-merge` (D102: its run finished and it waits for the developer's Merge, "Waiting for your merge"; see *Merge step*), `done`, `blocked` (failed, discarded, could not start, its session stopped with an error, a second conflict; and every dependent of a blocked item, with the reason "waiting on PROJ-12, which was discarded"). The view also carries the critical path, progress and the estimated time left.

## Item history (the Timeline)

Each item keeps its history as **spans** (`plan_item_spans` in `plans.db`, migration 2): `running` (its agent works, also while its PR's checks run), `waiting-you` (a question, waiting for your merge, a second conflict, a session stopped with an error, or D120 an item `stopped`: its agent ended its turn without finishing), `waiting-dependency` (an item it runs after is not done or is blocked), `paused-usage` (ready, but the usage threshold holds new starts) and `paused-plan` (the plan is paused, by the developer or because Plans was switched off). Every plan change publishes `planChanged`, and with it the service compares each item's kind now with its open span: a changed kind closes the open span and opens the new one (at most one open per item). A draft has none; a done, failed or about-to-start item has none open; a finished or cancelled plan has every span closed. At activation (a restart, Plans switched on) every plan is brought up to date the same way, so nothing doubles up. While Plans is off nothing changes: open spans stay open (the time off counts in them). `GET /api/plans/{id}` answers each item's newest 200 spans, oldest first (`PlanItem.spans`); "Waiting on you: X h" is the sum of its `waiting-you` spans.

## Stopped items (D120)

Developer report, 2026-10-20: an item's agent ended its turn with its todo open (a CI check needed a re-run it was not allowed to start), and the plan showed the item **running** for 3 hours. Now it shows **stopped**: "Stopped — needs you", red.

- **When.** A started item (stored `running`) whose run session's turn is over and which is not working by the 1.23 rule: its status is `done`, `idle` or `paused`, never `run` (a running turn, subagents, a GitHub Actions wait such as `gh pr checks --watch` or `gh run watch`, and the background work counted for up to 30 minutes all keep `run`: `docs/derivations.md` → *Session status*), its todo is not done, and no other state covers it: not `question` (a pending question or permission), not `ready-to-merge` / `to-confirm` (its PRs green while idle, its todo done: waiting for your merge or confirmation), not `blocked` (an error, a second conflict, failed). In every merge mode, also `none`.
- **Grace period.** Only once its session has been idle that way for **2 minutes** (`PLAN_STOPPED_GRACE_MS`; tests: `SWITCHBOARD_PLAN_STOPPED_GRACE_MS`, `docs/configuration.md`), so the normal "turn ends, then the agent marks the todo done" never flashes red. Within it the item is `running`; the scheduler arms a timer for the end of the grace period and looks again then.
- **PR checks.** Red checks while its session is idle: `stopped` (not `running`, not `ready-to-merge`). Plans' own message about red checks (or the PR watcher's) makes the session work again, so the item is `running` while the agent reacts, and `stopped` again if it ends its turn without finishing. Every PR open with green or no checks while idle stays `ready-to-merge` for an item the developer merges (D102).
- **Reason.** The agent's **last message** (its newest assistant text, not a progress note), whitespace folded and cut to 300 characters (`stoppedExcerpt`), is the item's `reason`; the UI shows "Stopped: <excerpt>" and **Open session** to read it all. `PlanItem.stoppedSince` (additive) is since when (its session's last activity, the turn's end; else the item's start).
- **Back to running.** As soon as its session works again (the developer replied, a turn started), the item is `running` again by itself; a later stop is a new episode.
- **Scheduling.** A stopped item keeps its stored `running`: it holds its concurrency slot, its dependents keep waiting on it (`waiting`, not `blocked`), it is never moved to blocked, and the time left still counts it. Its time is a `waiting-you` span.
- **Inbox.** Becoming `stopped` raises a Needs-you system item, **"Stopped: <key> <title> (<plan>)"** (`kind: plan-stopped`, label **Stopped**, source `plans`, on the item's run session), the excerpt as its detail, with **Open session** (a link to the run session; the item stays open) and **Dismiss**. One per item per stop episode (dedupe `plan-stopped:<item>:<since>`, so a dismissed one is not raised again for the same episode); it closes by itself when the item leaves `stopped` (works again, done, failed), when a new episode starts, or when the plan ends or is deleted (after a restart, a started item that is no longer stopped has its open item closed once). A paired machine's item is merged and its actions forwarded like every system item, phones may act on it, and the devices' push announces it (*Other Inbox items*).
- **Storage.** Nothing new: derived from the session's status and `lastActivityAt` and the todo, the episodes it raised kept in memory. No `plans.db` migration (still 4).
- Tests: `tests/core/plans.test.ts` (*D120*: past / within the grace period, working, a question, an error, green and red PRs, a second conflict, `none` mode, the excerpt), `tests/server/plans/scheduler.test.ts` (*D120*: the timer, the Inbox item once, `waiting-you`, the slot held, the dependent waiting, back to running, a new episode, turn end then todo done never stopped, green vs red PRs, a question, Delete closes it), `tests/server/plans/integration.test.ts` (*D120*: the real path with fake claude: the Inbox item with Open session and Dismiss, closed by a reply, a new episode, Dismiss), `tests/e2e/plans-stopped.spec.ts`.

## Needs-you items (D124)

A run session whose turn ended **waiting for the developer** (its agent's `turn_status` `waiting_for_you` / `blocked`, or the text check of its last message: `docs/derivations.md` → *Session status* → *Waiting for you at a turn's end*) reads `need` with an ask. Its item then shows **needs-you** ("Needs you", amber, the ask as its `reason`) instead of D120's red `stopped`: the agent did not stop unfinished, it asked something. No grace period (the ask is explicit, or the text check found one); it holds its slot, its dependents wait, its time is a `waiting-you` span, and it is `running` again as soon as its session works again (the developer's reply starts a new turn, which clears the wait).

- **Red stays for the rest.** A turn that ended without finishing and without a waiting signal (and **Not waiting** on the session, or a Dismiss of its "Waiting for you" item) is D120's `stopped` as before, after its grace period.
- **No double raise.** The session raises its own "Waiting for you: <session>" Inbox item (`docs/inbox.md`); the plan raises no "Stopped" item for it (an item that is `needs-you` is not `stopped`). A `need` that is a pending question or permission is still `question`.
- **Derived, no migration.** `PlanItemFacts.sessionAsk` (the run session's turn ask) and the session's read status (`effectiveSessionStatus`); `plans.db` is unchanged. A turn's end that reads `need` this way (not only `idle` / `done`) marks the item for a look, like any turn's end (D102's finish).
- Tests: `tests/server/plans/scheduler.test.ts` (*D124*), `tests/web/plans.test.ts` (the state look).

## Merge modes (required at start, no default)

`POST /api/plans/{id}/start` requires `mergeMode` when the plan has a target (422 `merge-mode-required`); the UI pre-selects `agents-with-holds` as the recommendation, the server never picks one. A plan without a target is `none` (any other mode: 422 `target-required`). The `plan_start` tool's description tells the agent to ASK the developer and never choose.

- `agents`: each item's agent opens a PR into the target and merges it once its checks are green.
- `agents-with-holds`: the same, except held items wait for the developer's Merge (*Merge step* below).
- `developer`: every item waits for the developer's Merge (*Merge step* below).
- `none` (D99 follow-up 2026-10-15): no merge step; an item is done when its agent marks its todo done (*Plans for anything* below).

The mode can change while a plan runs (but not to or from `none` once started: the briefs say whether there is a merge step; 409 `started`) (`PUT /api/plans/{id}/mode`), as can holds (`PUT /api/plans/{id}/holds`, or an item's edit `PUT /api/plans/{id}/items/{itemId}` `{ hold }`); running items whose rule changed are told their new rule. The plan's own agent can do both too (D129: `plan_set_mode`, `plan_update_item`), with the same checks and refusals.

## Safeguards

- **Agents merge only into the target branch**; the brief says never to merge anywhere else. **A protected target needs the developer's acknowledgement** (D99 follow-up 2026-10-15; until then a hard refusal): an agent mode (`agents`, `agents-with-holds`) whose target is `dev`, `develop`, `master`, `main`, the repo's default branch or a protected branch (gh, best effort) is refused (422 `target-forbidden`, field `allowProtectedTarget`) unless `start` / `mode` carries `allowProtectedTarget: true`, which is stored on the plan (`Plan.allowProtectedTarget`). The UI asks with a warning checkbox, "Agents will merge straight into `dev`"; the `plan_start` tool tells the agent to ask the developer first. Developer mode (and `none`) may target any branch without it.
- **Green checks first.** In agent modes an item is done when its work is merged into the target and its PR's checks are green or absent (gh `statusCheckRollup`). Without a remote or gh, merged into the local target counts, with a note.
- **Red checks go back to the session**: once per head and failure, the session gets a message; the item stays running and its dependents wait. D109: the PRs are read through the shared PR watcher (`docs/ci.md` → *Plans*); while *Send CI failures to the session* is on, the watcher sends the failure with the failing job's log (at most `ci.maxAttempts` per PR) instead of Plans' own message, and it raises no "PR #n ready to merge" for a running item's session (Plans' Merge step stays).
- **Conflicts**: the first conflict with the target asks the agent to rebase; a **second** becomes an Inbox item for the developer and the item shows blocked.
- **Failed / discarded / blocked items block their dependents** with a reason. Retry (`POST …/items/{itemId}/retry`) puts a failed item back; Mark done (`…/done`) counts it as done; D121 Reopen (`…/reopen`) puts a done item back to work (*Merge step*).
- **Usage**: no new item starts while the account it would use (D82 routing, then D63's pick; D98's merged readings) is at or above the threshold of its 5-hour or weekly window, or spent; `held` says why. Running items go on.

## Plans for anything (D99 follow-up 2026-10-15)

Developer request: an agent skipped `plan_create` because the target had to be a feature branch; "can we allow to make plans for anything?"

- **Any target.** `dev`, `main`, `master` or the default branch are accepted (also equal to the base). `developer` mode needs nothing more; an agent mode needs the acknowledgement above. The header chip reads "⎇ dev (agents merge — acknowledged)"; "Plan ready: dev" when the target is the base.
- **No target, or no merge step.** For work that is not a git merge flow (research, docs elsewhere, ops tasks, agents that push on their own): leave the target out (`null`, `''` or `none`), or start a plan with a target in `mergeMode: 'none'` ("No merging — an item is done when its agent marks it done", the merge-mode dialog's fourth option).
  - The items still run in dependency order within the concurrency and usage limits; a question still shows `question`.
  - An item is **done when its todo is done** and its session's turn is over. Nothing is read from git or gh: no merge, no PR, no checks, no conflict.
  - A **held** item waits for the developer's confirmation instead (`to-confirm`, `waitingOn: confirm`, stored like the Merge as `review`): an Inbox item "Confirm done: <item> (<plan>)" (`kind: plan-confirm`, dismiss-only) and, on the item, **✔ Done** (`POST …/done`) or **Send back**. Merge and Open PR answer 409 `no-merge-step`.
  - Without a target the run is D76's own: cut from the source session's branch in a repo (a worktree), else in the source folder; a plain folder may be a source. With a target in `none` mode the runs are cut from the target as before.
  - The brief says there is no merge step: commit, push or open a PR only if the todo asks for it; mark the todo done at the end.
  - A session closed before its todo is done fails the item. The last item done raises "Plan done: <title>" in the Inbox. The header chip reads "No merge step".
- **Compatibility.** Plans made before are unchanged (`allowProtectedTarget: false`, their mode). `plans.db` migration 3 adds `no_merge` and `allow_protected_target`; migrations 1 and 2 are untouched (their checksums are pinned in `tests/server/plans/migration.test.ts`). The Jira import still requires a target branch (an epic merges into one).
- **MCP:** `plan_create`'s `target_branch` is optional (`none` = no target); `plan_start` takes `merge_mode` `none` and `allow_protected_target`; the descriptions say plans are for anything and when to ASK the developer (the merge mode, the acknowledgement).

## Repositories picked by the plan's agent (D115)

Developer request, 2026-10-20: "when importing plan from jira and directing the sessions withing the folder, i shouldnt be required to specify which repositories should be worked on. agent should be able to pick the solutions itself".

- **When.** A plan with a target branch whose source is a workspace that names no repos: a Jira import into a workspace folder (or from a workspace session without solutions) without `repos`, or `POST /api/plans` / `plan_create` from such a session. `Plan.reposPerItem` is `true`; `Plan.repos` is the union of the items' solutions (empty at first). A repo folder (its one repo), a plan with repos of its own, and a plan without a target are unchanged.
- **Waiting.** A pending item without solutions is `waiting` with the reason "Waiting for the plan's agent to pick repositories" and never starts (a blocked dependency still shows `blocked`). Starting the plan is allowed: such items just wait, and the scheduler starts each one once it has solutions and its dependencies are done. Their span is `waiting-dependency`.
- **The ask.** After the import the plan's source session (the new "Plan · …" session) gets one message that asks for the missing order (when items have no links) and for the repositories: the workspace's solutions (the Repositories picker's list: read-only ones left out), and each item without any (key, item id, todo id, title, the description cut at 600 characters), and to call `plan_set_solutions` once. A failed send is a line of the plan's Jira activity ("Could not ask the session to … pick the repositories"); the import still succeeds (`askedForRepos: false`). **Ask again** on the plan page (`POST /api/plans/{id}/solutions/ask`) asks again for the items still waiting.
- **The ask goes out by itself (follow-ups 2026-10-20).** Not only after an import: an item added without solutions to such a plan (New plan's items, the plan page's add item, `POST /api/plans/{id}/items`) sends the source session the same ask (`PlanService.askForRepos`, `auto`). A burst is one message: the service waits `PICK_REPOS_DEBOUNCE_MS` (2 s) after the last added item. The plan's **own agent** gets no separate message: when it creates the plan (`plan_create`) or adds an item without solutions (`plan_add_item`), the tool's answer is the ask ("This plan's repositories are picked per item, by you: …" and the workspace's solutions; `POST /agent/v1/plans` and `…/items` answer them as `solutionChoices`), because a message to the agent making that very call would only repeat it later; the check below is armed all the same. No ask for a plan with repos of its own, a repo folder's plan or a plan without a target.
- **Not picked in time, or not sent → Inbox (follow-ups 2026-10-20).** The time of the ask is kept in `plans.db` (`plans.repos_asked_at`, migration 4), so the check survives a restart: when Plans activates it re-arms each pending check for the time left (one that fell due meanwhile runs at once). `PICK_REPOS_TIMEOUT_MS` (15 minutes; tests: `SWITCHBOARD_PLAN_PICK_REPOS_MS`) after the ask, if items still wait, and at once when the ask could not be sent, the Inbox raises a Needs-you item for any plan, Jira or not (`kind: plan-pick-repos`, label **Pick repositories**, title "<n> items of "<plan>" wait for repositories", the detail names the items): **Ask again** (asks again, re-arms the check, closes the item), **Open plan** (a link to the plan) and **Dismiss**. One is open per plan (a newer one closes the older); it closes by itself once every item has repositories (any way: the tool, the item edit, a removed item) or the plan ends or is deleted (`plans.repos_ask_raised` remembers there is one). The plan page's line ("N items: Waiting for the plan's agent to pick repositories.", Ask again) stays, and a Jira plan's activity still gets its lines (asked, asked again, could not ask, not picked in time).
- **The tool.** `plan_set_solutions { plan_id, items: [{ item, solutions }] }` (with the other plan tools, only while Plans is on, only for the plan's own source session; `POST /agent/v1/plans/{planId}/solutions`). **Applied at once, not a proposal.** Every entry is checked first and any problem refuses the whole call with the reasons (nothing changes): an unknown item, one that started, one listed twice, no names, a name that is not a solution of the workspace ("not a solution of this workspace: nope (its solutions: …)") or is read-only. In a plan with repos of its own the names must be among them (the tool works there too).
- **Target branch per repo.** A repository's target branch is made or checked when the repository first joins the plan: at Start for the repositories picked by then (as before), and for a started plan when an item's solutions bring a new one (`plan_set_solutions`, the item edit, a new item): the protected-target rule (an agent mode without `allowProtectedTarget`: 422 `target-forbidden`) and `prepareTarget` from the base (409 `no-target`) refuse the call. Each item's run is cut in its own solutions only.
- **The developer** can still change a pending item's solutions with the item edit (`PUT /api/plans/{id}/items/{itemId}` `{ solutions }`, checked the same way), or name the repositories in the import dialog's optional **Limit to repositories…** (the old behaviour: every item works in those, nothing to pick).
- **Paired machines** work as before: Ask again is forwarded to the plan's machine (on `PEER_API_ALLOW`, devices allowed); the tool runs on the machine whose session owns the plan. The Inbox item is a system item of the plan's machine: a paired machine's Inbox merges it (its Open plan names the remote plan) and forwards Ask again and Dismiss there (`POST /api/inbox/{id}/actions/{action}`), and phones may act on it, like every Inbox item.
- **Storage.** The marker needs no migration: it is an empty `repos` on a plan with a target branch, which was refused (422 `repos`) before D115 and so cannot mean anything else; item solutions were stored already. The follow-ups' `plans.db` migration 4 adds `plans.repos_asked_at` (when the last ask was sent, NULL = no check waits) and `plans.repos_ask_raised` (an Inbox item is open); migrations 1-3 are untouched.
- Tests: `tests/server/plans/repos-per-item.test.ts` (with the follow-ups: the batched ask, the tool's answer, no ask for plans with repos, expiry, a failed send, Ask again, the restart), `tests/server/plans/migration.test.ts` (migration 4), `tests/core/plans.test.ts`, `tests/web/plans.test.ts`, `tests/e2e/plans-jira-folder.spec.ts`, `tests/e2e/plans-jira.spec.ts`, `tests/e2e/plans-repos-ask.spec.ts` (the Inbox item, Ask again, Open plan).

## Item runs

An item's run is D76's todo run with the plan's overrides (`TodoRunOverrides` in `src/server/todos/run.ts`): the branch above, cut from the target's tip in each repo it works in (the target is created locally from the base when missing, never pushed), the plan's start answers, and a brief: the todo, its plan / acceptance criteria, the notes, then "commit, push, open a PR into the target, merge rule, mark the todo done".

**Where the run appears (follow-up 2026-10-19):** in the sidebar folder of the plan's source session, right after the source; a later item's run after the earlier ones, so a plan's runs stay together (a source at the root: at the root, after it). `docs/sidebar.md` → *Where runs appear*.

The scheduler is event driven (run sessions' status, todo changes, usage updates), polls the checks of items waiting on them (60 s), and reads git / gh only for items whose session changed. On restart it resumes the running plans.

## Merge step (D102)

Until D102 the developer's Merge was the run session's Review card (D79); review cards were removed, so Plans has its own step. It applies to the items the developer merges: every item in `developer` mode, the held ones in `agents-with-holds`.

- **Ready:** an item's run is finished when its todo is done (the brief's last step, the agent's `todo_done`) and its session's turn is over, or when every pull request of its branch is open with green (or no) checks while its session is idle. The item then waits on `merge` (`waitingOn: 'merge'`, view state **`ready-to-merge`**, "Waiting for your merge", violet; stored as `waiting_on = 'review'`, the value `plans.db`'s migration 1 CHECK allows) until it is merged or sent back. Its time counts as `waiting-you`.
- **Inbox:** becoming ready raises a system item **"Ready to merge: <item> (<plan>)"** (kind `plan-ready-to-merge`, source `plans`, on the item's run session; actions **Merge** and **Open plan**; `InboxItem.route` = `/plans/<id>`). **Merge** runs the plan's Merge (refusals answer 409 with the reason; the item stays open); **Open plan** only navigates (the item stays open). It is closed when the item is merged (here or by the agent), sent back, or fails. A paired machine's item names its plan by its remote id.
- **Merge** (`POST /api/plans/{id}/items/{itemId}/merge`): the item's branch in every repo it worked in (its run session's worktrees on that branch) is merged into the plan's target **locally, never pushed, never forced**. Every repo is checked before any is merged (`src/server/worktrees/branch-merge.ts`, `BranchMergeGit`, moved from the old review cards' `ReviewGit`): refused 409 `uncommitted` (the worktree has uncommitted changes: they would not be merged), `target-dirty` (the target is checked out somewhere with uncommitted tracked changes), `conflicts` with `conflicts: [files]` (`git merge-tree --write-tree`, no working tree touched), `target-missing`, `no-branch`; also `not-ready` (not waiting for your merge), `busy` (its session's turn runs, or another action on the item runs), `finished` (the plan is done / cancelled). Then where the target is checked out `git merge --no-edit <branch>` runs there (hooks run; a failure is aborted), else the target ref moves with `git update-ref` (a fast-forward, or a merge commit from the conflict-free tree); D122: the merge commit's message is "Merge <key> into the plan's target" (or "Merge a plan item into the plan's target" without a key), never git's "Merge branch '<branch>' into <target>", whose target name may carry the epic's key; a target that exists only as `origin/<target>` is created locally. The item is done (`note`: "merged by you into <target>"), its todo done, its dependents may start. The developer's Merge is the developer's choice: it is not limited to agent-safe targets.
- **Open PR** (`…/open-pr`): `git push -u origin <branch>` (never forced; 409 `no-remote` without an `origin`), then an open PR of the branch is reused or `gh pr create --base <target>` opens one; its URL is the item's `prUrl`. The item stays ready. D122: its title is "<key>: <todo title>" with any other ticket key left out of the title, and its description is "<title>\n\nAn item of a Switchboard plan. Opened from Switchboard's Plans page." (no longer the plan's title, which may carry the epic's key).
- **Send back** (`…/send-back`, `{ comment }`, 1–4,000 characters, else 422): the comment goes to the item's session ("Plans: your work on "<item>" was sent back with this comment: …"; the normal message path), its todo goes back in progress, the item runs again (ready again when its run finishes once more: a new Inbox item).
- **Open diff**: the run session's Diff tab (UI only).
- **The agent merged it itself** (against the rule): the next look at git (a turn end, the poll) finds the branch merged into the target and the item is done with the note "merged into <target> without your Merge". In agent modes this is how every item is done (unchanged).
- **What "merged" means (D121).** An item is merged only when, in every repo it has work in, one of these holds (`PlanGit.inspect`, `src/server/plans/git.ts`):
  - its PR into the target is merged (gh `MERGED`; a closed or open PR never counts, nor one into another base); or
  - the branch has **commits of its own** and its tip is in the local target or in `origin/<target>` (the remote-tracking ref as it is: Plans adds no `git fetch`). Commits of its own: the tip is beyond where the branch started (its reflog's "branch: Created from" commit, else the recorded `cut`), and at least one reflog entry that made a commit of its own (a commit, an amend, a cherry-pick, a revert, a rebase that kept commits) is still on the branch. A fast-forward, a reset or a rebase onto newer target commits makes none. With no reflog, the commits beyond the recorded cut count.

  A fresh branch is **never** merged. That covers the target moving between the recorded cut and the worktree's cut (another item merged meanwhile), and an agent fast-forwarding its fresh branch to the target. Before D121 both read as merged: the item was done minutes after it started, its todo was marked done, its dependents started without its work, and Jira got "Merged into" and Done. A missing cut proves nothing on its own: then only the reflog or the PR can prove a merge. A repo whose branch is gone, or whose PR cannot be read while it has an `origin`, is **unknown**: never merged, and never a reason to reopen.
- **Auto-repair (D121).** At activation (a restart, Plans switched on) and in every scheduling cycle of a running or paused plan, every item done by the git detection is read again with this rule. That means every done item except the developer's Merge ("merged by you into …") and Mark done ("marked done by the developer"). A proven merge is never read again (until the next activation). An unknown reading is read again at most once a minute and changes nothing. An item whose merge cannot be shown is **reopened**, as below. This is idempotent: a reopened item is no longer done, and its Inbox item is raised once per false done.
- **Reopen (D121).** The auto-repair, or the developer's **Reopen** on any done item of a running or paused plan (`POST /api/plans/{id}/items/{itemId}/reopen`; 409 `not-running` for the plan, `not-done` for the item), does the following:
  - The item is `running` again. With its run session open, it goes on there. With the session closed or gone, it shows D120's **`stopped`**: the reason says to reopen the session or Mark done, and it is never failed for the missing session.
  - Its todo is back `in_progress`, and `merged_at` / `done_at` are cleared.
  - Its note is "Reopened: it was marked merged but its branch isn't in <target>" (or "Reopened: reopened by you"), plus "; Jira was told this was merged/Done — check <key>" when it was.
  - Every dependent that **started while it was done** gets the warning "started before <key> was merged — its branch may lack that work" in its note (a done dependent keeps its note and is only listed). Dependents are neither stopped nor restarted; pending ones simply wait again.
  - An Inbox item (kind `plan-reopened`, label **Reopened**, on the plan's source session, once per false done) says "Reopened <key>: it was marked merged but its branch isn't in <target>". It lists the early-started dependents and the Jira key that was told. The developer's own Reopen raises one only when there is something to list.
  - The Jira lane is told (*Status sync* below).

  A manual Reopen of a really merged item is the developer's call: the next look at git finds it merged again.
- **Ticket keys in PRs, branches and commits (D122).** A tracker's automation acts on every ticket key it finds: a merged PR for ticket 1 whose description mentions ticket 2 moves ticket 2 to Done. Every item brief therefore says, right after the D118 Jira context (which keeps the other keys, since the agent needs them): the PR title, the PR description, the branch name and every commit message may name only this item's own key, never another (not the epic, not a dependency, not a related ticket); other work is referred to without its key (`planOwnKeyRule`). Switchboard's own texts follow the rule:
  - the developer's Merge commit message, above;
  - Open PR's title and description, above;
  - the item branch `<KEY>-<slug>`, whose slug leaves out any other key in the todo's title.
- Tests (D121 / D122): `tests/server/plans/git-merged.test.ts` covers the rule on real temp repos:
  - a fresh branch, the target moved before the cut, a fast-forward;
  - commits not in the target, merged into the local target, merged into `origin/<target>` only;
  - multi-repo, a missing cut, a closed / open PR and one into another base, a gone branch.

  `tests/server/plans/false-merge.test.ts` covers the real scheduler on real repos:
  - the regression: the first look after the start keeps a fresh item running;
  - the auto-repair at a restart and when Plans is switched on: idempotent, with a closed and a gone session, merged only on the remote, Mark done untouched;
  - the developer's Reopen and its refusals;
  - the Merge commit message without the epic key.

  Also: `tests/server/plans/jira.test.ts` (*D121*: no correction in Jira, a real later merge comments and moves to Done again), `tests/core/plans-own-key.test.ts` (the brief's rule next to the context, the key filter, which done items are re-checked), `tests/web/plans.test.ts` and `tests/e2e/plans-reopen.spec.ts`.
- Phones may Merge, Open PR and Send back (as on the cards before); a paired machine's plan item is acted on there through the peer API.

## Continue in a fresh session (D83)

When a plan's source session is continued in a fresh session, the plan follows it: its source becomes the fresh session (`plansFollowContinuation`, called by `POST /api/sessions/{id}/fresh` right after the todos, loops and worktrees move). The todos move with their ids, so every item keeps its todo and pending items still start (their runs are cut from the fresh session). An item whose **run** session is continued is run by the fresh session from then on. While Plans is off (or `plans.db` is broken) the hook does nothing and nothing is recorded: when Plans is switched on, the service follows the sessions' own links (`continuedTo`, or the fresh session's `continuedFrom` when the old one was deleted, along the whole chain) for every source and run session before anything else, and does the same at every scheduling cycle.

## Agents (MCP tools)

While Plans is on, the `switchboard` MCP helper (`src/hook/sb-plan-tools.ts`) adds `plan_create` (target optional), `plan_add_item`, `plan_add_dependency`, `plan_status`, `plan_start` (`merge_mode`, `allow_protected_target`), `plan_set_solutions` (D115: the items' repositories, applied at once), and (D129) `plan_update_item`, `plan_remove_item`, `plan_remove_dependency` and `plan_set_mode` (*Editing items already in the plan* below) (the helper asks `GET /agent/v1/plans`; 200 = on; since 2026-10-16 again on each wake-up, the Plans switch included, and every ~25 s, so the tools appear in running sessions without a restart, `docs/mcp.md` → *Tools that appear without a restart*). They act only on plans whose source is the agent's own session. The helper's server instructions never name them (they exist only while on).

### Editing items already in the plan (D129)

Until D129 the agent could only add: a hold could be set only when an item was added, so an agent asked to hold an item already in the plan tried to add its todo again (refused: "that todo is in the plan already"). The four tools mirror what the developer can already do, through the same `PlanService` methods, so whatever is refused to the developer is refused to the agent with the same reason (the tool answers the refusal's `message`). Like the other plan tools: only while Plans is on (404 `plans-off`), only on plans whose source is the agent's own session (404 "no plan … in this session" otherwise), registered and refreshed with them. An item is given by its id (`[id]` accepted) or its key.

- **`plan_update_item { plan_id, item, hold?, title?, description?, estimate_minutes? }`** → `PUT /agent/v1/plans/{planId}/items/{item}` → `updateItem(…, 'agent')`, the developer's item edit. `hold` while the plan is a draft, runs or is paused, until the item is merged or done (409 `merged` "… is merged already"); in a running or paused plan a running item whose merge rule changed is told its new rule (as `setHolds`). `title`, `description` (`''` removes it) and `estimate_minutes` edit the item's **todo** through the todo service as the agent (its checks: a blank title is 422), only while the item has not started (stored `pending`; otherwise 409 `started` "the item's title, description and estimate change only before the item starts (PROJ-1 is running)"). The developer's `PUT /api/plans/{id}/items/{itemId}` accepts `title`, `description` and `estimateMinutes` the same way. Every check runs before anything is written. **No `after`:** replacing an item's dependencies does not map onto the edge API in one step (a cycle found halfway would leave half the edges changed), so dependencies change with `plan_add_dependency` and `plan_remove_dependency`. The description tells the agent that clearing a hold lets the item's agent merge it on its own, so only when the developer asked.
- **`plan_remove_item { plan_id, item }`** → `DELETE /agent/v1/plans/{planId}/items/{item}` → `removeItem`: an item that is not running or done (409 `started`); its edges go with it and **its todo stays** in the session's list (as the developer's route).
- **`plan_remove_dependency { plan_id, from, to }`** → `DELETE /agent/v1/plans/{planId}/edges/{from}/{to}` → `removeEdge`: `to` no longer waits for `from` (`plan_add_dependency`'s `item` = `to`, `after` = `from`); a missing one is 404 "no such dependency".
- **`plan_set_mode { plan_id, merge_mode, allow_protected_target? }`** → `PUT /agent/v1/plans/{planId}/mode` → `setMode`, the developer's mode change: a draft, running or paused plan; not to or from `none` once started (409 `started`); an agent mode on a protected target without the acknowledgement is 422 `target-forbidden`; running items whose rule changed are told. Its description, like `plan_start`'s, tells the agent to ASK the developer for the mode and for the protected-target acknowledgement and never to choose either itself. Built rather than left out because it gives the agent nothing `plan_start` does not already: the agent picks the same two inputs at start, under the same rule to ask, and the server applies the same refusals; leaving it out would only push the agent back to asking the developer to click.

## Jira import and status sync

A plan can be made from a Jira epic: its child issues become the items, their "blocks / is blocked by" links the dependencies. Optionally, Switchboard keeps the tickets in step with the plan. Code: `src/server/plans/jira/` (client, credentials, store, service, routes, `install.ts`), `src/core/plans-jira.ts` (shapes and pure rules), `src/web/plans/jira/` (the dialog, a plan's Jira section, the credentials form). Contract → *Plans · Jira (D99)*. Like the rest of Plans it is experimental: every route answers 404 `plans-off` and nothing reads or writes Jira while Plans is off.

### Import

1. **Import from Jira…** (the Plans page mounts `ImportJiraDialog`): paste an epic key (`PROJ-10`) or its link (`…/browse/PROJ-10`, `…?selectedIssue=PROJ-10`).
2. **Preview** reads, and creates nothing:
   - the epic (`GET /rest/api/3/issue/{key}`) and its children (`GET /rest/api/3/search/jql`, `parent = PROJ-10`, at most 100; more are reported as cut);
   - per child: summary, description, acceptance criteria, components, status, assignee, original estimate. Acceptance criteria come from a custom field named "Acceptance criteria" (found through `GET /rest/api/3/field`, any case) or else from a description section with that heading (an ADF heading, or a line "Acceptance criteria:"; the section runs to the next heading of the same or a higher level);
   - **dependencies**: every `Blocks` link between two children ("PROJ-12 waits on PROJ-11"); both sides of a link are read and deduplicated; other link types are ignored. D117: a link entry in an issue's `issuelinks` carries the **other** issue under the opposite side's verb. With the type `{ name: "Blocks", inward: "is blocked by", outward: "blocks" }`, issue X whose Jira page says "X blocks Y" has `{ inwardIssue: Y }`, and Y ("Y is blocked by X") has `{ outwardIssue: X }`: both mean "Y waits on X". So on issue I, `outwardIssue: O` = I waits on O, and `inwardIssue: N` = N waits on I (`blocksLinks` in `src/core/plans-jira.ts`; before D117 it read them the other way round);
   - **outside links**: a `Blocks` link to an issue outside the epic is a note ("PROJ-15 waits on PROJ-99 (outside the epic)"), never a dependency;
   - **cycles**: links are taken in ticket order (by the waiting issue, then the one it waits on); a link that would close a cycle is left out and named with the cycle ("PROJ-14 waits on PROJ-13 was left out: PROJ-13 → PROJ-14 → PROJ-13 would be a cycle"). The plan core refuses cycles, so nothing cyclic is ever sent to it;
   - items without any dependency inside the epic are flagged ("no links").
   - D118: what the agents will get besides the text: per ticket, the number of comments (`fields.comment.total`), sub-tasks (`fields.subtasks`), links (remote links from `GET …/remotelink`, read four at a time, plus links to issues outside the epic) and attachments (`fields.attachment`), shown as "2 comments · 2 sub-tasks · 3 links · 2 attachments"; and the epic's description and acceptance criteria (with its own counts), shown collapsed. Only the preview reads these; the import does not.
3. **Create plan** reads the epic again (the server never trusts a preview the page held) and calls the core's seam `PlanService.createFromExternal` with:
   - one item per child: `ref` and `key` = the issue key, title "KEY Summary", the todo's description = D118's short summary: the ticket's description cut to 1,200 characters, then "Acceptance criteria:" with them cut to 1,500, then a line with the ticket's link, components and assignee, then a line saying the full Jira context is read when the run starts (always within the todo's 4,000 characters, so nothing is dropped silently; *Jira context (D118)* below), the estimate in minutes, **no solutions** (the components are shown as a hint; in a workspace without repos the plan's agent picks each item's solutions, D115);
   - the preview's dependencies;
   - `external: { system: 'jira', key: <epic> }`;
   - the title, target branch, base branch and repos from the dialog (title and target pre-filled: "PROJ-10 Acme checkout", `feature/PROJ-10-acme-checkout`); D115: a workspace session without solutions has no repos of its own, and the dialog no longer asks for them: the plan's agent picks each item's repositories (an optional, collapsed *Limit to repositories…* names them instead).

   The plan is a **draft**; its merge mode is chosen at Start (the core requires it). A failure of the core (no target branch, a forbidden branch, too many items) creates nothing.

### Re-read dependencies from Jira (D117)

Plans imported before D117 have every Jira dependency backwards. On a **draft** Jira plan, the plan page's Jira section has **Re-read dependencies from Jira** (`POST /api/plans/{id}/jira/dependencies`, a read of Jira: nothing is written there). It reads the epic's links again with the corrected rule and answers the change (`JiraRelinkDiff`); `{ apply: true, fingerprint }` makes it.

- **Which dependencies change.** Plans do not record where a dependency came from (no new storage for it), so the rule is `jiraRelinkDiff` in `src/core/plans-jira.ts`: a plan dependency that **is** a Jira link (or a Jira link the import left out as a cycle) stays; one that is the **reverse** of a Jira link is what the old import made and is removed, unless it is an accepted proposal; anything else (added by hand, an accepted proposal, a link removed in Jira since) is kept. Then each Jira link the plan lacks is added, unless it would close a cycle with a kept dependency (listed as left out). Links to items no longer in the plan are skipped.
- **Confirmation.** The page lists what is removed, added, kept (yours) and left out before **Apply**. The fingerprint of that diff goes with Apply; if Jira or the plan changed meanwhile the answer is 409 `changed` and the page shows the new change. Nothing to change: the dialog says so.
- **Refused** once the plan has started (409 `not-draft`), for a plan not from Jira (404 `not-jira`), and while Plans is off. The activity line reads "Re-read dependencies from PROJ-10: 2 removed, 2 added, 1 of yours kept". A paired machine's plan is re-read on its machine (forwarded like the other plan Jira routes; a phone may too).

### Jira context (D118)

A Jira plan's agents get everything in Jira they need, read from Jira when it is sent; nothing new is stored. Code: `src/core/plans-jira-context.ts` (shapes, parsing, rendering, caps, the tool's definition), `PlanJiraService.itemContext | askContext | agentContext` in `src/server/plans/jira/service.ts`, and the core's seam `PlanService.setContextSource` (registered by `install.ts`). Everything is derived from what every Jira plan stores (`plan_jira.epic_key`, `plan_jira_items.issue_key`), so a plan imported before D118 gets it too.

- **What is read, per issue** (the ticket and the epic): `GET /rest/api/3/issue/{key}` with summary, description, the acceptance criteria field (else the description's section, as at the import), status, assignee, components, `issuelinks`, `subtasks`, `attachment`; all its comments (`GET …/comment`, oldest first, the newest 500 kept; ADF to text with the import's helpers), except Switchboard's own sync comments (those ending with the `[switchboard:<plan>:<item>:<event>]` marker), which are left out of the run block, the asks, the tool and the preview's counts; its remote links (`GET …/remotelink`: title and URL); and, when it has sub-tasks, their descriptions (`parent = KEY`, at most 50). Attachments are **names only** (never downloaded); remote links (Confluence, Figma, any page) are passed as **URLs** for the agent's own tools.
- **Linked tickets outside the epic**, of any link type (not the epic, not its children): key, summary, status and the phrase Jira shows **on that ticket**. D117's rule, for every type: an entry carries the other issue under the side that issue is on, and this ticket reads the opposite side's phrase, so `outwardIssue: O` reads "KEY <type.inward> O" ("PROJ-15 is blocked by PROJ-99 Mail service (In Progress)", "PROJ-12 is cloned by PROJ-96") and `inwardIssue: N` reads "KEY <type.outward> N" ("PROJ-12 blocks PROJ-97", "PROJ-12 clones PROJ-98"). Real Jira embeds the other issue's summary and status in the entry.
- **At run start.** When an item's run starts, the core asks the Jira lane for the block (`itemContext`) and puts it in the first message after the item's brief and the plan's notes, before "When the work is done" (`planItemBrief`'s `context`). It is "Jira context (read from Jira when this run started, <time> UTC):", the ticket in full (link, status, assignee, components; acceptance criteria; description; sub-tasks; linked tickets outside the epic; links; attachment names; comments, oldest first, with author and date), then "Epic context: <key> <summary> (shortened; the full text is available via plan_jira_context)" (about 3,000 characters: acceptance criteria first, then the description, links and the newest comments).
- **Caps.** The whole first message is at most 40,000 characters (`PLAN_RUN_MESSAGE_MAX`); the block gets what the brief leaves. Over it, the ticket's **comments** are trimmed first (the oldest go, the newest are kept, and the comments' heading says how many were left out), then the **epic** (cut, then left out), then the ticket's own text; the block ends with "Trimmed to keep this message short: …. Call plan_jira_context for everything."
- **No duplicate text.** When the read succeeds and the todo's description is the import's own text (it has the "Jira: <ticket link>" line: both the pre-D118 long text and D118's summary do), the brief leaves the todo's description out: the block has it fresh. A description the developer rewrote without that line is kept.
- **Jira cannot be read at start** (no credentials, network, 5xx): the run still starts, with the todo's imported text and "Jira couldn't be read at start; use plan_jira_context (<reason>)." (and a line of the plan's Jira activity). When only one of the ticket and the epic can be read, the block has that one and says the other could not be read. A run is never blocked.
- **The plan's agent.** Every ask to the plan's source session (the import's order and repositories ask, **Propose order**, **Ask again**, the automatic ask after items without repositories were added) ends with "Epic context (read from Jira now): <key> <summary>" and the full epic (at most 30,000 characters, the oldest comments trimmed first). A failed read is a one-line note instead.
- **The tool.** `plan_jira_context { plan_id?, item?, part?: item | epic | both }` (read-only, open-world; registered with the plan tools while Plans is on) answers the full current context of an item's ticket and/or the epic, read from Jira now (at most 120,000 characters, the oldest comments trimmed first). Agent routes: `GET /agent/v1/plans/{planId}/jira/context?item=&part=` and, without a plan id (a run session's own plan), `GET /agent/v1/plans/jira/context`. Answered only to the plan's **source session** and its **item run sessions** (404 for any other, 404 `not-jira` for a plan not from Jira, 404 `plans-off`, 502 when Jira cannot be read). A run session's default is its own item and the epic; the source session names an item (key or id) or gets the epic.
- **Machines.** Runs start, and asks are sent, on the plan's machine, with that machine's Jira connection; the tool's routes are agent routes of that machine. Nothing changes for paired machines.

### Import into a new session (D112)

From the Plans list, the import needs no session. The dialog asks **Where it runs** (machine, folder, CLI and account, model and effort; D115: no repositories to pick), and the two calls take no session id:

- `POST /api/plans/jira/preview` `{ epic }`: the same preview, read with that machine's Jira connection.
- `POST /api/plans/jira/import`: the import's body plus `folder` (a saved folder's id; omitted = the default folder), `provider`, `model`, `effort`, `profileId` and, for a workspace, optionally `repos` (D115). In order:
  1. it checks the body;
  2. it checks the place: a git repo or a workspace (a plain folder: 409 `not-a-repo`), and a workspace's repos when given, each a solution repo there (D115: none is fine);
  3. it reads the epic;
  4. it starts a session **"Plan · <plan title>"** (the plan title as edited in the dialog, e.g. "Plan · PROJ-10 Acme checkout"; the epic summary when it is empty; name `plan-<epic key>`, then `-2`, `-3`… when taken) through `POST /api/sessions`' own path (`startNewSession`): a Simple start with no message in that folder, with that CLI, model, effort and account. A workspace's repos (when given) become its solutions and the plan's `repos`; without them the plan's repositories are picked per item by that session's agent (D115). Like any New session without a first message, its CLI starts at once and waits, idle;
  5. it makes the plan with that session as its source (`createFromExternal`, the steps above, the ask for the missing order to that session when items have no links, and D115 for the repositories in the same message).

  The answer is `{ plan, jira, preview, askedForOrder, askedForRepos, session }`.

  A refusal in steps 1–3 creates nothing. A refusal after step 4 (the core refuses the plan, …) removes the plan if it was made, closes that session (its process stops) and deletes it with its attachments and exports, then answers the error.

The session is an ordinary one: todos, runs (`todo/<slug>` worktrees cut from its branch, in its folder and repos, with its CLI, model, effort and account), sidebar placement and Propose order work through it unchanged.

### The plan's own sidebar subfolder (D119)

The import body may carry `sidebarFolderId` (a sidebar folder's id; `null` = the sidebar's top level; omitted = no placement, as before D119). It is checked with the place, before the epic is read (404 / 422 on `sidebarFolderId`: an unknown folder, or one five levels deep that cannot hold another). Only once the import succeeded (after step 5) does the server make the plan's own subfolder: named after the session ("Plan · <plan title>", cut to the sidebar's 60 characters at a word break, `planSidebarFolderName`), " (2)", " (3)"… when a folder with that exact name sits at that level, made in the chosen folder (or at the top level) with the session as its first item. It is one write through the D71 layout store, published as `sidebarLayoutChanged` and handed to the shared-layout sync, like a manual move; the answer's `sidebarFolder` names it. A refusal after the session started (the D112 rollback) leaves no folder, since none was made yet; a placement that fails after success is logged and the session stays at the root (the import is not undone). The plan's item runs then land in the subfolder after the session (*Where runs appear*, `docs/sidebar.md`).

- **Paired machine:** the import runs there, but the subfolder is made in the layout of the machine the developer picked from (the dialog lists **this** machine's sidebar folders): `POST /api/machines/{id}/api/plans/jira/import` checks `sidebarFolderId` here, forwards the body without it, and places the answer's session by its remote id. Why: the D54 routes are not on the peer API (the other machine's layout cannot be read or written from here), its folder ids are its own unless the layout is shared, and a write in its layout would leave this sidebar showing the session at the root when sharing is off, the very report D119 fixes. This is how this machine already places that machine's runs (`RunPlaces`), so the runs follow the session here too; with the D71 shared layout on, the records reach the other machine and both show the same subfolder. With sharing off, the other machine's own sidebar shows the session at its root.
- **Unchanged:** Use an existing session instead and a session's Plan strip (no new session, no placement; runs follow that session's folder). **Use an existing session instead** goes back to picking a session (the routes above under `/api/sessions/{id}/…`), and a session's Plan strip imports with that session as before.

### Proposed order (ruling D99-Jira-q1 (b))

The missing order is proposed on the plan, not in the dialog:

- **Asking.** After an import whose epic has items without links (`askedForOrder: true` in the answer), and on **Propose order** for any draft plan (`POST /api/plans/{id}/proposals/ask`), Switchboard sends the plan's **source session** a message the normal way (queued while it works; a hooked session's mailbox): the plan, its items with the unlinked ones marked, its dependencies, and the ask to call `plan_propose_dependencies` once; D118: the message ends with the full epic, read from Jira then. A failed ask after an import is a line of the plan's Jira activity; the import still succeeds.
- **The tool.** `plan_propose_dependencies { plan_id, proposals: [{ from, to, reason }] }` (from = the item that goes first, to = the one that waits; keys or item ids; at most 50) is registered with the other plan tools, only while Plans is on, and only for the plan's own source session. Its description says these are proposals for the developer, not changes. Skipped, with the reason: an unknown item, the same item twice, a dependency the plan has, a pair proposed before.
- **Deciding.** Proposals live in `plans.db` (`plan_edge_proposals`), `pending` / `accepted` / `rejected`. **Accept** adds the dependency through the core's edge API, so a cycle is refused there: the proposal stays pending with the reason (`note`), and a single Accept answers 409 `cycle`. **Reject** records it. Accept all / Reject all act on every pending one. Each decision publishes `planChanged`.
- **UI.** `PlanEdgeProposals { planId }` (the page mounts it on the plan): rows "PROJ-15 should wait on PROJ-14 — <reason>" with ✓ / ✕ and Accept all; nothing when no proposal is pending. Phones may accept and reject; a paired machine's plan is decided on its machine.

### Status sync

A per-plan setting, chosen in the dialog (default **off**) and changeable on the plan (`PlanJiraPanel`, `PUT /api/plans/{id}/jira`):

- **off**: nothing is read or written after the import.
- **read-only**: the tickets are read again (title, status, description, with the import's fields) on **Refresh now** and every 30 minutes while the plan runs. A still-pending item's todo takes the new title and description (an item that started keeps its brief). Each item shows a **drift note** when Jira says Done and the item is not done, still says To Do (category `new`) while the item's run works, or its status changed since the import.
- **write**: read-only, plus, as the plan's items move (followed through `planChanged`, while the plan runs, is paused or just finished):
  - the item's run starts → the **In Progress** transition;
  - its pull request opens → the **In Review** transition and a comment "Pull request opened: <url>";
  - it waits on a developer question → a comment (one per question episode: it is in `question` again after it left);
  - it is merged into the target → a comment "Merged into <target>.", then (D116) the **Done** transition when the plan's **Move to Done when merged into the feature branch** is on (activity: "Moved PROJ-12 to Done (merged into <target>)"). Only a real merge gets the comment: an item the developer marks done gets no comment, and neither does an item in a plan without a merge step (`mergeMode: 'none'`, even with a target), since nothing was merged.

  **Move to Done when merged into the feature branch** (D116; reverses D99's "never Done" on the developer's request) is part of the write sync: per plan, `doneOnMerge` in the import body and `PUT /api/plans/{id}/jira`, a checkbox in the dialog's sync section (shown with write, **checked by default**) and in `PlanJiraPanel`. **On for a new plan** (also when the import body omits it); a plan imported before D116 has it **off** (no surprise for plans already running). It fires only on a **real merge into the target**: an agent's merge (its PR merged, or its branch merged, as the plan detects it) or the developer's **Merge**. Never for an item the developer counts as done with **Mark done** (no merge happened: no comment either), and never in a plan without a merge step (`mergeMode: 'none'`). It runs after the "Merged into" comment is written (or given up), with its own event `done:<item>`; once it is done, a still-pending In Progress / In Review retry for that item is dropped (it would move the ticket back). An issue already in a done-category status is left alone. Since the item is done before the ticket moves, the "Jira says Done; the plan item is …" drift note cannot show for a merged item, also between the merge and the transition.

  The transition names are per plan (defaults "In Progress", "In Review", "Done") and resolved through the issue's available transitions (`GET …/transitions`) by the transition's name or its target status' name, case-insensitive. An issue already in that status is left alone. **A missing transition is a soft failure**: noted on the item (`syncNote`) and in the activity, never retried, never blocking.

**Idempotent writes.** Each write is one event per item (`start:<run>`, `pr-transition:<url>`, `pr-comment:<url>`, `question:<n>`, `merged`, D116 `done:<item>`) recorded in `plan_jira_writes`: done or soft once, never again. **D121, a reopened item:** nothing is corrected in Jira (no comment, no transition back): the developer decides. Its `merged` and `done:<item>` records (any state) are **retired**: renamed `retired:<n>:<event>` and kept for the record. A `reopened:<n>` record moves the item to merge generation *n*, whose events are `merged#<n>` / `done:<item>#<n>`, with a new comment marker. A **real later merge** therefore comments "Merged into <target>." and moves the ticket to Done again (an issue still in Done is left alone, as before). The activity gets a `reopened` line, "<key>: reopened (<why>).", plus " Jira was told this was merged/Done — check <key>; Switchboard corrects nothing in Jira." when the comment or the Done went through. In that case the key is named in the item's note and in the Inbox item. Retiring was chosen over clearing the records so that the activity and the stored history still show what was written. A comment ends with a marker `[switchboard:<plan>:<item>:<event>]`; before posting, the issue's comments are read and a comment with that marker counts as posted (a retry after a lost answer adds no second one). A failed write (network, 5xx, 401) stays pending and is retried at the next `planChanged` or refresh, at most 5 times; a deleted issue is given up at once. Every write, soft failure, give-up, refresh and settings change is a line of the plan's **Jira activity** (`GET /api/plans/{id}/jira`, newest 200).

### Credentials

Jira Cloud REST API v3 with basic auth (the account's email and an API token): from **Settings → Experimental → Plans → Jira connection** (ruling D99-Jira-q3: `JiraCredentialsForm`, part of the Plans row and shown only while Plans is on; stored as one value in the OS keychain through the Team access lane's `SecretStore`, item "Switchboard Jira" / "default"), else from the environment `ATL_BASE_URL`, `ATL_USER`, `ATL_TOKEN`. Settings win when both are set. Requests go only to that base URL (`https://`, or `http://` on loopback for the tests' fake); redirects are refused. See `docs/security.md` → *Jira credentials (D99)*.

### Storage

Plans' `plans.db` (its own connection, opened on first use while Plans is on and closed when it is seen off), tables created when missing (`CREATE TABLE IF NOT EXISTS`, outside the core's migration list): `plan_jira` (epic, base URL, sync, transition names, last refresh; D116 `done_on_merge`, added to an older file when the store opens it, `0` for the plans already there: not one of the core's migrations, like the table itself), `plan_jira_items` (issue key, status at import and as last read, drift, last soft failure, question episodes), `plan_jira_writes`, `plan_jira_activity`, and `plan_edge_proposals` (the proposed order, for any plan). No secret. A deleted plan's rows go with its `planChanged` (`state: null`).

### Machines and devices

Import and sync run on the machine that owns the plan (the source session's machine): a remote session or plan id is forwarded by the peers' proxy and answered there with that machine's credentials. D112: an import into a new session on a paired machine goes through `/api/machines/{id}/api/plans/jira/preview | import` (on `PEER_API_ALLOW`), so the session starts there; the answer's plan and session come back namespaced. The token never travels: the credential routes are refused to peers and phones. Phones may preview, import and change a plan's sync (D73 ruling 2026-10-13); the credential settings are this computer's only.
