# Chat tab (M4.2)

SPEC → Session → Chat, prototype `vSession` chat markup + `msgs` / `card()` / `ssAnswered` / `sendDraft` (its `quick` replies are not in the app: D86). The tab reads only the contract routes and `/hub` (D13): the conversation from `GET /api/sessions/{id}/events` + the `event` stream, the question batches from `GET /api/sessions/{id}`, and it writes through `POST /api/sessions/{id}/messages` and `POST /api/questions/batch/{batchId}/answers`. Code: `src/web/views/session/ChatTab.tsx` (view), `ChatItems.tsx` (the items: bubbles, agent blocks with their step lines, question batches; shared with D36's subagent chats), `chat.ts` (pure state), `session.css` (`sb-chat-*`), the shared `QuestionCard` (`docs/questions.md`); server: `sessionQuestions` in `src/server/sessions/wire.ts`. D36: a subagent's own chat opens in the same tab (*Subagent chats* below).

## What it shows
`chatItems(events, questions, mainAgentId)`, top to bottom:

1. **Only the main conversation**: events of the session's main agent (or of no agent). A subagent's own lines (its text, tools, prompts) belong to its agent card, the timeline (M4.3 / M4.4) and, D36, its own chat; the main agent's `Agent · …` call is the step line that stands for it, and a link to that chat (*Subagent chats*). Without a known main agent every event shows.
2. **Time order**: `ts`, then id. Turns a terminal added while detached carry the transcript's timestamps (M4.1), so they sit where they happened; so does the remote history of a local copy of a remote session (D25), which comes first.
3. **User bubbles** (right, `#212227`, 12px radius, max 72%): every `user` payload: typed here, the task, "Continue.", a service note (restart, stale answers), a terminal prompt or, D25, a prompt of the remote session a local copy came from (`data-origin`: `remote`). D44: a message the agent has not taken up yet shows a clock beside it (*Queued messages* below).
4. **Agent blocks** (left, max 92%): an `assistant` text, then the **step lines** that followed it until the next text, user message, question batch, turn end or lifecycle step. A turn that starts with a tool gets a block without text. Step lines are mono 12px `#8d8c87`, `<mark> <event label>` (labels per `docs/derivations.md` → *Events*):

   | Event | Mark |
   |---|---|
   | tool call with its result | `✓` (`✕` when the result is an error, e.g. an interrupted or denied call) |
   | tool call without a result yet | `●` |
   | AskUserQuestion with an open request but no batch behind it (not read yet, or an input the pipeline turned into a permission item, M3.1) | `⏸` |
   | permission request (`request`) | `⏸` open · `✓` allowed · `✕` denied, cancelled or stale · D24: `✓` answered on claude.ai (the label gets ` · answered on claude.ai`) |
   | automatic denial (`denied`), failed turn (`result` with `isError`), permission-mode mismatch | `✕` |
   | D24 Remote Control (`remote`): `Remote Control on · <link>`, `… on again · <link>` (a reattach), `Remote Control off` | `✓` (`✕` for a failed request: `Remote Control could not … : <the CLI's text>`) |
   | D31 model and effort (`model`): `Model: Opus 5.5 · effort: high` (a change, live or stored for the next start; `docs/model-effort.md`) | `✓` (`✕` for a refusal: `Could not change the model: <the CLI's text>` / `Could not change the effort: …`) |

   Not shown: successful `result`s (the text before them is the answer), lifecycle steps, subagent prompts, events without a `type` (the demo's timeline rows). The demo's terminal lines are successful results (M4.3, `docs/session-panel.md`), so they do not show here either.
5. **Question batches** at their AskUserQuestion call (the tool event's `requestId` = `batchId`); batches with no such event among the loaded events (the demo seed's) come after everything else, in batch order:
   - **waiting** (a question without `answeredAt`: open, or stale and unanswered) → the shared `QuestionCard` with `variant="chat"`: head `n questions · relayed verbatim`, each source in mono blue, the question verbatim in “…”, option pills, `k of n answered`, Send disabled at 45% opacity until every question has an answer. Send posts the contract body; the card stays locked until the reloaded session shows the batch answered. D39: each question ends with **Other…**, which opens a field for an own answer (`docs/questions.md` → *QuestionCard*). A refusal shows `Not sent: <message>` in the status line.
   - **answered** → the answers bubble (right, `12px 12px 4px 12px`, max 80%), one line per question `<source name>: <option label>` (the source's part before `" · "`, prototype `ssAnswered`; D39: an own answer's text verbatim in place of the label, line breaks kept), and under it `● Answers written into the briefs. Blocked agents are resuming…` (mono 12px, `oklch(0.74 0.12 250)`), the SPEC copy, for every answered batch (a stale batch's answers go out as a user message instead, `docs/questions.md`, and that message then shows as a user bubble).

The list stays scrolled to the newest item while the developer is at (or within 32px of) the bottom, and jumps there after they send a message or an answer; scrolling up stops that until they scroll back down.

## Queued messages (D44)
A message of the developer's that the agent has not taken up yet shows a small clock (`docs/decisions.md` → D44). The state comes from the server (`UserPayload.queued`, `Question.queued`; the rules and the CLI's signals: `docs/derivations.md` → *Queued messages (D44)*), live: the bubble's event is re-sent on `/hub` `event` when it changes, and the answers bubble follows the detail reloads.

- **Which bubbles:** a user bubble whose payload has `queued` (`chatItems` → `ChatItem.queued`), and the answers bubble of a stale batch whose answers wait in the outbox (`batchQueued(questions)`). Everything else, delivered messages included, renders exactly as before (no attribute, no element).
- **Tooltip** (`QUEUED_TOOLTIPS`, also the `aria-label`; `role="img"`): `turn` → "Queued: the agent reads it after its current turn"; `resume` → "Queued: sent when the session resumes".
- **Look:** an inline SVG clock (a circle and two hands, `currentColor`, 1.2 px strokes), 12×12, in the SPEC's muted `--muted-3` (`#76756f`). It sits **beside** the bubble, 6 px left of its left edge, its centre on the last line (`bottom: 14px`), and is absolutely positioned inside the message box (`.sb-chat-message[data-queued]` / `.sb-chat-answers[data-queued]` get `position: relative`), so the bubble keeps its size and place and the message's text is unchanged (no text node).
- **When it goes:** the moment the CLI takes the message up (the turn that starts on it, or the running turn absorbing it at a tool boundary); for outbox answers, once they are written (Resume, or the session's next message). A process that ends first leaves no clock behind.
- **Order:** a message queued behind a running turn sits where it was written, so it can come before that turn's reply.
- Test ids: `chat-queued` (`data-reason`: `turn` / `resume`, `title`); the message's `data-queued`, the answers' `data-queued`.

### Hooked sessions (D53)
A message to a hooked terminal session (D48 P4) waits on the terminal's hooks, so its clock says **what** it waits on, in plain words, as the tooltip **and** a muted line under the bubble (`chat-queued-note`, 11.5 px, `--muted-3`, right-aligned; the message gets `data-queued-note`, and the clock moves up to stay beside the bubble). The state is `Session.hookStatus.delivery` (server: `docs/derivations.md` → *Live activity* → *Hooked terminal sessions (D53)*); the words are `HOOK_DELIVERY_TEXT` (`src/core/derive/hooked-status.ts`, `hookedQueuedNote`):

| `delivery` | Words |
|---|---|
| `no-waiter` | No hook listening yet — type anything in that terminal once (the hooks were installed after this session started) |
| `turn` | Waiting for the next turn boundary |
| `handed` | Waiting for the session to take it up (delivered to its hook) |
| `ended` | Session ended |
| `null` | (nothing: the D44 tooltip as before) |

The session header's hooked note adds the `no-waiter` and `ended` words in bold (`session-hooked-delivery`, `hookedDeliveryNote`), also before any message is sent, so a session nothing can wake is visible up front. An offline peer's session shows no line (its offline note says why).

## Stop (D50)
Stop interrupts the running turn only: the process lives on and the session becomes idle, ready for the next message (`docs/decisions.md` → D50; the server side: `docs/supervisor.md` → *Stop the current turn (D50)*). Rules and copy: `src/web/views/session/stop.ts`, `src/core/stop-turn.ts`.

- **Button.** While a turn runs, **Send becomes ■ Stop** (same slot and size, tooltip "Stop the current turn (Esc)"). "A turn runs" (`canStop`) = a live process whose status is `run` (a turn runs, or a message waits for its turn) or `need` (the turn waits on a question or permission), and not only background work (activity `background`, D30 / D43: there is no turn to stop). Clicking posts `POST /api/sessions/{id}/interrupt`; the button reads "Stopping…" (disabled) until the reply. Send is back as soon as the reply says the turn stopped, even before the view's throttled session refresh lands; a new message clears that.
- **Esc** (`escStops`, read in the window's capture phase, like the subagent chat's Esc) stops the turn when nothing else owns the key: no modal, dialog or popover is open (`role="dialog"` / `"alertdialog"` / `aria-modal`: Esc closes that first), focus is not in another text field (the composer's own field is fine; a title being renamed or an own answer keeps its Esc), no modifier is held (**Ctrl+C stays copy**), no IME composes, and no other handler took the key. With no turn running, or a Stop already waiting, Esc does nothing. A subagent's chat has no composer: there Esc goes back to the main chat (D36).
- **Queued messages come back.** D57: their attachments too, as chips (`withdrawnAttachments`). The reply's `withdrawn` texts (messages sent while the turn ran that the agent had not taken up; the D44 clock) are put back into the field in order, separated by a blank line; text already in the field comes after them (it was typed later), and the field gets the focus (`withdrawnDraft`). Their bubbles go: their events carry `withdrawn: true` (`/hub` `event`) and `chatItems` / `chatMessages` leave them out.
- **The "■ Stopped" line.** The stopped turn's result is a step line `■ Stopped` (`data-mark="■"`, the step lines' mono muted look), not a failure `✕`.
- **No acknowledgement.** When the CLI does not acknowledge in time, the chat gets the error step line `✕ Stop: the agent did not stop within 5 s. Pause ends the process.`, and under the field `The agent did not stop in time. Pause ends the process.` with a **Pause** button (D7 Pause). Nothing is killed without the developer.
- **Only background work (ruling).** When no turn runs but the session waits on background tasks (activity `background`, D30 / D43), an outlined **■ Stop background tasks** button sits beside Send (Send stays). It opens a confirmation (D33's dialog look) listing the tasks in the activity line's words; **Stop tasks** posts `POST /api/sessions/{id}/background/stop` (the CLI's `stop_task` for each), **Cancel** or Esc closes it. A wake-up has no CLI task and is listed as "a timer the CLI cannot stop; it stays"; with only wake-ups there is no button. Esc never stops background tasks (`stoppableBackground`, `StopBackground.tsx`).
- **Peers and hooked sessions (D48).** A peer's session stops the same way (through the proxy). A hooked terminal session offers neither button and Esc does nothing: its turns are stopped in its terminal.
- Test ids: `chat-stop` (the button), `chat-stop-timeout`, `chat-stop-pause`; the step line's `data-mark="■"`; `chat-stop-background`, `stop-background-confirm`, `stop-background-task` (`data-stoppable`), `stop-background-yes`, `stop-background-cancel`, `stop-background-error`.

## Markdown (D20)
The text of every user bubble and agent block renders as GitHub-flavored Markdown: `ChatMarkdown` (`src/web/views/session/ChatMarkdown.tsx`, memoized on the text) = `react-markdown` + `remark-gfm` + `rehype-highlight`, with the chat's own rules in `markdown.ts` and the styles in `markdown.css` (`.sb-md`). Only the message text: the step lines, the question cards (questions quoted verbatim), the answers bubble and its note, the composer field, and everything outside the chat (terminal tail, Timeline, Inbox, toasts) stay plain text.

- **Covered:** headings, emphasis / strong / strikethrough, lists (nested, ordered), task lists (read-only checkboxes), tables (column alignment from the delimiter row; a wide table scrolls), block quotes, inline code, fenced code blocks, links, horizontal rules; GFM footnotes work too (their links are in-page `#` links, so they render as text).
- **Raw HTML is never rendered.** No `rehype-raw`, no `dangerouslySetInnerHTML`: an HTML tag, comment or block shows as its source text (a block of it as a paragraph), so `<script>` or `<img onerror>` in a message is just text.
- **Links** (`[text](url)`, `<url>`, and bare URLs / `www.` links / e-mail addresses, the GFM autolink literals: *developer addition 2026-09-28*) open in a new tab (`target="_blank"`, `rel="noopener noreferrer"`). Only absolute `http:`, `https:` and `mailto:` URLs are kept (`safeLinkUrl`, read the way the browser reads an `href`); any other URL (relative, `#…`, `javascript:`, `data:`, …) renders as the link's text without a link. Trailing punctuation is not part of a bare URL (`see https://example.com/a.` links `https://example.com/a`); a URL in inline code or a code block stays text; long URLs wrap inside the bubble. The composer field stays plain text: the link appears once the message is sent and shows in the chat.
- **Images are never loaded:** an image becomes a link to its URL (same rules), labelled with its alt text, or its URL when it has none; inside a link only that label shows (links do not nest). No `<img>` is ever rendered.
- **Syntax colors:** a fenced block with a language (` ```ts `, ` ```bash `, …) is highlighted by `rehype-highlight` with lowlight's 37 common languages (highlight.js classes); a block without a language, or with an unknown one, stays plain (no guessing). The colors are the SPEC's hues in muted form on `bg-code`: keywords / tags in the branch-chip blue, strings and `+` lines in the diff-add green, numbers / types / built-ins in amber (the question hue at the diff colors' chroma), variables and `−` lines in the diff-del red, comments in `--muted-3`, names in `--text-strong`.
- **Code blocks** (`bg-code`, 1 px `--border-card`, 8 px radius, Geist Mono 12px/1.35) never wrap: box-drawing status tables keep their columns exactly, and a wide block scrolls inside itself. At 12px Geist Mono's box-drawing glyphs are about 15.7px tall, so at the 1.35 line height the vertical lines join. Inline code: Geist Mono 12px on `bg-code` with a 1 px border.
- **Plain text looks exactly as before.** The bubble keeps its pre-D20 rules (13.5px/1.55, `--text-2b`, `white-space: pre-wrap`), and the text of a message without Markdown becomes paragraphs without margins, a blank line (1.55em) apart, with soft line breaks kept as line breaks, so it takes exactly the room the plain text took. `rehypeChatText` makes that hold under pre-wrap: it drops the newline nodes that `mdast-util-to-hast` puts between blocks (and after a hard break), which pre-wrap would show as empty lines. Markdown blocks follow the same rhythm: one blank line between blocks, 4px under a heading, 2px between list items. Headings stay modest (16 / 15 / 14 / 13.5px, 600).
- **Performance:** the chat re-renders on every event, so `ChatMarkdown` is memoized on the text; a streamed message re-parses only itself.
- **Status tables (D21):** the newest status table an agent message holds (a box-drawing or pipe table with an Agent and a Status column) is also repeated in the right panel's agent overview under "As reported by the agent" (D27: drawn as a readable table, the original behind an "as printed" popover) (`docs/session-panel.md` → *Agent overview*); the chat itself shows it unchanged.

## Live activity line (D19)
While a turn runs (D30: or, after it, background work the agent started is pending), one line sits between the conversation and the composer, Claude-Code style; it is not rendered at all otherwise, so an idle chat is unchanged. Source: `Session.activity` from the session detail, replaced by each `/hub` `activity` event for the session until the next reload (`useLiveActivity`, `src/web/activity/useActivity.ts`; server side `docs/derivations.md` → *Live activity*). Code: `src/web/activity/activity.ts` (pure copy and formats), `ActivityViews.tsx` (`ChatActivityLine`), `activity.css`. The times are the server's timestamps; the line ticks locally once a second.

| State | Line |
|---|---|
| thinking | spinner glyph, a **playful verb** from Switchboard's own list of 20 (`Pondering…`, `Noodling…`, `Cogitating…`, `Patching through…`, …; `THINKING_VERBS`), the time since the turn started (`12s`, `1m 23s`), then `· ↓ 1.2k tokens` once a thinking-token tick arrived (`formatTokens`: `850`, `1.2k`, `12k`, rounded down) |
| tool | `●` (blinking) and `<Tool>: <summary>` literally (`Bash: npm test`; just the name when the summary is the name), then the time since that tool started (`0:42`, `1:02:03`) |
| writing | spinner, `Writing…`, the time since the turn started |
| waiting | `⏸` (amber, still), `Waiting for you`, the time since the question or permission request opened (`0:42`); D53: a hooked session's held permission request reads `Waiting for permission: <tool>` (`waitingText`) |
| background (D30) | no turn runs, but background work the agent started is pending: `⏳` (amber, still), the oldest pending task's words: `Waiting for GitHub Actions: <summary>` for a command that uses `gh run`, `gh pr checks` or `gh workflow` (the summary is its `gh …` command), `Waking up at 18:40` for a `ScheduleWakeup` (local `HH:MM`), D43: `Running a workflow: <summary>` for a background `Workflow` (its launch's `Summary:`), else `Waiting for a background task: <summary>` (D43: a task the CLI reported of another type included, with its description); then `+N more` (`--muted-3`) when other tasks are pending, then the time since the oldest one started (`3:21`, a tool's clock) |

- The verb changes every 4 s (`VERB_ROTATE_MS`): the turn's start time picks the first verb, then it steps through the list, so the same turn shows the same verb in every tab at the same moment (`thinkingVerb`, deterministic for a given clock).
- The spinner is `·✢✳✶✻✽` stepping in place (a CSS `content` animation on the glyph's `::before`), in the running blue (`--status-run`); `prefers-reduced-motion` stops it.
- Type and colors are the prototype's: mono 12px, `#8d8c87` (the step lines' muted color) with the action in `#c9c8c3`, the tokens in `#76756f`; padding 8px 26px like the conversation. A long action is cut with `…`; the time and tokens always show.
- D30: the pending tasks are `Session.activity.background` (`docs/derivations.md` → *Background work*); the line shows the oldest (`backgroundLine` in `src/web/activity/activity.ts`). While a turn runs the list is there too, but the line reads as the turn (the four rows above). The hourglass asks for text presentation (`font-variant-emoji: text`) in `--status-need`; a font without a text hourglass shows the emoji.
- **Hooked and peer sessions (D53).** A hooked terminal session (D48 P4) shows the same line, from its transcript and hook calls instead of stream-json (`docs/derivations.md` → *Live activity* → *Hooked terminal sessions (D53)*): `Pondering…` from the prompt (UserPromptSubmit, or the transcript's prompt line), `● Bash: npm test 0:42` from the transcript's `tool_use` line until its `tool_result`, `Writing…` after a text block, `⏸ Waiting for permission: Bash` while its PermissionRequest is held, nothing after Stop. No token count (the transcript has none). A paired machine's sessions (supervised and hooked) show their machine's line live through the D48 event forwarding; an offline machine's session shows none.
- **Staleness hint (D53).** A hooked session carries `activity.quietSince` (its newest transcript change or hook call). While its turn runs and nothing changed for **3 minutes** (`STALE_AFTER_MS`, ASSUMED D53-stale), the line ends with `· no activity for 3m` (`chat-activity-stale`, `--muted-3`, `staleHint` / `formatQuiet`: `3m`, `59m`, `1h 5m`), and the sidebar row the same (`session-activity-stale`). A long tool or a long thinking block writes nothing, so the hint means "nothing observable", not "stuck": the developer judges. Never while waiting for the developer, never for a supervised session (its stream is live).
- Test ids: `chat-activity` (`data-state`), `chat-activity-glyph` (`data-glyph`: `spinner` / `●` / `⏸` / `⏳`), `chat-activity-text`, `chat-activity-more` (D30), `chat-activity-time`, `chat-activity-tokens`, `chat-activity-stale` (D53).

## Composer
- **No quick replies (D86).** The prototype's `QUICK REPLIES` row (four pills that filled the draft) is gone (`docs/decisions.md` → D86); the context bar (D49) and the todo strip (D68) keep their places, and the chat gets the height back.
- **Field + 📎 + Send**: placeholder `Message <session name>…` (D22: the session's title, else its name). D26: the field is a textarea that looks like the prototype's one-line input (`rows=1`, same box): **Shift+Enter inserts a line break**, and it grows with its text up to 8 lines (`COMPOSER_MAX_LINES`), then scrolls; Send keeps its one-line height at the bottom while it is taller; after a send it is one line again (`composerKeyAction` in `chat.ts`, the resize in `Composer`). The one-line height is measured whenever the field is empty and again when web fonts finish loading: with `line-height: normal` it follows the font, and a page can render before Geist arrives (under D34's service worker Chromium takes the fonts from its disk cache, not the memory cache, so they land after the first render). Enter (not while an IME composes, not with Shift) or Send posts the trimmed draft to `POST /api/sessions/{id}/messages`; an empty draft sends nothing. On `202` the draft clears (unless it was edited meanwhile); the message shows once the service records it (the `/hub` `event`), so what the chat shows is what the process got. The service resumes a paused session to deliver it (`SessionSupervisor.sendMessage`).
- **Typing stays cheap in a long chat** (fix 2026-10-08, developer report: typing lagged in a long conversation on a phone). The composer owns its draft, so a keystroke renders only the composer (the context bar is memoized); it never re-renders the conversation. The field's height is written only when it changes: the natural height is measured by collapsing the field only when it may have shrunk (taller than one line and the text got shorter or lost a line break, emptied, or a web font loaded), because collapsing it on every key resized the composer and laid the chat out twice per key. The chat area is `flex: 1 1 0px`: with `flex: 1` (a 0% basis) the session column sized it from its content on every layout at phone size. The Esc-stops check returns before its document query for every other key. Measured with 780 messages at 6× CPU throttling (per keystroke, mean): phone 390×844 54 → 23 ms (layout 37 → 7 ms), desktop 15 ms either way (it was already one frame). Guard: `tests/e2e/typing-long-chat.spec.ts` (no conversation component renders while typing, no write to the field's style and no chat resize while typing one line, and a keystroke's layout with the chat shown at most 20× the cost with it hidden). Not done: `content-visibility: auto` on the messages would halve it again on phones, but its paint containment clips what sits outside a message (the D80 ↶, the queued clock) and captures the image viewer (`position: fixed`), and windowing would cost search, selection capture and scroll anchoring; neither is needed at these numbers.
- A refusal shows `Not sent: <server message>` under the field and keeps the draft, e.g. `Not sent: the session continues in a terminal; attach it first` while detached (M4.1). The next send clears it.

## Drafts (D88)
What is typed and not sent stays with the session (`docs/decisions.md` → D88, developer request 2026-10-09: "when I switch from session to session, it shouldn't clear"). Drafts are kept **on the server**, on the machine that runs the session, so they follow the developer to another session and back, through a reload, to a paired device (D73) and to a paired machine's UI (D48: the routes are forwarded to that machine, like every session route). Code: `src/core/drafts.ts` (field keys, value shapes, emptiness, limits), `src/server/drafts/service.ts` + `src/server/api/drafts.ts` + `src/server/db/repos/drafts.ts` (migration 0038), `src/web/drafts/draft-field.ts` (the sync rules, Node-tested) + `useDraft.ts` (the hook) + `session-drafts.ts` (what the page knows per session).

- **What is kept, per session** (the field key, ids are always the session machine's own, `r~<machine>~<id>` made raw):
  - `composer`: the message field's text and the chips already **uploaded** to the session (id, name, size, kind). On restore the server answers only the chips whose upload still exists in that session (an upload removed by the clean-up, or one still uploading when the page left, is not restored; its text is). Chips still uploading are not part of the draft.
  - `question:<batchId>`: a waiting batch's picks: the options picked and the **Other…** own answers (D39), shared by the chat's card and the Inbox's. An own answer comes back closed (its text shown as the answer; a click edits it), so a restore never takes the focus.
  - `review:<reviewId>`: the review card's **Send back** comment (D79); with one, the card opens with its form.
  - `todo-add`: the todo strip's **+ Add** form (D69–D70: title, description, plan, priority, estimate as typed). A form with only the defaults (`No plan`, medium) is empty. With a draft, the session opens with the form open.
  - `todo-edit:<todoId>`: an item's **Edit** form while it is open (kept even unchanged: it reopens).
- **Save:** ~400 ms after the last change (`DRAFT_SAVE_MS`), and at once when the field loses focus, the page hides (`visibilitychange`) or unloads (`pagehide`, with `keepalive`), and when the field goes away (switching sessions, a closed form). `PUT /api/sessions/{id}/drafts/{field}` `{ value, client }`; an empty value clears the draft.
- **Clear:** when the message or answers were sent, the review sent back, the todo saved, or a form cancelled (`DELETE …/drafts/{field}`); an emptied field clears it too. A text just sent is never saved again (on blur or leaving), even if the field still shows it for a moment.
- **Restore:** on opening the session (returning to it in this tab shows what the page knew at once and reads the server again), after a reload, and on another device.
- **Live, and the conflict rule (ruling):** each save or clear publishes `/hub` `draftChanged { sessionId, field, client }` (forwarded between peers with the remote session id); other open pages read the session's drafts again (the writing page skips its own `client`). **Last write wins** on the server, but **what the developer is typing on this device is never overwritten**: a remote change to a field that has focus (or holds text not saved yet) waits; when the field loses focus it saves its own text if it changed since (and so wins), else it reads the server again and shows what is there. A field without focus follows at once.
- **Limits:** a value's JSON at most 64 KB (413 `too-large`; the composer's text at most 50,000 characters), at most 200 drafts per session (409 `too-many`); a bad field or value is 422 `invalid`. Drafts are removed with their session (`ON DELETE CASCADE`).
- **Typing stays cheap:** the text stays each field's own state; a keystroke only arms the save timer (no state above the field changes), so the conversation does not re-render (`tests/e2e/typing-long-chat.spec.ts` stays green).
- **Not kept:** the New-session forms, the review card's Commit message (it is drafted from the agent's summary each time), an offline peer's session (nothing can reach its machine; its field shows the offline note).
- Tests: `tests/server/drafts/drafts.test.ts`, `tests/server/peers/drafts.test.ts`, `tests/web/drafts.test.ts`, `tests/e2e/drafts.spec.ts`.

## Attachments (D57)
Images and files go with a message, as on claude.ai (`docs/decisions.md` → D57). Code: `src/core/attachments.ts` (the pure rules: sniffing, caps, the delivery plan, the content blocks, the files' lines), `src/server/attachments/service.ts` (storage, `prepare`, cleanup), `src/server/api/attachments.ts` (routes, serving headers), `src/web/components/attachments.ts` (the draft's model) + `Attachments.tsx` (chips, 📎, drop, paste, the bubble's attachments, the image viewer) + `attachments.css`.

- **Adding:** **paste** into the field (a paste that carries files attaches them and types nothing; a text paste is untouched, ASSUMED D57-paste), **drop** files on the chat or the composer (the drop zone lights up with a dashed outline only while a drag carries files), or **📎** in the field's row between the field and Send (D86; a 36 px button as tall as the one-line field, kept at the bottom like Send while the field grows; a real `<button>`, so Tab reaches it and Enter / Space open the file picker; several files; the `<input type="file">` is made on click; on touch screens 44 px wide, several files; the `<input type="file">` is made on click). A pasted image without a real name is called `pasted-image-HHMMSS.png`.
- **Chips** above the field (`attachment-chips`): an image's 56 px thumbnail, a file's icon (`IMG` / `PDF` / `FILE`), name and size, a × to remove it. Each uploads at once (`POST /api/sessions/{id}/attachments`, `{ name, data }` base64); while one reads or uploads Send is disabled ("Attaching…"), and one that failed must be removed first. Refused at once, with a line under the chips: an empty file, a file over 20 MiB, the 21st file, more than 50 MiB together.
- **Images are downscaled first** (ASSUMED D57-downscale): a PNG, JPEG or WebP with an edge over 2000 px, or larger than 3.75 MB, is redrawn on a canvas to fit 2000 px (a PNG stays PNG, others become JPEG; still too large → JPEG at lower quality); GIFs are never touched. What the CLI would still not take inline goes as a file (below).
- **Sending:** Enter or Send posts `{ text, attachments: [ids] }`; with attachments the text may be empty. The service sends images and PDFs **inline** (content blocks before the text), other files (and whatever is too large inline) as **paths**: the text gets `Attached files:` and one `- <absolute path> (<size>)` line each. The event keeps the typed text, the attachments (id, name, size, kind, type, how each went: `inline` / `file`) and the text as sent (`sentText`); the bytes stay in the data folder.
- **The bubble** (`message-attachments`, under the user bubble; a message of only attachments has no text bubble): images as thumbnails (at most 220×160; a click opens the viewer, `attachment-lightbox`, closed by a click or Esc, which then stops nothing); PDFs and files as chips with name and size (a PDF opens in a new tab, other files download with `?download`). An image a transcript named without its bytes, or one cleaned up since, shows a dashed placeholder "image".
- **Queued and Stop:** a message with attachments queues like any other (D44, its clock beside it); Stop gives its text back to the field and its attachments back as chips (served thumbnails; still uploaded, so the next send carries them).
- **Hooked terminal sessions:** every attachment goes as a path (hooks carry text only). **A peer's session:** the uploads and the thumbnails go through the proxy to that machine.
- **New session:** the Simple form's message has a 📎 row with the chips under it; the Full form's task field has the 📎 inside its right end and the chips under the row; paste and drop work in both. The files upload at **Start** to the chosen machine (`POST /api/attachments`, staged) and their ids go with `POST /api/sessions`; Start waits while one is still read. Not offered for a schedule, a move or a teleport.

## Context bar (D49)
How full the main agent's context window is, the composer's first row, directly above the field's row (`docs/decisions.md` → D49; D86 removed the quick replies it used to sit on). Code: `src/core/context-meter.ts` (the pure meter: reducer, window, percent, band, transcript replay), the recorder's `#updateContext` (`src/server/supervisor/recorder.ts`), `importTerminalTurns` (`src/server/supervisor/attach.ts`), `toSessionContext` (`src/server/sessions/wire.ts`), `context-bar.ts` + `ContextBar` in `ChatTab.tsx`, `session.css` (`sb-chat-context-*`).

- **Tokens in use** = the latest **main-agent** assistant message's `usage.input_tokens + usage.cache_creation_input_tokens + usage.cache_read_input_tokens`. This is the CLI's own status-line formula (CLI 2.1.284: `used_percentage = round(tokens / window × 100)`, clamped 0–100; `output_tokens` not counted). With `usage.iterations`, the last iteration that is not a `compaction` / `advisor_message` one counts, as in the CLI. A usage whose inputs sum to 0, and `<synthetic>` filler lines, are no reading. Lines with a `parent_tool_use_id` (subagents) never count; neither do `isSidechain` transcript entries.
- **Window** = the result's `modelUsage[<model>].contextWindow` for the reading's model: the key may be the model or the model + `[1m]`, and the key whose `[1m]` matches the session's choice wins. Without a reported window it is derived: `[1m]` in the session's model choice (D31; with no choice, the process's `system/init` model) → 1 000 000, else 200 000. It is resolved on every read, so a model pick in the header re-resolves it at once (e.g. `opus` → `opus[1m]`). A report under 1M does not count for a `[1m]` choice.
- **Compaction:** `system/compact_boundary` (main chain only) stores `{at, trigger, preTokens, postTokens}` and resets the reading to `post_tokens` (unknown without it); the next main usage replaces it. "compacted HH:MM" shows beside the text from the boundary until the next turn starts (the first `system/init` after the compaction turn's `result`). The tooltip always has `Last compacted: HH:MM (<trigger>)`, or `Not compacted yet`.
- **Shows:** a 4 px track (`--border-card`, radius 2 px) filled to the percentage: `--status-done` below 60 %, `--status-need` from 60 %, `--status-fail` from 80 %, banded on the shown (rounded) percentage. Then the text `Context 62% · 124k / 200k` (mono 11 px `--muted-2`; tokens as the activity line writes them: `850`, `1.2k`, `124k`, `1M`), then `compacted 14:05` (`--muted-3`). No reading yet: an empty bar and `Context —`. Tooltip: `Context window: 200,000 tokens · <model>` / `Auto-compact at 84%` (or `Auto-compact off`) / the compaction line. `role="meter"` with `aria-valuenow`.
- **Auto-compact tick (ruling D49-autocompact-mark):**
  - **Position:** a 2 px `--muted-3` tick on the track at `autoCompactPercent`, and the tooltip's middle line `Auto-compact at N%`.
  - **Threshold:** the CLI's own (2.1.284 `kK` + `_Q`): `effective = window − min(maxOutputTokens, 20 000)` (the model's `maxOutputTokens` from the result's `modelUsage`, else 20 000; `CLAUDE_CODE_MAX_OUTPUT_TOKENS` when set), `threshold = effective − 13 000`, or `min(floor(effective × pct / 100), that)` with `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`. The window is clamped to `CLAUDE_CODE_AUTO_COMPACT_WINDOW` when that is smaller.
  - **Auto-compact off:** no tick and `Auto-compact off` in the tooltip, when `autoCompactEnabled: false` or `DISABLE_COMPACT` / `DISABLE_AUTO_COMPACT` is set.
  - **Where the config comes from:** at each spawn, the process's env (Switchboard's, minus the scrubbed `CLAUDE_CODE_*`) plus the user (`<config dir>/settings.json`), project and local (`<cwd>/.claude/settings(.local).json`) settings files, including their `env` blocks, later files winning. It is stored in the meter (`autoCompact`).
  - **Scale:** the CLI compares its threshold with the last usage *including* that reply's output tokens (`Ox`). The bar leaves them out, so compaction can fire slightly before the fill reaches the tick (by about one reply's output).
- **Backfill (ruling D49-backfill):**
  - **When:** a session with no stored meter reads it once from its transcript (`contextFromTranscript` over the newest main chain) in the background of its first `GET /api/sessions/{id}` (`SessionSupervisor.backfillContext`), then publishes `sessionUpdated`, or at its next spawn.
  - **Stored:** the result is stored even when the transcript is missing or unreadable (the empty meter), so it is read once.
  - **Skipped:** a live session (its recorder fills it) and one Switchboard never ran a process for (the demo seed).
- **Where:** the composer's first row (it grows upwards; the field, 📎 and Send keep their boxes). It shows only when `Session.context` is not `null`. That is every session Switchboard ran a process for, but not the demo seed, so the D10 visual gate is unchanged. Subagent chats have no composer and no bar.
- **Stored:** `sessions.context` (JSON, migration 0015; D49 rulings add `maxOutputs` and `autoCompact` inside the JSON, no migration), written by the recorder on each change (the same message's next block with the same usage writes nothing) and announced as `sessionUpdated`, which the session view reloads on. A new process (resume, restart recovery) starts from the stored state. A terminal-turn import (Attach here, a move, a teleported copy) replays the transcript's newest main chain (through the boundary's `logicalParentUuid`) on top of it. A session from before D49 reads its meter from the transcript once (*Backfill* above).
- Test ids: `chat-context` (`data-band`: `ok` / `warn` / `high` / `unknown`, `title`), `chat-context-fill`, `chat-context-tick`, `chat-context-text`, `chat-context-compacted`.
- Tests: `tests/core/context-meter.test.ts`, `tests/server/supervisor/context.test.ts`, the Attach case in `tests/server/supervisor/attach.test.ts`, the D49 lines in `tests/server/hub/hub.test.ts`, `tests/tools/fake-claude-context.test.ts`, `tests/web/context-bar.test.ts`, `tests/e2e/context-bar.spec.ts` (real path: values, colors at 59/60/80 %, placement, live, compaction reset, reload, restart, 1M, unknown), `tests/e2e/visual/context-bar.spec.ts` (own check, `docs/visual/context-bar.md`).

## Subagent chats (D36)

- **Address:** `/sessions/{id}/agents/{agentId}` (the chat tab; the session header keeps Chat as the current tab), parsed and printed by the router; the main chat stays `/sessions/{id}`. It can be linked and reloaded.
- **Which subagents have a chat:** a subagent started by an Agent / Task call Switchboard saw, i.e. one whose `Agent.toolUseId` is set (`hasSubagentChat`; additive on the wire, `docs/handoff/contracts/local-api.md` → *D36*). The main agent and agents seen without a call (the demo's) have none. - **Entry points** (each keyboard-focusable, tooltip "Open this subagent's chat"):
  - the main chat's Agent / Task **step line**: an `<a>` in the step line's own box, color and type (`sb-chat-step--link`: no underline until hovered, a pointer), `data-subagent-id`; the line of a call whose subagent has no chat stays plain text;
  - the subagent's **agent card** in the right panel (the card itself is the link; D37: a finished subagent's card shows once its "✓ N finished" line is expanded);
  - its **row in the D21 overview**: the whole row (a pointer) and its name as a link (`overview-open`). The main agent's card and row stay as they are.
- **What it shows** (`subagentChat(events, questions, agent, agents)`): the session's events are already all loaded by the chat (`GET /api/sessions/{id}/events` does not page), so they are filtered here (no API filter):
  - **top bar** (`subagent-bar`): `← Main chat` (the way back) · the status dot · `<name>: <description>` (the name in `--text`, cut with …, the whole as tooltip), and on the right the agent's live D19 action and time (its card's words: `Thinking…`, `Read: hello.txt  0:03`, …) or its status (`done`, `failed`, its progress text), in its status color;
  - the **brief** as the first bubble (right, the user bubble), labelled `Brief from the main agent` (mono 11px `--muted-3`): the `prompt` of the Agent / Task call that started it (from the main agent's call event), else its first prompt line (`agent-prompt`);
  - its **messages and tool steps** (events whose `agentId` is the subagent's), by the main chat's rules (D20 Markdown, step lines and marks, time order); its first prompt line is the brief delivered, so it is not repeated; a later prompt line (a message the main agent sent it) is a user bubble; a nested Agent call links to that subagent's chat;
  - its **question batches** at its AskUserQuestion calls, read-only (`QuestionCard` with a `note`: no picks, no Send; the footer reads "Answer in the main chat or the Inbox · Open it in the main chat", whose link returns to the main chat with that batch's card brought into view). Batches it did not ask are not in its chat. (M0.2: subagents do not have AskUserQuestion on CLI 2.1.283, so this is for later CLIs.)
  - its **result** as the last block, labelled `Result`: the call's `tool_result` text, verbatim (the CLI's `[Subagent hand-back]` frame included), in a `--bg-card` box with a `--border-card` line (`--status-fail` when the result is an error). None while the call runs, and none for an agent that runs in the background: its call returns only the CLI's launch notice ("Async agent launched successfully", `isAsyncAgentLaunch`), and its final report is its last message;
  - its **live activity line** while it works (`SubagentActivityLine`): the chat line's look and glyphs with its card's words (a subagent thinks as `Thinking…`, D21 ruling; the time since it started; no token count, the ticks are the main agent's);
  - **no composer**: in its place the note `Subagents take no messages · reply in the main chat` (`subagent-note`; the second part links back); no 📎.
  - An unknown agent id, or one without a chat: `This subagent has no chat here` with the back link.
- **The way back:** the bar's link, the note's link, **Esc** and the browser's **Back** return to the main chat. The link and Esc go one step back in the browser's history when the subagent chat was opened from the main chat inside the app (the router keeps `history.state.from`), so Back and Forward stay in step; otherwise (a pasted address) they navigate to the main chat. Esc is read in the window's capture phase and only counts when no modal, dialog or popover is open (`role="dialog"` / `"alertdialog"`, `aria-modal`: Esc closes that instead), focus is not in a text field, no modifier is held and no IME composes (`escGoesBack`).
- **The main chat's place:** the main chat remembers its scroll position (and whether it follows new items) per session in memory for the page's life (`rememberMainChat` on every scroll), and restores it when it comes back, so returning from a subagent's chat shows it where it was left; a fresh page starts at the bottom as before. The chat tab keeps the loaded events while switching between the two, so nothing is fetched again.
- **Live:** the subagent chat follows the same `/hub` `event` stream and the session detail's reloads (its status, its activity).

## Cut messages (Fix · long messages)
A message is stored whole (`docs/derivations.md` → *What is clipped*), so a long reply shows whole. Text that is still cut gets a muted note under its bubble (`CutNote` in `FullText.tsx`, `full-text.ts`, `session.css` `sb-chat-cut*`):
- **"Message cut at 4,000 characters · Show full message"** under an agent bubble or a subagent's prompt stored before the fix (no flag, exactly 4,000 characters), or one past the 1,000,000-character cap ("Message cut at 1,000,000 characters"); under a subagent's brief when it came from the Agent call's cut input;
- **"Output truncated at 4,000 characters · Show full output"** under a subagent's **Result** (its Agent call's `tool_result`, which the database keeps cut).
The button fetches `GET /api/sessions/{id}/events/{eventId}/full` (`useFullText`): while it loads the note reads "Loading the full text…"; the answer's event stands in for the cut one (`withRestored`), so the bubble shows the whole text and the note goes. Message text is written back on the service, so a reload (and the other tabs, by `/hub`) shows it whole; a tool output is shown for the page's life only. When it cannot be restored the note keeps its button and says why, e.g. "The session's CLI transcript is gone: the full text cannot be restored." It works for live, attached, moved and hooked sessions and their subagents, and for a peer's sessions (the route is on the peer API). A Workflow agent's chat is read whole from its files, so it has no note.

## Switching CLIs (D62)
A session switched to another CLI shows a divider in the chat at that point (the lifecycle event `switched`): "Switched from Claude Code to Codex CLI · handover by Claude Code (outgoing agent)" or "… · handover by Codex CLI from the history". The handover request and the incoming agent's first message are Switchboard's bubbles (origin `service`). While a switch runs the header says what it does and the composer's messages are refused (409 `switching`). `docs/providers.md` → *Switching CLIs*.
