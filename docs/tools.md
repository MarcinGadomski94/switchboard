# Embedded tools (M8.1)

SPEC → Tools: local web apps shown under TOOLS in the sidebar and opened in the main area in an iframe. Switchboard stores their URLs (gap #13: "saved in Switchboard", not in the browser) and checks that they answer.

## Data
- Table `tools` (`docs/database.md`). A fresh database gets two rows from `src/server/db/migrations/0002_default_tools.sql`: **Codebase Memory** (`cm`, `http://localhost:13000`, "code graph for your indexed solutions") and **Acme Tool** (`sw`, no URL, "AI chat connected to other tools"). The migration runs once per database, so a tool the developer removes or edits later stays that way (gap #14).
- Wire type `Tool` = `{ id, name, url, description, showInSidebar, frameUrl }` (`src/core/api.ts`); `url: null` = not configured. `frameUrl` (D15, additive) is the tool's framing proxy (below), `null` when the tool has no URL, is a signed-in site (D28, below) or no proxy runs for it (demo mode); a `PUT` body's `frameUrl` is ignored.

## API (`src/server/api/tools.ts`)
| Route | Behavior |
|---|---|
| `GET /api/tools` | `Tool[]` in display order. D15: `frameUrl` names the proxy on the host name the page used (`127.0.0.1` or `localhost`), so the frame stays same-site with the page. |
| `PUT /api/tools` | Replaces the whole list (add, edit, remove, reorder; gap #14), one transaction, `position` = list index. Each item: `name` 1–80 chars (required), `url` blank/`null` = not configured, else an absolute `http:`/`https:` URL without credentials, `description` (blank → `null`), `showInSidebar` (default `true`), `id` (`[A-Za-z0-9_-]{1,64}`, generated for a new tool, unique). Anything else → `422 {error:"invalid", errors:[{field, message}]}` with fields like `[1].url`; nothing changes. Returns the stored list. Settings → Embedded tools (M8.2, `docs/settings.md`) edits, adds and removes tools through it. D15: before it answers, the framing proxies follow the new list (a new URL gets a proxy, a changed URL restarts its proxy on a new port, a cleared or removed tool loses it), so the answer's `frameUrl`s are live. |
| `POST /api/tools/{id}/probe` | `{ state: "up" \| "down" }`, plus `framing: "refused"` (D15, additive) only when the tool is up, its answer keeps the page from framing it (below) and no framing proxy runs for it. `404 not-found` for an unknown id, `409 not-configured` for a tool without a URL; neither fetches anything. |
| `GET /api/frame-helper/check` | Additive (D28, below): a tiny HTML page answered with `X-Frame-Options: DENY` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (`cache-control: no-store`; its `<html>` carries `data-sb-frame-check="ok"`). Behind the cookie guard like every `/api` route. The Tool view frames it to learn whether the frame helper removes those headers in this browser. |
| `GET /api/codebase-memory?folder=` | Additive (not in the contract): `{ projects: CodebaseMemoryProject[], indexed: {projects, mode} \| null }` for the Codebase Memory strip. D14: one folder at a time (`folder` as for `GET /api/solutions`, the default when omitted, `docs/folders.md`); a repo folder has no workspace dirty list, so its list is empty; `409 no-folder` / `404 not-found`. |
| `POST /api/codebase-memory/reindex?folder=` | Additive: starts the reindex session (below) in that folder → `201` Session; `409 nothing-to-reindex` when the list is empty (always for a repo folder); `409 no-folder` / `404 not-found`; `409 folder-missing` / `503 closing` from the supervisor. |

## The probe (`src/server/tools/probe.ts`)
The service, not the page, probes: one `GET` of the saved URL with a **3 s** timeout (`AbortSignal.timeout`), redirects not followed. **Any** HTTP response counts as `up` (like the prototype's `fetch(url, {mode:'no-cors'})`, which resolves on every status); a refused connection, DNS/TLS failure or no response in time is `down`. The body is never read. Only saved URLs are probed (the route looks the URL up by tool id), so the endpoint cannot be pointed at arbitrary hosts. The provider is `providers.toolProbe` (`src/server/providers.ts`); without one the route uses the real one. Demo mode answers `down` for every tool and never touches the network (the prototype's screenshots show Codebase Memory unreachable).

D15: the probe keeps the answer's `X-Frame-Options` and `Content-Security-Policy` headers (`ToolProbeReport.framing`), and the route decides with `refusesFraming` (`src/server/tools/framing.ts`) whether they keep the page's origin (`http://<host name of the request>:<Switchboard port>`) from framing the tool, the way a browser does: an enforced CSP policy with `frame-ancestors` decides alone (`'none'`, `'self'`, or no source matching the page → refused); otherwise `X-Frame-Options` `DENY` / `SAMEORIGIN` (or conflicting values that include one of `DENY` / `SAMEORIGIN` / `ALLOWALL`) refuse. The refusal is reported only while no proxy runs for the tool, because the proxy removes it.

## Framing proxy (D15)
Some tools refuse to be framed: the Codebase Memory UI at `http://localhost:13000` answers `Content-Security-Policy: default-src 'self'; …; frame-ancestors 'none'`, so a plain iframe stays blank while the probe says `up`. Switchboard therefore serves each tool through its own reverse proxy and the iframe loads `Tool.frameUrl`.

- **One proxy per tool with a local URL** (`src/server/tools/proxy.ts`, `startToolProxy`; D28: a signed-in site gets none, below), on **127.0.0.1 with an OS-assigned port**. `ToolProxies` (`src/server/tools/proxies.ts`, `providers.toolFrames`) owns them: main.ts syncs it with the saved tools **before the service listens**, `PUT /api/tools` syncs it again (unchanged URL = same proxy and port; changed URL = restarted on a new port; no URL or removed = stopped), and it is **closed on shutdown** (every socket, WebSockets and upstream keep-alive ones included). Syncs run one at a time. A proxy that cannot start is logged (`switchboard tool proxy (<id>)`) and its tool keeps `frameUrl: null`. **Demo mode runs none** (its tools stay unreachable, as the prototype shows).
- `frameUrl` = `http://<127.0.0.1 or localhost, as the page>:<proxy port>` + the tool URL's path, query and hash. The port changes with each start, so a tool's origin in the frame (and its `localStorage` there) does too; its cookies do not (cookies ignore ports).
- **Forwarded unchanged:** method, path, query, body and headers, streamed both ways, and WebSocket (any HTTP `Upgrade`) handshakes with both sockets piped together. Only to the configured tool URL's host and port, never anywhere else; redirects are passed on, never followed.
- **The exceptions (only these):**
  - requests: `Host` = the tool's host; Switchboard's `sb_token` removed from `Cookie` (other cookies kept; no `Cookie` header when nothing is left); hop-by-hop headers (`Connection`, `Keep-Alive`, `Transfer-Encoding`, `TE`, `Trailer`, `Upgrade` outside an upgrade, `Proxy-Connection` and the headers `Connection` names) are the proxy's own, as HTTP requires;
  - answers: `X-Frame-Options` dropped; every `Content-Security-Policy` header, and each policy in it (`,`-separated), gets `frame-ancestors http://127.0.0.1:<Switchboard port> http://localhost:<Switchboard port>` in place of its own (appended when it had none), every other directive verbatim; an answer **without** a CSP gets one with only that `frame-ancestors`, so no other site can frame the tool through the proxy; `Content-Security-Policy-Report-Only` is left alone (it blocks nothing); a `Location` pointing at the tool's origin (absolute or scheme-relative) points at the proxy (same host name as the request), other `Location`s stay; hop-by-hop headers as above.
- **Refused:** a `Host` other than `127.0.0.1:<proxy port>` / `localhost:<proxy port>` (the service's own rule, `isAllowedHost`) → **403** `forbidden host`, also for upgrades (DNS rebinding); a request target that is not a path (absolute-form, `*`) → **400**; `CONNECT` connections are closed. The tool sees none of them.
- **Upstream failure** (refused, reset, DNS, TLS) → **502** `text/plain` "Switchboard's tool proxy could not reach <host> (<code>)"; once the answer has started, the connection is cut instead. When the browser goes away, the upstream request is cancelled.
- `https:` tool URLs are proxied with normal certificate checks (a self-signed tool certificate is a 502); the frame itself is plain `http:` on loopback.
- Security notes: `docs/security.md` → *Tool framing proxies (D15)*.

## The UI
- **Probe state** (`src/web/tools/probe.ts`), shared by the sidebar and the tool view, as the prototype's `tstate`: `idle` (not probed yet), `checking`, `up`, `down`, `unset` (probed without a URL, i.e. its view was opened). Dot colors: up = status done, down = status fail, checking = status need, idle `#8d8c87`, unset `#5a5955`. Toolbar text: connected / offline / checking… / (none) / not configured. States last for the page's lifetime, keyed by id + URL.
- **Sidebar TOOLS rows**: every configured tool is probed once per page load (the prototype probes its tools on mount); the row shows the dot, the name and the host (`urlHost`: the URL without `http(s)://`) or "set URL".
- **Tool view** (`src/web/views/ToolView.tsx`, `views/tool.css`): opening it probes the tool. Toolbar = dot, name, description, URL field (URL or "no URL set" + state text), **↻ Reload** (new iframe + probe), **↗ New tab** (`<a target="_blank" rel="noopener">` to the tool's own URL, never the proxy; no `href` without a URL), **Edit** (→ `/settings/tools`). The iframe fills the area while the tool has a URL and is not `down`; D15: it loads `frameUrl` (the framing proxy), the tool's own URL only when no proxy runs, and keeps the sandbox (`TOOL_FRAME_SANDBOX`, no `allow-top-navigation`). Overlays:
  - no URL: "{name} isn't configured" · "Add the URL where {name} runs on this PC. It is saved in Switchboard." (gap #13) · **Set URL in Settings** → `/settings/tools`;
  - `down`: "{host} is not reachable" · "Start {name} on this PC and retry. If it runs but refuses to load in a frame (X-Frame-Options / frame-ancestors), use New tab." · **Retry** (new iframe + probe).
  - D15 fallback, only when the probe answered `framing: "refused"` (up, refusing to be framed, no proxy running): "{host} refuses to load in a frame" · "{name} runs but refuses to load in a frame (X-Frame-Options / frame-ancestors), use New tab." · **↗ New tab** (a link to the tool's own URL, new tab, `noopener`), and no iframe. The flag is kept per tool id + URL next to the probe state (`toolFramingRefused` in `src/web/tools/probe.ts`).
  - An id that is not in the list: "Unknown tool" + Open Settings.
- **Codebase Memory strip** (`views/tool/CodebaseMemoryStrip.tsx`, only for the tool with id `cm`): D14: first the folder switcher (`cm-folder`, `docs/folders.md` → *UI*: the default folder, the other saved folders, the folders sessions use; `?folder=` in the URL; shown only with two folders or more), then `.codebase-memory-dirty` of that folder (a repo folder: nothing listed), one chip per listed project (dot, repo name, the time when known; the path as tooltip), the indexed note when known, and **Reindex n now** (for the folder shown). After a successful start the button becomes "✓ Reindex started", a link to the session. The list is read again on every `sessionUpdated` (the reindex session removes lines as it goes). With nothing listed the strip says "nothing to reindex" and has no button.

## `.codebase-memory-dirty` (`src/server/tools/codebase-memory.ts`)
The workspace's PostToolUse hook (`.claude/hooks/cm-mark-dirty.js` in the workspace, read-only to Switchboard) writes `<workspace folder>/.claude/.codebase-memory-dirty`: one codebase-memory **project id** per line, sorted, no times. A project id is the repo's absolute path with backslashes as `/`, trailing slashes dropped, every run of `:` `/` `\` replaced by one `-`, leading/trailing `-` trimmed (`/Users/me/ws/nugets/auth-nuget` → `Users-me-ws-nugets-auth-nuget`). Switchboard reads the file of the folder asked for asynchronously (missing file, or a repo folder (D14) = nothing listed) and names each line:
- an id that starts (case-insensitively) with the id of the workspace folder — as saved or as its real path, since the hook sees the path Claude Code runs in — followed by `-<category>-<repo>` with a router category (`microfrontends`, `microservices`, `functions`, `nugets`, `mobile`, `other`, `infrastructure`) is that repo: name = the repo folder (`mobile` for any `…-mobile-<folder>`, like its Solutions row), path = the folder the id encodes, `<root>/<category>/<folder>` (the indexed project: `mobile/acme-app-mobile` for the nested mobile clone). The lines are parsed with M6.4's rules (`dirtyProject` in `src/core/codebase-memory.ts`), the same the Solutions view uses;
- anything else keeps the id as its name, with no path.
Blank lines and duplicates are dropped. `markedAt` is `null` (the file keeps no times) and `indexed` is `null` (only codebase-memory itself knows its project count, and gap #4 rules out calling it from the service). Demo mode feeds the prototype's list with its times and "16 projects indexed · full mode". M6.4 reads the same file for the Solutions view; the lane merge keeps one reader.

## Reindex (gap #4)
`POST /api/codebase-memory/reindex?folder=` re-reads that folder's list and starts a background session through the SessionSupervisor (real `claude`, baseline argv, cwd = the workspace folder's root, the session's folder = that folder, D14), named `reindex-codebase-memory` (then `-2`, `-3`, … while taken), with no work type, mode or phase (`SessionStartInput`, `docs/database.md`), no solutions and no worktrees. Its first stdin message is the built-in prompt (`reindexPrompt`): re-index each listed project through the codebase-memory MCP tool `index_repository` in `full` mode, one at a time; remove the project's line from the dirty file once it succeeded (delete the file when empty); never run the codebase-memory binary directly; change nothing else; leave a line in place and say why when a project fails. Switchboard itself never runs the binary and never writes the file. Like any session, questions it asks reach the Inbox.

### Origin and Referer (D15 amendment, 2026-09-28)
The real Codebase Memory UI (v0.11.0) answers 403 to any request whose `Origin` is not its own, and the browser sends `Origin` on module scripts and fetches. Seen through the proxy, the tool's own page names the proxy's origin, so the proxy rewrites an `Origin` / `Referer` that names the proxy itself to the tool's origin (`rewriteOriginHeader` in `src/server/tools/proxy.ts`). Any other value (another site, `null`) passes unchanged, so the tool's own checks still see a foreign caller. Checked against the real tool: the UI renders inside the app (38 projects, the graph stats) with no failing request.

### Stable proxy port (developer ruling 2026-09-28)
Each tool keeps the proxy port it got the first time, remembered in the settings table (`tools.proxyPort.<id>`, `settingsProxyPorts` in `src/server/tools/proxies.ts`). A restart or a URL change starts the proxy on that port again, so the tool's origin inside the frame, and whatever it stores there (localStorage), survives. Only when the port is taken does the proxy take a new OS-assigned one, which is then remembered.

### Sidebar rows (D29, developer ruling 2026-09-28)
A TOOLS row shows the tool's name in full on its first line; a URL that does not fit beside it moves to its own line (right-aligned) and is cut with … (`.sb-tool` wraps, `.sb-tool-host` ellipsis), the whole URL as its tooltip. The sidebar never scrolls sideways. Oracle: `tests/e2e/tools.spec.ts` (a long URL), `tests/e2e/visual/tools.spec.ts` (`sidebarRuling`).

## Signed-in sites (D28)
The D15 proxy cannot frame a site the developer is signed in to, such as Jira at `https://acme.atlassian.net/…`: through the proxy the page is `http://127.0.0.1:<port>`, the site's login cookies never reach it, and it bounces to a login page that refuses every frame. Such tools are framed **directly** with the help of the **Switchboard frame helper**, a browser extension in this repo (`tools/frame-helper/`, Chrome and Safari). Details, install steps, the security scope and troubleshooting: `docs/frame-helper.md`.

- **Site tool** = a tool whose URL is a non-loopback `https:` URL (`isSiteToolUrl` in `src/core/site-tools.ts`; loopback = `localhost` and its subdomains, `127.0.0.0/8`, `0.0.0.0`, `::1`, IPv4-mapped loopback). Everything else keeps the D15 proxy.
- **Service:** `ToolProxies` starts no proxy for a site, so its `frameUrl` is `null`; a proxied tool whose URL becomes a site loses its proxy. The probe is unchanged (a site like Jira reports `framing: "refused"`; the Tool view ignores it for sites). `GET /api/frame-helper/check` is the capability-check page (above). D35: `GET /api/frame-helper`, `POST /api/frame-helper/reveal` and `/open-extensions` serve the guided setup (`src/server/api/frame-helper.ts`; `docs/frame-helper.md` → *Guided setup (D35)*).
- **Scope (developer ruling 2026-09-28):** the helper removes the frame headers only for the hosts of the saved site tools, and only in the tab that runs Switchboard. The page gives it those hosts: whenever the tools list loads or changes (the sidebar's list, reloaded on `useToolsChanged`, and the Tool view's own fetch), `useFrameHelperSites` (`src/web/tools/useFrameHelper.ts`) posts `{ source: 'switchboard', type: 'frame-helper:sites', id, hosts }` to its own window. `hosts` = `frameHelperHosts` (`src/core/site-tools.ts`): Switchboard's own host first (the capability check page is on it), then each site tool's hostname, deduplicated, plain host names only, at most 50. The helper's content script relays it to its service worker, which replaces that tab's session rule (`tabIds` + `requestDomains`) and answers `{ source: 'switchboard-frame-helper', type: 'frame-helper:sites-applied', id, ok, hosts, error }`. The page waits up to 2 s for the answer to its latest list. Details: `docs/frame-helper.md` → *What it does*, *Security scope*.
- **Tool view** of a site: it waits up to 1.5 s for the helper's marker (`<html data-sb-frame-helper="<version>">`, set by the extension at `document_start`), keeps watching after, and with the marker, once the helper answered the page's host list, frames `GET /api/frame-helper/check` once, hidden. States (`data-frame-helper` on the view; `siteFrameStatus` in `src/web/tools/frame-helper.ts`):
  - `checking`: the frame area stays empty (also while the page's latest host list waits for the helper's answer);
  - `ready` (the check page showed, so the helper removes frame headers here, and the helper confirmed this site's host for the tab): the iframe loads the tool's **own URL** (`data-frame-mode="site"`), sandboxed as every tool plus `allow-storage-access-by-user-activation` (Safari's Storage Access prompt needs it);
  - `absent`: "{host} needs the Switchboard frame helper to open here" · "Install it once in Chrome: docs/frame-helper.md (Safari can’t frame signed-in sites: open it in a new tab)" · **Open in new tab** (the tool's URL, new tab, `noopener`) and, D35, an outlined **Set up frame helper** that opens the guided setup inside the card (`docs/frame-helper.md` → *Guided setup (D35)*);
  - `blocked` (marker, but the check page was refused: Safari today, or a Chrome helper without site access; or the helper answered without this site's host): "{host} can't open in a frame in this browser" · the reason and the docs · **Open in new tab**.
  A helper that never answers a host list (the first build, 1.0.0) is trusted on its capability check alone.
  `{host}` is the URL's host (with its port, if any). No URL and `down` keep their overlays and come first. The overlays reuse the D15 fallback's card, classes and tokens. Local tools are unchanged (`data-frame-mode="proxy"`, or `plain` without a proxy).
