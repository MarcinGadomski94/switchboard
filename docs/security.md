# Service security (M1.1)

Switchboard is a local service with the power to start `claude` processes and run git in the developer's repos, so any web page the developer visits must be unable to use it. The rules come from `docs/handoff/ARCHITECTURE.md` → *Security* and `docs/decisions.md` gap #20. Code: `src/server/security.ts`, `src/server/listen.ts`, `src/server/web.ts`, `src/server/token.ts`.

## Bind address
- The UI service listens on **127.0.0.1 only**. There is no host setting. (D48 adds one more, separate socket: the optional peer listener, bound only to the Tailscale address; *Peer listener (D48)* below. D73 adds the optional device listener, also on **127.0.0.1**, published to the tailnet by `tailscale serve`; *Device listener (D73)* below.) `listenLoopback` refuses any other address (`0.0.0.0`, `::`, a LAN address, `localhost` (which can also bind `::1`), `::1`, other `127.x`) before a socket is opened, then checks the address the socket actually bound and closes the server if it is not 127.0.0.1.
- Port: `SWITCHBOARD_PORT`, default 13001. Tests use 127.0.0.1:4871–4879 only.

## Request guard (every request, the UI page included)
Installed as the first `onRequest` hook, so it also covers 404s and every route added later.

1. **Host** must be `127.0.0.1:<port>` or `localhost:<port>` (host name case-insensitive, port exact). Otherwise **403** `{"error":"forbidden-host"}`. This stops DNS rebinding: a hostile domain that resolves to 127.0.0.1 still sends its own name as Host.
2. **Origin**, when the browser sends one, must be exactly `http://127.0.0.1:<port>` or `http://localhost:<port>`. Otherwise **403** `{"error":"forbidden-origin"}`. `null` origins count as foreign. **Other loopback ports are foreign too.** SameSite does not look at ports, so a page from another local app (for example `http://127.0.0.1:13000`) is "same-site" and its browser requests would carry the cookie. Only the Origin check stops those.
3. **Cookie.** Every route needs a matching `sb_token` cookie, **401** `{"error":"unauthorized"}` otherwise. This is default-deny: unknown paths get 401 before 404. The only exceptions are routes marked `config: { public: true }`, which are just the UI page, its static files and D34's installable-app files in `web.ts` (below), and even a route marked public is protected when its path is `/api`, `/api/…`, `/hub` or `/hub/…`. API route modules registered through `src/server/routes.ts` must never set `public`.
   - Tokens are compared in constant time. Any `sb_token` value in the Cookie header may match, so a stray cookie with the same name planted by another loopback app (cookies are not isolated by port) cannot lock the UI out.

## The token and the cookie
- **Token:** 32 random bytes, base64url, created on first start at `<dataDir>/sb_token` (file 0600, folder 0700). It stays the same across restarts. An empty or corrupt file is replaced. `dataDir` = `SWITCHBOARD_DATA_DIR` or the per-user app-data folder (gap #18).
- **Issuing (gap #20):** a GET of the UI page (`/`, `/index.html` or any client-side route: a path under neither `/api` nor `/hub` whose last segment has no file extension) returns `index.html` with
  `Set-Cookie: sb_token=<token>; Path=/; HttpOnly; SameSite=Strict`
  only when the request passed the Host/Origin guard **and** has `Sec-Fetch-Site: none` (typed URL, bookmark, reload) or `same-origin`. `cross-site`, `same-site`, a missing header or any other value gets the page without the cookie. So a browser that sends no Fetch Metadata cannot use the UI (every current browser sends it).
- It is a session cookie with no `Max-Age`, `Expires`, `Domain` or `Secure` (plain http on loopback). Each qualifying page load sets it again.
- The page response is `Cache-Control: no-store`. Static files (`/assets/*`) never set the cookie. `@fastify/static` serves them from `dist/web` and refuses paths outside it.
- **One origin (D34 ruling, 2026-09-28):** a page load whose Host is `localhost:<port>` (accepted by the guard) is answered `302` to `http://127.0.0.1:<port><same path and query>` with no cookie, so the installed app and the cookie live on one origin. API and `/hub` requests are never redirected.
- When `dist/web/index.html` does not exist (`npm run build` not run yet), the same route serves a short placeholder page, with the same cookie rules.

## Installable-app files (D34)
Switchboard can be installed from the browser as an app (`docs/install-app.md`). The files that make that work are public, like the page shell, and have routes of their own in `web.ts` (`APP_FILES`, `APP_ICONS_PREFIX`):

| Path | Type | Why public |
|---|---|---|
| `/manifest.webmanifest` | `application/manifest+json` | browsers fetch a manifest without credentials (`crossorigin` absent = no cookies) |
| `/sw.js` | `text/javascript` | the service worker script; registration and update checks must not depend on the cookie |
| `/offline.html` | `text/html` | the worker caches it at install; it is shown only when the service is down |
| `/icons/*` | `image/png`, `image/svg+xml` | the app icons, the `apple-touch-icon` and the favicons, fetched by the browser and the OS |

- They hold nothing sensitive (static files from the build: no token, no data, no paths), never set the cookie, and are sent with `Cache-Control: no-cache` (the icons: `public, max-age=0`), so a new build reaches an installed app on its next load.
- The **Host/Origin guard still applies** to them (403 `forbidden-host` / `forbidden-origin`), exactly as for the page. A manifest fetch is a CORS request, so it carries Switchboard's own `Origin`, which passes.
- Everything else is unchanged: `/api` and `/hub` still need the cookie; the installed app is the same origin (`http://127.0.0.1:<port>`), so it gets the cookie from its page load like a tab does.
- **The service worker and the cookie rule (gap #20):** the worker answers only navigations and fetches them through **navigation preload**, so the page request the service sees is the browser's own, with its original `Sec-Fetch-Site` (`none` for a typed URL or the app launch, `cross-site` for a link from another site). A cross-site navigation therefore still gets the page without a cookie. It never answers `/api`, `/hub` or asset requests (they go straight to the network) and caches nothing but the offline page. Checked in `tests/e2e/install-app.spec.ts`.

## Why a framed or cross-site Switchboard page cannot act
A cross-site iframe or link that loads the UI gets `Sec-Fetch-Site: cross-site`, so no cookie is set. A cookie that already exists is `SameSite=Strict`, so the browser does not send it on cross-site requests. A same-site page on another loopback port fails the Origin check.

## Tool framing proxies (D15)
Embedded tools are framed through one reverse proxy per tool (`src/server/tools/proxy.ts`, details in `docs/tools.md` → *Framing proxy*). Each is a second listening socket, so it follows the same rules as the service, adapted to what it is:
- **Loopback only**, 127.0.0.1 with an OS-assigned port; the bound address is checked after `listen` like `listenLoopback` does.
- **Host guard:** the same `isAllowedHost` rule with the proxy's port (`127.0.0.1:<port>` / `localhost:<port>`), else 403 before anything is forwarded (HTTP and WebSocket upgrades). A rebinding domain cannot reach the tool through it.
- **One upstream:** it connects only to the saved tool URL's host and port (the same saved URLs the probe may fetch). Only a path is accepted as request target (no absolute-form proxy requests, no `CONNECT`), and redirects are passed to the browser, never followed.
- **The token never leaves:** browsers send cookies to every port of a host, so the frame's requests carry `sb_token`. The proxy removes every `sb_token` pair from `Cookie` before forwarding; the tool's own cookies pass.
- **A different origin, on purpose:** the tool runs at `http://127.0.0.1:<proxy port>`, not at Switchboard's origin, so it cannot use Switchboard's API: its API calls carry its own `Origin` and fail the Origin check (403). Its no-cors GETs are same-site and may carry the cookie, as for any other local app today, but their answers are opaque and every state-changing route needs an allowed `Origin`. The proxy itself has no cookie check: it grants nothing the tool's own port does not already offer on this machine.
- **Clickjacking:** `X-Frame-Options` is dropped and `frame-ancestors` is set to Switchboard's two origins in every CSP, **added** when the tool sends none, so only a Switchboard page can frame the tool through the proxy. The iframe keeps its sandbox (no `allow-top-navigation`).
- The proxies start with the service and stop with it; demo mode runs none.

## Frame helper extension (D28)
The optional browser extension `tools/frame-helper/` removes `X-Frame-Options` and `Content-Security-Policy` from `sub_frame` responses so Switchboard can frame signed-in sites (Jira) directly. Developer ruling 2026-09-28 (narrowed scope): only for the hosts Switchboard's page gives it (its own host, for the capability check, plus the saved site tools' hosts; plain host names, at most 50) and only in that page's tab, as tab-scoped `declarativeNetRequest` session rules kept by the extension's service worker. Only the extension's content script in the top frame of a `127.0.0.1` / `localhost` page may set a tab's hosts; a tab's rule goes when it closes, leaves loopback pages or loads a new loopback document. It is outside the service: the service only stops proxying such sites and serves `GET /api/frame-helper/check` (a page that refuses every frame, behind the cookie guard). What remains open (another loopback page can name hosts for its own tab; the framed document loses its whole CSP; in Switchboard's tab frames from Switchboard's own host, the local tools' proxies included, lose their headers too) and why that is accepted: `docs/frame-helper.md` → *Security scope*.

## Frame-helper setup openers (D35)
The guided frame-helper setup (`docs/frame-helper.md` → *Guided setup (D35)*) lets a page ask the service to run two OS commands: `POST /api/frame-helper/reveal` (the OS file manager on `tools/frame-helper`: `open -R`, `explorer /select,`, `xdg-open`) and `POST /api/frame-helper/open-extensions` (Chrome on `chrome://extensions`: `open -a "Google Chrome"`, `chrome.exe` from the usual install paths or `cmd /c start`, `google-chrome` / `chromium`). `GET /api/frame-helper` answers the folder's path and the manifest version.
- **Behind the guard:** all three are ordinary `/api` routes: loopback Host, the service's own Origin (a POST from another site or another loopback port is 403), and the `sb_token` cookie (401 without it). The cookie is `SameSite=Strict`, so a cross-site page cannot make the browser send them.
- **Fixed arguments only:** every argv is built by the service from its own checkout path and the constant `chrome://extensions`. Nothing in the request (body, query, headers) reaches a command, and the page cannot name a URL, a file or a program. Spawned with `shell: false`, detached, stdin and stdout ignored; at worst a page with the token opens Finder on that folder or Chrome's extensions page again.
- **What leaves the service:** the folder's absolute path (which reveals the user name and where the checkout lives) goes to the page that holds the token, the same page that already sees the saved folders' paths.
- **Tests never open a real app:** without an opener provider (a test app built bare) both POSTs answer 501; every test server runs them through `tools/fake-opener` (`SWITCHBOARD_OPEN_COMMAND`, a default of `testServerDefaults()`).

## Peer listener (D48)
Switchboard machines pair with each other over Tailscale (`docs/peers.md`). The developer approved amending the loopback-only rule (AGENTS.md): **the UI binds loopback only; the optional peer listener binds only the Tailscale address, with per-peer tokens.**
- **Off by default**, switched in Settings → Machines. It binds only the address `tailscale ip -4` reports, or a typed one, and only if that is a Tailscale IPv4 (**100.64.0.0/10**): `assertPeerBind` refuses `0.0.0.0`, `::`, LAN addresses, names, IPv6 and loopback before a socket opens, and the bound address is checked afterwards like `listenLoopback` does. Nothing is served on any other interface. (Tests alone may bind 127.0.0.1, with `SWITCHBOARD_PEER_TEST_LOOPBACK=1`.)
- **Only the peer API.** The listener is its own Fastify app: no page, no static files, no `/api` or `/hub` of the UI. It serves `/peer/v1/*` only; unknown paths are 401 before 404.
- **Guard:** `Host` must be exactly `<bound address>:<port>` (403 `forbidden-host`); any `Origin` is refused (403 `forbidden-origin`: a browser page never talks to it, so a web page on the tailnet or a rebinding domain cannot use it); every route but the pairing exchange needs `Authorization: Bearer <per-pair token>` (401 `unauthorized`). The UI cookie is not accepted. Bodies are limited to 1 MiB (D57: the two attachment uploads take the attachments' limit, about 27 MiB of JSON for a 20 MiB file).
- **Per-pair tokens:** 32 random bytes (base64url), one per direction per pair, made at pairing. The side that checks a token stores only its **sha256**, compared in **constant time**; the side that presents it stores it as is (it must send it) in the database under the user's 0700 data folder. Tokens never appear in logs, errors or API answers. Pairing again replaces them; Remove revokes them at once (and tells the other machine to forget its side).
- **Pairing codes:** made only by a click on this machine ("Allow a new peer"), **single use**, **10 minutes**, burned after **5 wrong tries**, 40 bits, in memory only.
- **What a peer can do:** exactly the allow-list in `src/server/peers/service.ts` (`PEER_API_ALLOW`, `docs/peers.md` → *The peer API*): the sessions' routes (read, message, answer, pause/resume, model, close/reopen, Remote Control), the Inbox and its answers, starting a session (with the folders, models, solutions and branching preflight it needs), and the terminal-session hooks. **No** settings, no folder management, no schedules, no tools or their proxies, no terminal handoff (attach / detach), no teleport, no history, no `/hub`. Allowed calls are run as local requests through the app's own routes (`app.inject`), so every route's own checks apply; they are marked so that they answer this machine's data only and are never forwarded on to a further machine (no chains; a remote id in a peer's path is refused).
- **Answers go only to the paired machine over the tailnet**; Tailscale encrypts the traffic (WireGuard). The peer API itself is plain HTTP on the tailnet address.

## Device listener (D73)
Paired phones and tablets reach Switchboard over Tailscale (`docs/devices.md`). Developer ruling 2026-10-08 amended the loopback rule (AGENTS.md): **the UI listener keeps its loopback trust unchanged; the optional device listener also binds 127.0.0.1 and is published to the tailnet only through `tailscale serve` (HTTPS), with per-device credentials.**

**Threat model.** Who can reach the device listener: (1) anyone on the tailnet allowed by its ACLs to reach this machine's HTTPS port, through `tailscaled`; (2) any local process or user on this machine (it is a loopback port); (3) a web page in a browser on the tailnet or on this machine (cross-site requests, DNS rebinding). Not reachable: the LAN, the internet (nothing binds anything but 127.0.0.1; `tailscale serve` is not Funnel). What they could want: drive sessions (run code in the developer's repos), read chats, approve permission requests, administer the machine.

- **Off by default** (Settings → Devices). On: the listener binds 127.0.0.1 only (`assertLoopbackBind`, the bound address checked), and `tailscale serve --bg --https=<port>` (default 8443) proxies to it with a real `*.ts.net` certificate. Switchboard only ever turns off the serve entry it made.
- **Loopback proves nothing here.** Every request arrives from 127.0.0.1, so the device listener never applies the UI's rules: its requests are marked by the listener itself (a `Symbol` on the raw request, never a header) and judged only by `DeviceService.guard`. The install token (`sb_token`) is not accepted there and never issued there; the UI page served to a device sets no `sb_token` cookie.
- **Guard** (first `onRequest` hook, every route and 404):
  1. `Host` must be the devices' origin (`<machine>.<tailnet>.ts.net:<port>`; `tailscale serve` keeps the browser's Host). A proxy that rewrote Host to `127.0.0.1:<device port>` is accepted only with `X-Forwarded-Host` naming the origin. Anything else → 403 `forbidden-host` (DNS rebinding: a rebinding domain sends its own name).
  2. `/hook/*` and `/agent/*` → 403 (those doors exist on the UI listener only).
  3. `Origin`, when present, must be exactly the devices' origin → else 403 `forbidden-origin`.
  4. **Device credential:** the `__Host-sb_device=<id>.<secret>` cookie (32 random bytes, `HttpOnly; Secure; SameSite=Strict; Path=/`, host-only, 400 days, refreshed on page loads); sha256 of the secret stored, compared in constant time; the `Tailscale-User-Login` recorded at pairing must match when one was recorded. Without a valid credential only the pairing page, the pairing exchange and the installable-app files are served; page loads are redirected to `/pair`, everything else is 401.
  5. **Allow-list** → 403 `local-only` for a device unless the `/api` route is on `DEVICE_ALLOWED` (`docs/devices.md` → *What a device may do*): the work (sessions, Inbox, todos, schedules, history, the UI's reads and preferences, its own push settings) is allowed; machine administration (devices, machines, hooks, MCP edits, updates, Start at login, CLIs, accounts, tools, the frame helper, folders and setup, take-over, test hooks) is not. A route nobody classified is refused, and a test fails until it is classified. Matched on the percent-decoded path with doubled slashes collapsed (an undecodable path is refused); `/api/machines/{id}/api/<rest>` is judged as `/api/<rest>` (a proxy inside it is refused).
- **Pairing codes:** made only by a click on this machine's own UI (the route is local-only), 40 bits, **10 minutes**, **single use**, burned after **5 wrong tries**, one at a time, stored hashed. **10 attempts per 10 minutes** in total on the listener (429), since every caller looks like 127.0.0.1. The code travels in the QR link's fragment (never in a request line or a log).
- **Revoke** deletes the device and destroys its sockets on the device listener (its `/hub` stream and keep-alive connections end at once).
- **The pairing page** is a self-contained HTML form with a strict CSP (`default-src 'none'`, nonce'd script and style, `connect-src 'self'`, `frame-ancestors 'none'`), `no-store`, `nosniff`, `no-referrer`. It shows this machine's name (as Settings → Machines names it) to whoever can open it on the tailnet.
- **Web push:** endpoints only on the browser vendors' push services (https, default port, known host suffixes), so a device cannot make Switchboard send requests to arbitrary hosts; payloads are encrypted (RFC 8291) and minimal; VAPID private key in `<dataDir>/vapid.json` (0600). See `PRIVACY.md`.
- **Residual risks:** a stolen unlocked phone has the device's access until it is revoked (revoke it on the computer); the tailnet's ACLs decide who can try to pair (the rate limit and single-use codes make guessing a 40-bit code impractical); a local process can reach the loopback port too but needs a device credential like anyone else.

## Hook endpoints (D48 P4)
Hand-started terminal `claude` sessions report to Switchboard through hooks the developer installs explicitly (Settings → Machines → Install hooks; `docs/peers.md` → *Hooked terminal sessions*). Their script calls `POST /hook/v1/event | permission | waiter` on the UI's **loopback** listener (never the peer listener):
- **Guard:** the loopback Host check as for every route; then any `Origin` is refused (403 `forbidden-origin`: no page may call it) and only `Authorization: Bearer <hook token>` is accepted (401 otherwise); the `sb_token` cookie is not a credential here, and the hook token is not one for `/api`.
- **The hook token:** 32 random bytes, `<dataDir>/hook-token`, file 0600 in the 0700 data folder, made at first start, compared in constant time. The installed entries name the file, not the token. It keeps other local users and processes from injecting messages or decisions.
- **What a call can do:** report a terminal session's events, hold a permission request until the developer answers it in Switchboard, hold a waiter until the developer's message is released. It cannot decide anything or send a message itself; the terminal's own permission dialog stays open meanwhile.
- **Writing the user's Claude settings** happens only through the explicit Install / Remove action, after a timestamped backup, touching only Switchboard's own entries (`--switchboard-hook`); a file that is not a JSON object is never changed. On Windows the entries are exec form (absolute `node.exe` + args), so no shell parses them; elsewhere every path is single-quoted.
- **Never read:** credentials, the keychain, the CLI's `sessions/*.key` files, `CLAUDE_CODE_MESSAGING_TOKEN`. Switchboard reads the transcripts and the `sessions/<pid>.json` registry entry of a listed pid, and runs only the unmodified `claude` (`--version`, `agents --json`). The hook script forwards only the hook input, the CLI's pid and entrypoint.

## Updates (D55)
The updater (`docs/updates.md`) downloads code and restarts Switchboard, so it is held to these rules:
- **Where from:** only the GitHub releases of the configured repository (`RELEASE_REPO`, or `SWITCHBOARD_UPDATE_REPO`, validated as `owner/name`). The REST API is called unauthenticated; Switchboard never sends a credential of the user's (no token, no cookie; `gh`, the fallback for a private repository or a rate limit, uses its own sign-in, which Switchboard never reads). Asset downloads take only the release's `browser_download_url`, which must be exactly `https://github.com/<repo>/releases/download/<tag>/<name>`; redirects are followed by hand, at most 5, only over HTTPS to GitHub's asset hosts (`github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`, `github-releases.githubusercontent.com`), no userinfo, no other port.
- **Size limits:** tarball 200 MiB, checksum 4 KiB (listed size, `Content-Length` and a running count, also for gh's downloads); unpacked at most 512 MiB and 50 000 entries.
- **Checksum before anything else:** the `.sha256` asset must exist and name the tarball; its SHA-256 must match, else the update is refused before unpacking. (The checksum comes from the same release, so it guards against a corrupt or swapped download, not against a compromised repository; the release is trusted as far as the repository is.)
- **Extraction** with Node's own zlib and a pure tar reader: only entries under `switchboard-<v>/`; absolute paths, drive letters, `..`, backslashes, colons, NULs, Windows device names, links (symbolic and hard) and special files are refused; files are created exclusively in a fresh staging folder under the data folder; header checksums verified.
- **What runs:** nothing from the package but `npm ci --omit=dev` (with its dependencies' install scripts, as a manual install from the release does) in the staged folder, and the new server when the login service starts it. `npm`, the service manager and the restart helper are spawned as argv arrays with `shell: false`; the helper script comes from the running install, never from the download.
- **The switch** only re-registers this user's own login service (M9.1's plan and rollback); the database and the rest of the data folder are not touched; the running install's folder is kept.
- **Who can start it:** the `/api/updates*` routes are ordinary `/api` routes behind the Host / Origin / cookie guard; none is on the peer API, and `updateChanged` is not forwarded to peers. Tests never reach GitHub: every test server runs with `SWITCHBOARD_UPDATES=off`, and the test redirect `SWITCHBOARD_UPDATE_API` accepts only `http://127.0.0.1:<port>`.

## Attachments (D57)
Images and files the developer pastes, drops or picks for a message (`docs/chat.md` → *Attachments (D57)*). Code: `src/server/attachments/service.ts`, `src/server/api/attachments.ts`, `src/core/attachments.ts`.
- **What is stored where:** only in Switchboard's data folder, `<dataDir>/attachments/<session id>/<id>-<name>` (the New-session form's uploads in `<dataDir>/attachments/_staged/` until their session starts), folders 0700, files 0600, written exclusively (`wx`); never in a repo, never in the database (a row per file keeps the sanitized name, size, sniffed type and kind; the message's event lists them by id). The agent reads a non-inline file through the absolute path the message names, as it reads any file. Inline images and PDFs are also sent to the model (that is their purpose).
- **Names and paths:** the stored name is `<random UUID>-<name>`, where `name` is the upload's last path segment with separators, control characters and `:*?"<>|` replaced, leading dots removed, at most 120 characters. Session and attachment ids must be plain ids (`[A-Za-z0-9_-]`) before they name a folder or a file; a download looks the row up by id and serves only a file of that session, so `..`, encoded slashes, another session's id or a staged upload are 404.
- **Types:** decided by sniffing the bytes, never by the name or the browser's claim: PNG, JPEG, GIF and WebP by their magic bytes are images, `%PDF-` is a PDF; everything else (SVG, HTML, scripts, archives, text) is a file.
- **Serving:** `GET /api/sessions/{id}/attachments/{attachmentId}` behind the Host / Origin / cookie guard like every route. An image or PDF: its sniffed type, `Content-Disposition: inline`; anything else: `application/octet-stream` and `Content-Disposition: attachment` (SVG and HTML are never rendered by the browser); `?download` makes an image or PDF a download too. Always `X-Content-Type-Options: nosniff`; everything but a PDF (the browser's viewer needs it) also gets `Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; sandbox`. The name goes as an ASCII fallback plus RFC 5987 `filename*`. `Cache-Control: private, max-age=3600`.
- **Caps:** 20 MiB per file (413 above it; the upload route's body limit is the base64 of that plus 64 KiB), 50 MiB and 20 files per message (422), an empty file refused. Inline, the CLI's own limits apply (an image over 3.75 MB, a PDF over 20 MiB or 100 pages, and what exceeds 24 MiB of base64 in one message go as files).
- **Retention:** a session's rows go with the session; at every start files older than 30 days, folders of sessions that no longer exist and files no row owns are removed (a row is written before its file, so a fresh upload is never taken for a stray one).
- **Peers (D48):** a peer's session's uploads go through the proxy to that machine and live in its data folder; the three routes are on `PEER_API_ALLOW`; a download is passed through as bytes with the headers above. Nothing of another machine is kept here.

## MCP servers (D61)
The MCP page manages Claude Code's MCP servers (`docs/mcp.md`). Code: `src/server/mcp/`, `src/server/api/mcp.ts`, `src/core/mcp.ts`.
- **Guard:** every `/api/mcp…` route is behind the Host / Origin guard and the `sb_token` cookie; they are on `PEER_API_ALLOW` (a paired machine can manage this machine's servers, the same trust as starting a session there: a stdio server is a command Claude Code runs).
- **Secrets never reach the browser:** answers carry env and header **names** only; args and URLs are masked where they look like secrets (`••••`); the Edit form sends `keep: true` for an unchanged env / header and posts masked args / URLs back unchanged, and the service restores the stored values itself. CLI output is never passed on as is: `claude mcp get`'s output (which prints env values and headers) is read for its `Status:` / `Issue:` lines only; errors and command logs go through a scrubber that replaces every known secret value and any `Authorization:` value.
- **Writes through the CLI only:** `claude mcp add-json / remove` and the `mcp_toggle` control request change Claude Code's files; Switchboard only reads `~/.claude.json`, `.mcp.json` and the settings files. The one exposure: `add-json` takes the server's JSON (with its env / header values) as an argument, so while it runs (well under a second) the values are visible in the process list to this user's own processes (and root); the CLI has no stdin or file input for it.
- **Processes:** `spawn` with argv arrays (`shell: false`), cwd = the chosen saved folder, the supervisor's scrubbed environment. `claude mcp …` commands have a 45 s limit and 1 MiB of output; the helper (`claude -p --input-format stream-json`, no user message, so no model call) is closed after its answer (EOF, then SIGTERM / SIGKILL), a sign-in's after 5 minutes at most or on cancel, and all of them when Switchboard stops.
- **Sign-in:** the CLI's own OAuth flow; its callback listens on localhost of the machine running the helper. The authorization URL goes to the browser (it is meant to be opened); tokens stay in the CLI's storage. A pasted redirect URL must be an http(s) URL and is handed to the CLI, which checks its `state`.

## Accounts (D63)
`docs/accounts.md`.
- **No token is ever touched:** sign-in and sign-out are the CLI's own commands (`claude auth login | logout | status`, `codex login | logout | login status`, OpenCode's server routes); Switchboard reads their output only for the page to open, a device code and the account label the status prints (email, plan), never a credential file (`.credentials.json`, `auth.json`, the Keychain, OpenCode's store). The login's output is kept in memory (16 KB) for the page, never logged or stored; an OpenCode API key is sent once to that profile's own loopback server and dropped.
- **Processes:** the login / logout / status commands are `spawn` argv arrays (`shell: false`), time-limited (status 20 s, logout 30 s, a sign-in 5 minutes), with the profile's folder variable in the scrubbed environment and `BROWSER=true` so the CLI does not open its own browser. OpenCode's sign-in server binds 127.0.0.1 on a free port with a random password and is registered with the orphan reaper; it is stopped when the sign-in ends.
- **Profile folders** are created under `<dataDir>/profiles/<cli>/<id>` with mode 0700; their conversation copies keep mode 0600. A folder is deleted only on request and only when it is inside `<dataDir>/profiles/` (the developer's own folders are never removed). Sharing the Default's settings links configuration only (`settings.json`, `CLAUDE.md`, agents, `config.toml`, …) and merges only `mcpServers` of Claude Code's `.claude.json`: credentials, `projects/`, `sessions/` and the account identity are never shared or copied between profiles except the conversation being switched.
- **Paste-back:** a pasted address is fetched only when it is a loopback `http(s)` URL (it is delivered to the CLI's own callback server on that machine); anything else is refused or written to the CLI's stdin as a code.
- **Peers:** the account routes are on the peer allow-list, so a paired machine can manage this machine's profiles and sign-ins (pairing is the trust, as for sessions and the MCP page).

## Take-over (D65)
- **Pairing is the trust, as for the MCP page and the accounts:** the take-over operations (`/api/takeover/source/*`, `target/*`, the leftovers) are on `PEER_API_ALLOW`, so a paired machine can ask this one to describe a session, push its work in progress, read its conversation files, check out a branch, clone a repo into a path it names and start a session there (the same reach a peer already has through `POST /api/sessions`). Starting a take-over (`preview`, the start, the run's status) is **not** on the list: a peer never drives one through us.
- **What the other machine sends is checked before it reaches git** (`src/core/takeover.ts`): branch and temp-branch names (no leading `-`, no ref syntax), repo keys, commit ids and the clone URL (no transport helpers such as `ext::`; `git clone -- <url>`); every git call is argv-only. File names in a transfer must be relative and stay inside the staging folder (`<dataDir>/takeover/<op>/files/`); chunks are bounded, a file is verified by size and sha256 and capped at 200 MB.
- **Only a take-over branch is ever deleted** (`switchboard/takeover/…`); the real branch is never pushed or forced. The WIP commit is built outside the source's branch, index and working tree; the source repo is only read.
- **No secret travels:** git uses each machine's own credentials; remote URLs are sent and logged without their `user:password@` part; the CLI's credentials are not copied (the conversation files only). A hooked terminal's process is stopped only after `claude agents --json` confirmed that pid for that session.

## Agent todo tools (D68)
- **`/agent/*` is its own door** (`src/server/security.ts`): never from a page (any `Origin` → 403), never the cookie; only `Authorization: Bearer <agent token>` with the session named in `x-switchboard-session` (else 401), after the same Host check as everything else. The routes behind it (`src/server/api/todos.ts`) read only that session's list: the session comes from the checked header, never from the path, and an item id of another session is 404.
- **The agent token** (`src/server/todos/agent-token.ts`) is HMAC-SHA256 of the session id under the install's secret (`sb_token`), base64url: not guessable without the secret, one per session (session A's token named as session B is refused), and nothing to store (a resume or a restart derives the same one). It opens nothing under `/api` or `/hub`, and `/agent/*` is not on the peer API.
- **Where it travels:** to the session's CLI only, never on an argv: Claude Code reads it from its `--mcp-config` file (`<dataDir>/agent-mcp/<session id>.json`, folder 0700, file 0600, rewritten at each spawn); Codex CLI from its own environment (`env_vars`); OpenCode from `OPENCODE_CONFIG_CONTENT` (its environment). The agent itself can see it (it runs as the user with that environment): the scope is what limits it, not secrecy from the session's own agent.
- **The helper** (`src/hook/sb-mcp.ts`, built on the official MCP TypeScript SDK `@modelcontextprotocol/sdk` + `zod`, exact-pinned runtime dependencies; only its stdio server is used) only talks to `127.0.0.1:<port>`; it reads no file and no other variable, and forwards only the tool's arguments.
- **D69:** `GET /agent/v1/todos/{todoId}` (the `todo_get` tool) is behind the same door: one item of the token's own session (another session's id is 404). The description and plan are Markdown the UI renders with the chat's renderer (D20: no raw HTML, no images, only http(s) / mailto links), so an agent's text cannot inject markup into the page.

## Artifacts (D89)
Artifacts saved on purpose (`docs/artifacts.md`). Code: `src/server/artifacts/service.ts`, `src/server/api/artifacts.ts`, `src/web/views/session/ArtifactViewer.tsx`.
- **An HTML artifact runs, but never as the app.** The viewer frames the version's raw route (`GET /api/sessions/{id}/artifacts/{artifactId}/versions/{n}/raw`) in `<iframe sandbox="allow-scripts">`, **without** `allow-same-origin`, `allow-top-navigation`, `allow-popups` or `allow-forms`; and the route serves it with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; media-src data: blob:; form-action 'none'; base-uri 'none'; frame-ancestors 'self'`. So the page gets an **opaque origin** even when it is opened on its own (a new tab, the Download link): `document.cookie` throws, it has no storage of the app's origin, and `default-src 'none'` stops every request (no fetch, no images or scripts from anywhere, the app's API included). The `sb_token` cookie is `HttpOnly` and `SameSite=Strict` besides, and the request guard refuses any request whose `Origin` is not the service's own (an opaque origin sends `Origin: null`). Only the app may frame it (`frame-ancestors 'self'`). A test runs a page that tries the cookie and the API (`tests/e2e/session-artifacts.spec.ts`).
- **A Mermaid diagram is drawn the same way** (developer ruling 2026-10-09): the raw route's `?render` on a Mermaid version serves a page that inlines the pinned Mermaid bundle (`dist/web/vendor/mermaid.min.js`) and the HTML-escaped source, under the HTML CSP above, framed `sandbox="allow-scripts"`; Mermaid runs with `securityLevel: 'strict'` (its own sanitizing, no click handlers or HTML labels), in the opaque origin, never in the app's. The bundle is also a static file of the UI (`/vendor/mermaid.min.js`, public library code like the app's own assets); the app never loads it.
- **An SVG is an image, never markup in the page:** shown with `<img src>` of the raw route (scripts in an `<img>` never run), served as `image/svg+xml` under `default-src 'none'; …; sandbox` (opened on its own, its scripts do not run either). Images are served as their sniffed type under the same CSP; every other text kind as `text/plain`. Always `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`.
- **Markdown, code, Mermaid and CSV** render with the chat's renderer (D20: no raw HTML, no images loaded, http(s) / mailto links only) or as plain table cells: an agent's text cannot inject markup.
- **`path` copies only from the session's own folders:** the agent's `artifact_save` may name a file instead of `content`; Switchboard (not the helper) resolves it against the session's working folder, resolves symbolic links (`realpath`), and copies it only when it is a regular file inside the session's folder, its working folder or one of its registered worktrees, within the size limits (2 MB text, 10 MB image; an image must sniff as png / jpg / gif / webp). Anything else is refused (422 / 413). The developer's Save as artifact takes `content` only.
- **Scope and storage:** the agent's routes (`/agent/v1/artifacts…`) are behind the agent token like the todo tools: only the token's session's artifacts, an id of another session's is 404. Image files live in `<dataDir>/artifacts/<id>/` (0700 / 0600); the file a version names is checked to stay inside that folder before it is read.
- **Who may:** the UI (cookie); a paired machine through its peer API (read, save from a message, delete; the bytes pass through with their headers, the CSP included); a paired phone (normal use).

## Checkpoints (D80)
- **Git only, argv only, in the session's own repos** (`src/server/checkpoints/git.ts`): a checkpoint writes objects and one ref under `refs/switchboard/checkpoints/` (the only refs Switchboard ever writes or deletes there: `isCheckpointRef`); the developer's index, HEAD, branch and files are not written. Switchboard's own `GIT_DIR` / `GIT_INDEX_FILE` / `GIT_WORK_TREE` never reach these calls; the temp index lives in the OS temp folder and is removed.
- **A revert writes only inside the working tree it reverts:** every path comes from `git diff-tree` between two of its own trees and is checked to stay inside the top-level folder; ignored files are never in those trees, so never touched. A branch is moved with `update-ref <new> <old>` (refused if it moved meanwhile), never `reset --hard`, never a push; pushed commits refuse the move.
- **Who may:** the UI (cookie), a paired machine through its peer API (pairing is the trust, as for messages), a paired phone (normal use, with the confirm). The checkpoint refs are local: they are only pushed if the developer pushes `--mirror` / `refs/*` themselves.

## Other CLIs (D62)
`docs/providers.md`.
- **Spawning:** Codex CLI (`codex app-server`, its `--version`, `login status`, `mcp list|add|remove`) and OpenCode (`opencode serve`, `--version`, `auth list`, `models`, `session list`, `export`, `mcp list`) are spawned like Claude Code: `spawn(cmd, argvArray, { shell: false })`, time-limited, from `SWITCHBOARD_CODEX_BIN` / `SWITCHBOARD_OPENCODE_BIN` or the Settings → CLIs override (an argv array, never shell-parsed); the child env is the service's with Claude Code's own variables scrubbed.
- **Credentials are never read:** sign-in is each CLI's own check (`codex login status`, `opencode auth list` read for its counts only); `~/.codex/auth.json`, OpenCode's `auth.json` and its SQLite store are never opened. History reads only Codex's rollout files (`$CODEX_HOME/sessions/**/rollout-*.jsonl`, by name and content) and only when the developer asks for those conversations.
- **OpenCode's server** binds 127.0.0.1 on a free port, with a random 24-byte `OPENCODE_SERVER_PASSWORD` per server (HTTP Basic on every request; never stored or logged) and Switchboard's permission rules in `OPENCODE_CONFIG_CONTENT` (edits allowed; shell, web fetches and paths outside the project ask). It ends with the session's process (SIGTERM); see OPEN D62-orphan-opencode for a Switchboard that is killed.
- **Permissions:** Codex threads start with `approvalPolicy: on-request` + `sandbox: workspace-write` (leaving the workspace asks); approvals and questions come to the Inbox; "Always for this session" is the CLI's own (`acceptForSession`, `always`), offered only for those CLIs.
- **Handover exports** (a switch without the outgoing agent's handover) are written under `<dataDir>/handovers/<session>/` (folder 0700, file 0600) and hold the session's chat; nothing else is copied.
- **MCP:** Codex servers are added with `codex mcp add` (its argv carries the server's env values while it runs, as D61's `add-json` does); the page shows env names and masked commands / URLs only.
