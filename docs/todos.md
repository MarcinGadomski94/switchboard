# Session todos (D68, D69, D70)

Every session has a todo list: things that still need doing. The developer keeps it in the session (and on the Todos page); the session's agent keeps it through built-in MCP tools, so "add it to the todo list" in the chat lands on the same list. Each item has a **title**, a **description** for the developer and a **handover plan** for an AI agent (D69), a **priority** and an **estimate** (D70; the plan is mandatory, `No plan` allowed). Rulings: `docs/decisions.md` → D68, D69, D70. Contract: `docs/handoff/contracts/local-api.md` → *Session todos (D68)*, *Todo title, description and handover plan (D69)* and *Todo priority, estimate and the mandatory plan (D70)*.

## Storage
- Migration **0026** (`session_todos`, `docs/database.md`): id, session, text (D69: `title`), state (`open` / `done`), who added it (`developer` / `agent`), position, created / updated, `done_at`. Deleting a session deletes its items.
- `src/server/db/repos/todos.ts` (the rows), `src/server/todos/service.ts` (`TodoService`: validation, events, the hour's removal), `src/core/todos.ts` (the shared rules and the tool definitions).
- D68: text trimmed, 1–1,000 characters. D69: see *Title, description and plan* below. D70: migration **0028** adds `priority` and `estimate_minutes` and fills empty plans; see *Priority, estimate and the mandatory plan* below. A session keeps at most 200 items (open and done together), so a runaway agent stops with `409 too-many`.

## Done items
- A ticked item stays visible (struck through, under a collapsed **Done (n)**) and is **removed automatically one hour after it was ticked**, earlier by its ✕ or **Clear done**. Unticking it before the hour cancels the removal (its `done_at` is cleared).
- Server side: `TodoService.start()` sweeps at startup (items whose hour passed while Switchboard was stopped go at once), then a timer is armed for the earliest `done_at` + 1 hour, re-armed after every change and every sweep. The hour is computed from the stored `done_at`, so a restart keeps it. Every item answer carries `removeAt`.

## The agent's tools
- Every session Switchboard **starts or resumes** (new, resume, restart recovery, Attach here, account and CLI switches, take-over) gets an MCP server named **`switchboard`** with six tools (D69): `todo_list` (compact), `todo_get` (id: the item in full), `todo_add` (title, description?, plan, priority, estimate_minutes: D70), `todo_update` (id, title?, description?, plan?, priority?, estimate_minutes?), `todo_done` (id; `done: false` reopens), `todo_remove` (id). Items show their id in brackets in every tool answer (`[3f9a1c2b7d4e] ☐ HIGH ~45m Fix the login test · has description, plan`), so the agent can name them.
- The server is a small stdio helper, `src/hook/sb-mcp.ts` (run by Switchboard's own Node like the hook script), started by the CLI as `node sb-mcp.ts --switchboard-mcp <port> <sessionId>` with the session's **agent token** in `SWITCHBOARD_TODO_TOKEN`. It speaks MCP over stdio and turns each call into one request to `http://127.0.0.1:<port>/agent/v1/todos`. Failures (Switchboard stopped, an unknown id, a missing field) are tool errors the agent can read.
- **Built on the official MCP TypeScript SDK** (`@modelcontextprotocol/sdk` with `zod`, both exact-pinned runtime dependencies, so a release install's `npm ci --omit=dev` brings them; the helper imports them from the app's `node_modules`). It uses the SDK's high-level API: one `McpServer` over a `StdioServerTransport`, each tool registered with `registerTool(name, { title, description, inputSchema, annotations }, handler)` next to its own handler (`todoList`, `todoGet`, `todoAdd`, …), so a directory scanner can resolve every tool's handler. `src/core/todos.ts` (`TODO_TOOLS`, `AGENT_MCP_INSTRUCTIONS`) stays the one place of the names, descriptions, annotations and instructions; the zod input schemas take their field descriptions from it, and a test checks `tools/list` against it.
  - The zod fields are **optional for validation** and the JSON Schema's `required` / `additionalProperties: false` are declared as `TODO_TOOLS` has them: a missing title, plan, priority or estimate reaches the handler, which answers what is missing in its own words (D70), and D68's `text` (the old name of the title) still works. A value of the wrong type or outside the schema (a priority `asap`, an estimate `1.5`) is answered by the SDK's input validation, also as a tool error (`Input validation error: Invalid arguments for tool …`), and nothing is sent.
  - `tools/list` as the SDK renders it adds, next to `TODO_TOOLS`' fields, the display `title` on the tool (the annotation's), `$schema` (JSON Schema draft-07) in each input schema and `execution: { taskSupport: "forbidden" }`. The server declares `tools: { listChanged: true }` (the SDK's), answers the client's protocol version when it knows it (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, 2024-10-07), else its newest; `ping` is the SDK's. `resources/list` / `prompts/list` are no longer answered (the server never declared them). A line that is not JSON is skipped. Tool calls run one at a time in the order they came, as before.
  - Startup: about 175 ms from spawn to the `initialize` answer (about 95 ms for the dependency-free helper it replaced).
- **Scope:** the agent token is HMAC-SHA256 of the session id under the install's secret (`src/server/todos/agent-token.ts`): it opens that one session's list and nothing else (no `/api`, no other session; an item id of another session is 404). See `docs/security.md` → *Agent todo tools (D68)*.
- **Injection** (`src/server/todos/agent-mcp.ts`, `SpawnRequest.agentMcp`), added to the developer's own MCP configuration, never replacing it, and never writing their files:
  - **Claude Code:** `--mcp-config <dataDir>/agent-mcp/<session id>.json` (0600, rewritten at every spawn, so the token is not on the argv) and `--allowedTools mcp__switchboard` (its tools run without a permission prompt). No `--strict-mcp-config`: the developer's user / project / local servers load as before. VERIFIED with one bounded real probe (CLI 2.1.285, Haiku, an isolated config folder): `system/init` lists `switchboard` as `connected` (source `dynamic`) with the five `mcp__switchboard__todo_*` tools. The tool call itself was not run against the model (the isolated folder has no login, by design).
  - **Codex CLI:** `-c mcp_servers.switchboard.command=…`, `.args=[…]`, `.env_vars=["SWITCHBOARD_TODO_TOKEN"]` before `app-server`; the token is in the app-server's own environment. UNVERIFIED (no Codex CLI here; `docs/spike-providers.md` lists the probe).
  - **OpenCode:** an `mcp.switchboard` entry (`type: local`, `command`, `environment`, `enabled`) merged into `OPENCODE_CONFIG_CONTENT` next to the environment's own servers. UNVERIFIED likewise.
- A launch that cannot be prepared (the config file cannot be written) is reported and the session starts without the tools.
- **Not injected:** hand-started hooked terminal sessions (D48 P4): Switchboard does not start their process, so their list is the UI's only. The D61 helper processes, the usage poller and model listings are not sessions either.
- **The MCP page (D61)** does not show the server: it is not in any of the developer's config files, and the page's helper process starts without it.
- **Standing instruction (D64):** the default gains one sentence; D70: "Todo list: when asked to add to it, use the switchboard todo tools with a title, short description, handover plan (or 'No plan: reason'), priority and estimate (minutes); revise those as you learn more; mark items done when finished; check it when asked what's left." (502 characters in all; the "short" bound in the tests went from 450 to 510.) A stored text equal to an earlier default (D64's, 1.7.0's with D68's sentence, or 1.8.0's with D69's) reads as the new default (`currentStandingInstruction`); a text the developer edited stays theirs and does not get the sentence (ASSUMED D68-instruction-edited). The server's MCP `instructions` (`AGENT_MCP_INSTRUCTIONS`) explain the fields (D70: also the plan's `No plan: <reason>`, the four priorities and the estimate), for CLIs that pass them on.

## Title, description and plan (D69)
- **title**: one short line, 1–120 characters (a line break is refused; the form turns one into a space).
- **description**: for the developer: plain, brief Markdown, at most 4,000 characters; optional.
- **plan**: the **handover plan for an AI agent**: context, relevant files, steps, acceptance criteria, enough to pick the item up cold without the conversation it came from. Markdown, at most 8,000 characters; ~~optional~~ D70: mandatory (`No plan` when there is nothing to plan).
- Migration **0027** renames `text` to `title` and adds `description` and `plan`. An existing text with a line break or over 120 characters keeps all of it as the description; its title is its first line, cut to 119 characters + `…`.
- **Compatibility:** `text` is accepted for `title` on input, and every item still carries `text` (= title), so a paired machine on 1.7.0 keeps working through the peer proxy (it drops the description and plan: it has no columns for them).
- **The agent fills all three.** When asked to add something, the agent writes the title, a short description, and a handover plan drafted from what has been discussed: the tools' JSON-schema descriptions, the server's `instructions` and the standing instruction all say so. `todo_list` stays compact (id, state, title, `· has description, plan`); `todo_get` reads one item in full before the agent starts on it.

## Priority, estimate and the mandatory plan (D70)
- **Plan is mandatory.** An item always has a plan; when there is nothing to plan it says `No plan` (an agent writes `No plan: <one-line reason>`). The agent's `todo_add` schema requires it; the server stores an absent or blank plan on **create** as `No plan` on every route (an older UI or peer, or an older agent tool, keeps working; ruling D70: no 422 for it). On **update** a plan can change but not be emptied: `""` / `null` / blanks are 422 (`write a handover plan, or "No plan: <one-line reason>"`). Migration 0028 gave every existing item without a plan `No plan`.
- **`No plan` is not a plan** (`todoHasPlan`): `No plan` and `No plan: …` (any case) give no **▸ Handover plan** on the card (▶ Start sits on the title row), ▶ Start sends the description instead, and `todo_list` does not say `has plan`.
- **Priority:** `urgent` / `high` / `medium` / `low` (labels Urgent / High / Medium / Low; existing and unspecified items `medium`). How to judge (tool and field descriptions): urgent = blocking or breaking now (production down, data loss, blocks other work); high = important, should be next; medium = a normal task; low = nice-to-have or cleanup. The agent sets it in `todo_add` and may revise it with `todo_update` when it learns more.
- **Estimate:** `estimate_minutes` / `estimateMinutes`, whole minutes 1–10,080 (a week), `null` = not estimated (`—` nowhere: the card just shows none). It is the agent's rough estimate of how long **an AI agent** would take to do the item (development time), not a human's. Required in `todo_add`'s schema, nullable for older callers; revised with `todo_update`.
- **Order:** open items sort by priority (urgent → low), the manual order (`position`) within a level (`splitTodos`): the strip, the Todos page and `todo_list`. **Move up / down** swaps only within the item's level (`todoMoveScope`); the ⋯ entries are disabled at the level's edges. A changed priority moves the item into its new level by its own position. Done items keep their list order. The collapsed strip's next item is the top one after sorting.
- **Look:** an open card has a 3px left edge in its priority's color, a barely visible tint over the card fill and a small label (URGENT red, HIGH amber, MEDIUM neutral, LOW blue-grey), tokens `--todo-*` in `styles/tokens.css` (tints are 3–4% sRGB mixes into `--bg-card-2`; medium has none). The estimate shows next to the label: `~45m`, `~2h`, `~1h 30m`. Done cards: no edge color, tint, label or estimate (muted as before).
- **Totals:** the strip header reads `3 open · ~2h 15m · 1 done`: the open items' known estimates, with a `+` when some open items have none (`~2h 15m+`), left out when none is known (`todoEstimateTotal`). The Todos page shows the same total in each session's header, after its open count.
- **The form:** under the title, **Priority** (a select, prefilled Medium) and **Estimate** (optional text: `45`, `45m`, `2h`, `1h 30m`, `1.5h`; an unreadable or out-of-range value shows a message and disables Save), then the description and the **Handover plan**, now always shown and required (a new item's is prefilled `No plan`; an emptied plan disables Save). After **+ Add** the form resets to `No plan`, Medium and no estimate. The priority is changed in this form (Edit) or with one click in the card's ⋯ → **Priority ▸** submenu (below).
- **⋯ → Priority ▸** (open cards, strip and Todos page; developer ruling): the ⋯ menu reads Edit, **Priority ▸**, Move up, Move down, Delete. Priority opens a submenu to the left of the menu: Urgent / High / Medium / Low (`role="menuitemradio"`, the current one `aria-checked`, shown with a ✓). → / Enter / a click open it with the focus on the checked level; ↑ ↓ move; ← or Esc close the submenu (focus back on Priority; Esc again closes the menu); Enter / a click sets the level, closes the menu and the list re-sorts. Done cards have no Priority entry.
- **Agent output:** `todo_list` lines carry the priority and estimate (`[id] ☐ HIGH ~45m Fix … · has description`, `~?` when not estimated); `todo_get` adds `Priority: High` and `Estimate: ~45m (45 minutes for an AI agent)`.
- **Peers and take-over:** an older peer's items read as medium, not estimated, `No plan`; a take-over carries `priority` and `estimateMinutes` (from an older source: medium / none / `No plan`).

## In the session
- A collapsible strip just above the composer. Its header: **▾ TODO**, `3 open · 1 done` (D70: `3 open · ~2h 15m · 1 done`), a thin progress bar (done / all) and **+ Add** on the right; collapsed it also shows the next open item's title (D70: the top one by priority). Expanded (remembered in this browser): the open items as **cards** (D70: by priority), and, when there are done items, **▸ Done (n)** (collapsed) with the note "removed an hour after done" and **Clear done**.
- **A card:** a round box to tick, the bold title, the description (rendered Markdown with the chat's renderer, D20) muted and clamped to two lines, who added it (`you` / `agent`) and how long ago on the right, and a **⋯** menu (Edit, D70 Priority ▸, Move up, Move down, Delete; arrows move in it, Esc closes it). With a plan, a row under the description holds **▸ Handover plan** and **▶ Start**; the plan opens **below** that toggle in a scrollable panel. Without a plan, **▶ Start** sits on the title row (no row of its own). A click on the card (or Enter on its title) opens it in place: the full description and the plan; opening a card or its plan keeps its title row in view (the list scrolls, not the title away). The expanded strip is at most about a third of the window (32vh); its list scrolls inside.
- **The form** (**+ Add** at the top of the list, **Edit** in place of the card): title (required), D70 priority and estimate, description, and the plan (D69: behind **+ Add handover plan** until it had text; D70: always shown, required, prefilled `No plan`); the plan's field grows with its text. **Save** / **Cancel** stay in view (stuck to the bottom of the list; the description and plan fields grow only to a capped height, then scroll); Esc cancels, ⌘ / Ctrl + Enter saves (Enter too in the title). An emptied description is removed (D70: an emptied plan cannot be saved). After a successful **+ Add** the form stays open, cleared, with the title focused for the next item; Esc or Cancel closes it (D69 ruling).
- **Done cards:** the box filled, the title struck through, no description, and `removed in 42m` (minutes to the hour's removal).
- **▶ Start** (open items): fills this session's message box with `Work on todo [<id>]: <title>`, a blank line and the plan (else the description; D70: `No plan` counts as none), and focuses it. It never sends. A draft already in the box is kept; the message goes after it, with no dialog (D69 ruling). `src/web/views/session/composer-fill.ts` hands the text to the composer.
- While the list is empty the strip is not shown; a small **+ Todo** pill sits just above the composer's top edge at the right (out of the flow: no part of the chat or the composer moves) and opens the strip with the add form.
- Live: `todosChanged` reloads the list, so an item the agent adds shows at once. An unreachable peer's session shows its list read-only.

## Sidebar and Todos page
- A session row with open items shows **☐ n** right of its title, before its age.
- The nav has **Todos** after History (like D61's MCP after the prototype's items, so the prototype's parts keep their places), with the total open count of the listed sessions (this machine's and the paired machines').
- `/todos`: every open session that has items, most recently active first, under a session header: its title (opens it), its machine tag, where it works (solutions, else the folder), its open count, D70 its open items' estimate total, and **Open session**; then the same cards as the strip (tick, open, plan, ⋯ Edit / Move / Delete). **▶ Start** opens the session and fills its composer. **Show done (n)** adds each group's done cards under **Done (n)**. Closed sessions are left out.

## Peers (D48) and take-over (D65)
- A paired machine's session's list is read and edited through the peer proxy like every session route (`r~<machine>~<id>`, the routes are on `PEER_API_ALLOW`); answers and `todosChanged` carry the remote ids. The Todos page lists the paired machines' groups as last known (`PEER_LISTS.todos`, snapshotted like the schedules; fetched again when a `todosChanged` arrives from that machine or after an edit through the proxy).
- A take-over carries the list: `SourceInspect.todos` (title, description, plan, state, author, created, done time; D69 also `text` = title for a 1.7.0 target; from a 1.7.0 source the text is split like migration 0027), re-created on the new session before the agent's first turn (`beforeSpawn`), so a done item keeps its hour. An older Switchboard sends none: its list stays behind with the moved-away session.
