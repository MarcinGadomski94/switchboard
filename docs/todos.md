# Session todos (D68, D69, D70, D75, D76, D77, D78, D81)

Every session has a todo list: things that still need doing. The developer keeps it in the session (and on the Todos page); the session's agent keeps it through built-in MCP tools, so "add it to the todo list" in the chat lands on the same list. Each item has a **title**, a **description** for the developer and a **handover plan** for an AI agent (D69), a **priority** and an **estimate** (D70; the plan is mandatory, `No plan` allowed). D75: an item can be **in progress** between open and done, **▶ Start sends** its message, and the agent is reminded once to finish what it started. D81: an item can be **captured quickly** (⌘K, a chat selection, the phone's share sheet) and the agent fills it in when it is idle. Rulings: `docs/decisions.md` → D68, D69, D70, D75, D81. Contract: `docs/handoff/contracts/local-api.md` → *Session todos (D68)*, *Todo title, description and handover plan (D69)*, *Todo priority, estimate and the mandatory plan (D70)* *Todo in progress and ▶ Start that sends (D75)* and *Quick capture (D81)*.

## Storage
- Migration **0026** (`session_todos`, `docs/database.md`): id, session, text (D69: `title`), state (`open` / `done`; D75, migration **0031**: also `in_progress`, with `started_at`, `started_by`, `reminded_at`), who added it (`developer` / `agent`), position, created / updated, `done_at`. Deleting a session deletes its items.
- `src/server/db/repos/todos.ts` (the rows), `src/server/todos/service.ts` (`TodoService`: validation, events, the hour's removal), `src/core/todos.ts` (the shared rules and the tool definitions).
- D76 / D78: migration **0032** rebuilds `session_todos` with the `review` state and `run_session_id`, `run_state`, `started_first_at`, `span_started_at`, `actual_ms`, `actual_tokens`, adds `sessions.todo_link` and the `todo_actuals` history (`docs/database.md`).
- D68: text trimmed, 1–1,000 characters. D69: see *Title, description and plan* below. D70: migration **0028** adds `priority` and `estimate_minutes` and fills empty plans; see *Priority, estimate and the mandatory plan* below. A session keeps at most 200 items (open and done together), so a runaway agent stops with `409 too-many`.

## Done items
- A ticked item stays visible (struck through, under a collapsed **Done (n)**) and is **removed automatically one hour after it was ticked**, earlier by its ✕ or **Clear done**. Unticking it before the hour cancels the removal (its `done_at` is cleared).
- Server side: `TodoService.start()` sweeps at startup (items whose hour passed while Switchboard was stopped go at once), then a timer is armed for the earliest `done_at` + 1 hour, re-armed after every change and every sweep. The hour is computed from the stored `done_at`, so a restart keeps it. Every item answer carries `removeAt`.

## The agent's tools
- Every session Switchboard **starts or resumes** (new, resume, restart recovery, Attach here, account and CLI switches, take-over) gets an MCP server named **`switchboard`** with seven tools (D69; D75 `todo_start`): `todo_list` (compact), `todo_get` (id: the item in full), `todo_add` (title, description?, plan, priority, estimate_minutes: D70), `todo_update` (id, title?, description?, plan?, priority?, estimate_minutes?), `todo_start` (id: in progress, D75), `todo_done` (id; `done: false` reopens it, not started), `todo_remove` (id). Items show their id in brackets in every tool answer (`[3f9a1c2b7d4e] ☐ HIGH ~45m Fix the login test · has description, plan`), so the agent can name them.
- The server is a small stdio helper, `src/hook/sb-mcp.ts` (run by Switchboard's own Node like the hook script), started by the CLI as `node sb-mcp.ts --switchboard-mcp <port> <sessionId>` with the session's **agent token** in `SWITCHBOARD_TODO_TOKEN`. It speaks MCP over stdio and turns each call into one request to `http://127.0.0.1:<port>/agent/v1/todos`. Failures (Switchboard stopped, an unknown id, a missing field) are tool errors the agent can read.
- **Built on the official MCP TypeScript SDK** (`@modelcontextprotocol/sdk` with `zod`, both exact-pinned runtime dependencies, so a release install's `npm ci --omit=dev` brings them; the helper imports them from the app's `node_modules`). It uses the SDK's high-level API: one `McpServer` over a `StdioServerTransport`, each tool registered with `registerTool(name, { title, description, inputSchema, annotations }, handler)` next to its own handler (`todoList`, `todoGet`, `todoAdd`, …), so a directory scanner can resolve every tool's handler. `src/core/todos.ts` (`TODO_TOOLS`, `AGENT_MCP_INSTRUCTIONS`) stays the one place of the names, descriptions, annotations and instructions; the zod input schemas take their field descriptions from it, and a test checks `tools/list` against it.
  - The zod fields are **optional for validation** and the JSON Schema's `required` / `additionalProperties: false` are declared as `TODO_TOOLS` has them: a missing title, plan, priority or estimate reaches the handler, which answers what is missing in its own words (D70), and D68's `text` (the old name of the title) still works. A value of the wrong type or outside the schema (a priority `asap`, an estimate `1.5`) is answered by the SDK's input validation, also as a tool error (`Input validation error: Invalid arguments for tool …`), and nothing is sent.
  - `tools/list` as the SDK renders it adds, next to `TODO_TOOLS`' fields, the display `title` on the tool (the annotation's), `$schema` (JSON Schema draft-07) in each input schema and `execution: { taskSupport: "forbidden" }`. The server declares `tools: { listChanged: true }` (the SDK's), answers the client's protocol version when it knows it (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, 2024-10-07), else its newest; `ping` is the SDK's. `resources/list` / `prompts/list` are no longer answered (the server never declared them). A line that is not JSON is skipped. Tool calls run one at a time in the order they came, as before.
  - Startup: about 175 ms from spawn to the `initialize` answer (about 95 ms for the dependency-free helper it replaced).
- **Scope:** the agent token is HMAC-SHA256 of the session id under the install's secret (`src/server/todos/agent-token.ts`): it opens that one session's list and nothing else (no `/api`, no other session; an item id of another session is 404). See `docs/security.md` → *Agent todo tools (D68)*.
- **Injection** (`src/server/todos/agent-mcp.ts`, `SpawnRequest.agentMcp`), added to the developer's own MCP configuration, never replacing it, and never writing their files:
  - **Claude Code:** `--mcp-config <dataDir>/agent-mcp/<session id>.json` (0600, rewritten at every spawn, so the token is not on the argv) and `--allowedTools mcp__switchboard` (its tools run without a permission prompt). No `--strict-mcp-config`: the developer's user / project / local servers load as before. VERIFIED with one bounded real probe (CLI 2.1.285, Haiku, an isolated config folder): `system/init` lists `switchboard` as `connected` (source `dynamic`) with the five `mcp__switchboard__todo_*` tools. The tool call itself was not run against the model (the isolated folder has no login, by design).
  - **Codex CLI:** `-c mcp_servers.switchboard.command=…`, `.args=[…]`, `.env_vars=["SWITCHBOARD_TODO_TOKEN"]` before `app-server`; the token is in the app-server's own environment. UNVERIFIED (no Codex CLI here; `docs/spike-providers.md` lists the probe).
  - **OpenCode:** an `mcp.switchboard` entry (`type: local`, `command`, `environment`, `enabled`) merged into `OPENCODE_CONFIG_CONTENT` next to the environment's own servers. UNVERIFIED likewise.
- A launch that cannot be prepared (the config file cannot be written) is reported and the session starts without the tools.
- **Not injected:** hand-started hooked terminal sessions (D48 P4): Switchboard does not start their process, so their list is the UI's only. The D61 helper processes, the usage poller and model listings are not sessions either.
- **The MCP page (D61)** does not show the server: it is not in any of the developer's config files, and the page's helper process starts without it.
- **Standing instruction (D64):** the default gains one sentence; D70: "Todo list: when asked to add to it, use the switchboard todo tools with a title, short description, handover plan (or 'No plan: reason'), priority and estimate (minutes); revise those as you learn more; mark items done when finished; check it when asked what's left." (502 characters in all; the "short" bound in the tests went from 450 to 510.) D75: "…; always mark an item in progress when you start it and done when you finish it; check it when asked what's left." (550 characters; the bound is 560.) A stored text equal to an earlier default (D64's, 1.7.0's with D68's sentence, 1.8.0's with D69's, or 1.9–1.11's with D70's) reads as the new default (`currentStandingInstruction`); a text the developer edited stays theirs and does not get the sentence (ASSUMED D68-instruction-edited). The server's MCP `instructions` (`AGENT_MCP_INSTRUCTIONS`) explain the fields (D70: also the plan's `No plan: <reason>`, the four priorities and the estimate), for CLIs that pass them on.

## Title, description and plan (D69)
- **title**: one short line, 1–120 characters (a line break is refused; the form turns one into a space).
- **description**: for the developer: plain, brief Markdown, at most 4,000 characters; optional.
- **plan**: the **handover plan for an AI agent**: context, relevant files, steps, acceptance criteria, enough to pick the item up cold without the conversation it came from. Markdown, at most 8,000 characters; ~~optional~~ D70: mandatory (`No plan` when there is nothing to plan).
- Migration **0027** renames `text` to `title` and adds `description` and `plan`. An existing text with a line break or over 120 characters keeps all of it as the description; its title is its first line, cut to 119 characters + `…`.
- **Compatibility:** `text` is accepted for `title` on input, and every item still carries `text` (= title), so a paired machine on 1.7.0 keeps working through the peer proxy (it drops the description and plan: it has no columns for them).
- **The agent fills all three.** When asked to add something, the agent writes the title, a short description, and a handover plan drafted from what has been discussed: the tools' JSON-schema descriptions, the server's `instructions` and the standing instruction all say so. `todo_list` stays compact (id, state, title, `· has description, plan`); `todo_get` reads one item in full before the agent starts on it.

## Priority, estimate and the mandatory plan (D70)
- **Plan is mandatory.** An item always has a plan; when there is nothing to plan it says `No plan` (an agent writes `No plan: <one-line reason>`). The agent's `todo_add` schema requires it; the server stores an absent or blank plan on **create** as `No plan` on every route (an older UI or peer, or an older agent tool, keeps working; ruling D70: no 422 for it). On **update** a plan can change but not be emptied: `""` / `null` / blanks are 422 (`write a handover plan, or "No plan: <one-line reason>"`). Migration 0028 gave every existing item without a plan `No plan`.
- **`No plan` is not a plan** (`todoHasPlan`): `No plan` and `No plan: …` (any case) give no **▸ Handover plan** on the card (▶ Start sits on the title row), ▶ Start sends the description instead, and `todo_list` does not say `has plan`.
- **Priority:** `urgent` / `high` / `medium` / `low` (labels Urgent / High / Medium / Low; existing and unspecified items `medium`). How to judge (tool and field descriptions): urgent = blocking or breaking now (production down, data loss, blocks other work); high = important, should be next; medium = a normal task; low = nice-to-have or cleanup. The agent sets it in `todo_add` and may revise it with `todo_update` when it learns more.
- **Estimate:** `estimate_minutes` / `estimateMinutes`, whole minutes 1–10,080 (a week), `null` = not estimated (`—` nowhere: the card just shows none). It is the agent's rough estimate of how long **an AI agent** would take to do the item (development time), not a human's. Required in `todo_add`'s schema, nullable for older callers; revised with `todo_update`.
- **Order:** open items sort by priority (urgent → low), the manual order (`position`) within a level (`splitTodos`): the strip, the Todos page and `todo_list`. **Move up / down** swaps only within the item's level (`todoMoveScope`); the ⋯ entries are disabled at the level's edges. A changed priority moves the item into its new level by its own position. Done items keep their list order. The collapsed strip's next item is the top one after sorting.
- **Look:** an open card has a 3px left edge in its priority's color, a barely visible tint over the card fill and a small label (URGENT red, HIGH amber, MEDIUM neutral, LOW blue-grey), tokens `--todo-*` in `styles/tokens.css` (tints are 3–4% sRGB mixes into `--bg-card-2`; medium has none). The estimate shows next to the label: `~45m`, `~2h`, `~1h 30m`. Done cards: no edge color, tint, label or estimate (muted as before).
- **Totals:** the strip header reads `3 open · ~2h 15m · 1 done`: the open items' known estimates, with a `+` when some open items have none (`~2h 15m+`), left out when none is known (`todoEstimateTotal`). The Todos page shows the same total in each session's header, after its open count.
- **The form:** under the title, **Priority** (a select, prefilled Medium) and **Estimate** (optional text: `45`, `45m`, `2h`, `1h 30m`, `1.5h`; an unreadable or out-of-range value shows a message and disables Save), then the description and the **Handover plan**, now always shown and required (a new item's is prefilled `No plan`; an emptied plan disables Save). After **+ Add** the form resets to `No plan`, Medium and no estimate. The priority is changed in this form (Edit) or with one click in the card's ⋯ → **Priority ▸** submenu (below).
- **⋯ → Priority ▸** (open cards, strip and Todos page; developer ruling): the ⋯ menu reads Edit, **Priority ▸**, Move up, Move down, Delete. Priority opens a submenu to the left of the menu: Urgent / High / Medium / Low (`role="menuitemradio"`, the current one `aria-checked`, shown with a ✓). → / Enter / a click open it with the focus on the checked level; ↑ ↓ move; ← or Esc close the submenu (focus back on Priority; Esc again closes the menu); Enter / a click sets the level, closes the menu and the list re-sorts. Done cards have no Priority entry.
- **Agent output:** `todo_list` lines carry the priority and estimate (`[id] ☐ HIGH ~45m Fix … · has description`, `~?` when not estimated); `todo_get` adds `Priority: High` and `Estimate: ~45m (45 minutes for an AI agent)`.
- **Peers and take-over:** an older peer's items read as medium, not estimated, `No plan`; a take-over carries `priority` and `estimateMinutes` (from an older source: medium / none / `No plan`).

## In the session
- A collapsible strip just above the composer. Its header: **▾ TODO**, `3 open · 1 done` (D70: `3 open · ~2h 15m · 1 done`), a thin progress bar (done / all) and **+ Add** on the right; collapsed it also shows the next open item's title (D70: the top one by priority). Expanded (remembered in this browser): the open items as **cards** (D70: by priority), and, when there are done items, **▸ Done (n)** (collapsed) with the note "removed an hour after done" and **Clear done**.
- **A card:** a round box to tick, the bold title, the description (rendered Markdown with the chat's renderer, D20) muted and clamped to two lines, who added it (`you` / `agent`) and how long ago on the right, and a **⋯** menu (Edit, D70 Priority ▸, D75 Mark in progress / Mark not started, Move up, Move down, Delete; arrows move in it, Esc closes it). With a plan, a row under the description holds **▸ Handover plan** and **▶ Start**; the plan opens **below** that toggle in a scrollable panel. Without a plan, **▶ Start** sits on the title row (no row of its own). A click on the card (or Enter on its title) opens it in place: the full description and the plan; opening a card or its plan keeps its title row in view (the list scrolls, not the title away). The expanded strip is at most about a third of the window (32vh); its list scrolls inside.
- **The form** (**+ Add** at the top of the list, **Edit** in place of the card): title (required), D70 priority and estimate, description, and the plan (D69: behind **+ Add handover plan** until it had text; D70: always shown, required, prefilled `No plan`); the plan's field grows with its text. **Save** / **Cancel** stay in view (stuck to the bottom of the list; the description and plan fields grow only to a capped height, then scroll); Esc cancels, ⌘ / Ctrl + Enter saves (Enter too in the title). An emptied description is removed (D70: an emptied plan cannot be saved). After a successful **+ Add** the form stays open, cleared, with the title focused for the next item; Esc or Cancel closes it (D69 ruling). A field edited while the save was still in flight (the next item typed fast) keeps what was typed, even when it equals the saved value: the form counts each field's `input` events and clears only the fields with none since the save started (fix 2026-10-08; comparing values had dropped a repeated estimate or priority).
- **Done cards:** the box filled, the title struck through, no description, and `removed in 42m` (minutes to the hour's removal).
- **▶ Start** (open and in-progress items): ~~fills this session's message box~~ D75: **sends** `Work on todo [<id>]: <title>`, a blank line, the plan (else the description; D70: `No plan` counts as none), a blank line and `When it's finished, mark it done with todo_done [<id>]; if you stop before it's finished, say what's left.` to the session as a normal user message, and marks the item **in progress** (see *In progress (D75)*). The message box and its draft are not touched (D69's composer fill is gone).
- While the list is empty the strip is not shown; a small **+ Todo** pill sits just above the composer's top edge at the right (out of the flow: no part of the chat or the composer moves) and opens the strip with the add form.
- Live: `todosChanged` reloads the list, so an item the agent adds shows at once. An unreachable peer's session shows its list read-only.

- The nav has **Todos** after History (like D61's MCP after the prototype's items, so the prototype's parts keep their places), with the total open count of the listed sessions (this machine's and the paired machines').

Closed sessions are left out.

## Peers (D48) and take-over (D65)
- A paired machine's session's list is read and edited through the peer proxy like every session route (`r~<machine>~<id>`, the routes are on `PEER_API_ALLOW`); answers and `todosChanged` carry the remote ids. The Todos page lists the paired machines' groups as last known (`PEER_LISTS.todos`, snapshotted like the schedules; fetched again when a `todosChanged` arrives from that machine or after an edit through the proxy).
- A take-over carries the list: `SourceInspect.todos` (title, description, plan, state, author, created, done time; D69 also `text` = title for a 1.7.0 target; from a 1.7.0 source the text is split like migration 0027), re-created on the new session before the agent's first turn (`beforeSpawn`), so a done item keeps its hour. An older Switchboard sends none: its list stays behind with the moved-away session.

## In progress (D75)
Developer request 2026-10-08: "When clicking Start on a todo item, it's fine to just send the message … It would be nice if we could follow the status of the todo in the sense of 'in progress' too." Rulings: `docs/decisions.md` → D75.

- **States:** `open` → `in_progress` → `done`, and back: in progress → open (**Mark not started**), done → open (reopen, as before). **Several items** may be in progress at once. An in-progress item is an open one for the order (**priority order is kept**: it is not moved to the top), for Move up / down, the counts and the estimate total.
- **Who starts an item:** **▶ Start** (sends the start message; `startedBy: start`), the agent's **`todo_start`** (`startedBy: agent`; on an item the developer had marked, it becomes the agent's start), the developer's **⋯ → Mark in progress** (`startedBy: developer`; nothing is sent). **⋯ → Mark not started** puts it back to open. The **tick** on an in-progress card marks it done.
- **▶ Start sends** (`POST /api/sessions/{id}/todos/{todoId}/start`, `TodoService.startItem`): the item goes in progress first (afresh, also when it already was: its reminder is re-armed), then the message goes like `POST …/messages`: queued while the agent is busy (D44 / D50), a session without a live process is resumed with it, a **hooked terminal session**'s message waits in its mailbox for its next idle waiter (D48 P4). When the message is refused (closed, detached, a hooked session's refusal) the item is put back as it was and the refusal is shown. A done item cannot be started (reopen it first). A **paired machine's** session goes through the peer proxy; a peer before D75 has no such route: the UI then sends the start message as a plain message and the item stays as it was there.
- **The agent marks it done (developer ruling)**, enforced three ways: the start message ends with the finish line; `todo_start` / `todo_done`, the MCP `instructions` and the default standing instruction say to mark an item in progress when starting it and done when finishing it, always; and **one reminder** (below).
- **The finish reminder** (`src/server/todos/reminder.ts`, `TodoReminder`): when one of this machine's sessions goes from `run` to `idle` / `done` (a turn ended; `need` → `run` is the same turn), every item of it that is in progress, was started by ▶ Start or `todo_start` (not ⋯ → Mark in progress), has no reminder for this start yet, and was not changed by the agent during that turn (`todo_update`, `todo_done`, `todo_remove`; marking it in progress does not count), gets **one** message: `Todo [<id>] '<title>' is still in progress. If it's finished, mark it done with todo_done; if not, say what's left.` (origin `service`, one message per item). It is recorded (`reminded_at`), so it comes **at most once per item per start**; ▶ Start again re-arms it. A **hooked** session gets it only while its waiter is held (else it is not recorded, and a later turn end tries again); a paired machine's sessions are reminded by their own machine; closed sessions never. The agent's changes are remembered in memory (a restart forgets them: the turn's start is then unknown and any earlier change counts).
- **Setting:** Settings → Sessions & worktrees → **Remind the agent to finish started todos** (`sessions.todoReminder`, default **on**), read at every turn's end.
- **Look:** an in-progress card has a **half-filled box** (◐, the run color), an **IN PROGRESS** label next to its priority label, and keeps its priority edge and tint; while its session **works** (status `run`) its left edge **pulses** gently between the priority color and the run color (`prefers-reduced-motion: reduce`: no pulse, the edge in the run color). Done cards are unchanged. Phones (D74) included: the label wraps with the priority under the title; the strip header's counts give way (ellipsis) before the progress bar and + Add.
- **Counts:** the strip header reads `1 in progress · 2 open · ~2h · 1 done` (`todoCountsLabel`; `open` = not started; the in-progress part only when some are; the estimate counts open + in progress); the Todos page's group count, the sidebar's **☐ n** and the Todos nav count count open + in progress (`openCount`; `inProgressCount` says how many are started).
- **Agent output:** `todo_list` lines `[id] ◐ IN PROGRESS HIGH ~45m Title`; `todo_get` `◐ in progress`.
- **Storage:** migration **0031** (`docs/database.md`).
- **Peers and take-over:** answers carry `state`, `startedAt`, `startedBy`; an older peer's item reads as open with no start; a take-over carries the state and the start (an older target reads in progress as open; the reminder can come once on the new session).
- **Esc** in a card's ⋯ menu closes the menu and no longer stops a running turn (D50's Esc ignores a focused menu).

## Run in a new session (D76)
Developer request 2026-10-08 (rulings: `docs/decisions.md` → D76): an item can run in a session of its own.

- **Where:** the card's **⋯ → Run in new session** (open and in-progress items without a running run; also on the Todos page and the board), and **Select** (the strip's header, the Todos page's list) → tick items → **Run N in new sessions** (one run per item, one after the other; items in review, done or already running cannot be picked).
- **Route:** `POST /api/sessions/{id}/todos/{todoId}/run` → 201 `{ session, list, note }` (`src/server/todos/run.ts`, `runTodo`). The new session starts in the **source session's folder** on branch **`todo/<slug>`** (the D22 short-name rule over the item's title; `todo/<slug>-2`, `-3`, … until it is free in every repo involved):
  - **repo folder:** a supervised **simple** start (D56) on its own worktree (`<repo>-wt-<name>`), **cut from the branch the source session has checked out** (its worktree's branch, else the repo's; a detached HEAD: that commit). The first message carries the usual worktree note (`… (branch todo/<slug>, from <source branch>)`).
  - **workspace folder (ruling 2026-10-08):** **one worktree per solution repo the source session uses** (its `solutions`, the set its diff and the Solutions view use), all on `todo/<slug>`, each **cut from that repo's current branch** for the source (its own worktree's branch there, else the main checkout's). The run works at the workspace root like a Full start with worktrees per solution (`createForSession`, the session's `branch` = `todo/<slug>`, so D38 adoption applies): a source with the router's answers starts the run as a **Full** start with the same answers (work type, mode, phase, coordination, QA, ultracode) and its first message carries the session-start block with the worktrees (`- <folder>: <path> (branch todo/<slug>, from <branch>)`); a simple source's run is a simple start whose first message adds a **worktree note** listing them. A source that uses **no solution repo** (none named yet, or none that resolves) runs **in place** and the answer's `note` says so.
  - **plain folder** (not a git repository): in the same folder without a worktree, with a note. A repo source whose branch cannot be read runs the same way.
  - **Launch settings:** the source session's CLI, model, effort and account profile, computed by **`todoRunOptions`** (`src/server/todos/run-options.ts`: `todoRunOptions(input: { source, todo, rules?, labels? }): { settings, rule, explanation }`, `TodoLaunchSettings = LaunchSettings = { provider, model, effort, profileId }`). It starts from the source's settings, and a D82 *Model by task* rule that matches the item's priority and estimate changes what it sets (`docs/model-routing.md` → *Wired into D76's runs*; the Run toast then shows `Routed by rule: …`). A start that names a model does not become the New-session form's last choice.
  - **Title** = the item's title (cut to 80 characters); **name** = its short name (unique); **first message** = the item's ▶ Start message (D75's, with the "mark it done with todo_done [<id>]" line).
- **Link:** before the process starts, the session records **`todoLink { sourceSessionId, todoId }`** (`sessions.todo_link`) and the item **`runSessionId`** with **`runState: active`**; the item goes **in progress** (`startedBy: run`; a span of its actuals opens). A refused start (folder gone, model no longer listed, branch / CLI problems; answered like `POST /api/sessions`) puts the item back as it was. 409 `already-running` for an item whose run session is open and active; 422 for a done item or one in review; 409 `no-folder` when the source's folder is no longer saved.
- **The run's agent:** its `switchboard` MCP tools use its own agent token, which also reaches **that one linked item** of the source session: `todo_get`, `todo_start`, `todo_update`, `todo_done` on its id (in `PUT /agent/v1/todos/{id}` the answer then carries the item and the run session's **own** list, never the source's other items); `todo_remove` and every other item of the source's list stay out of reach (404). `todo_list` adds the linked item under "The item you run". Only while the run is active (a discarded run's link reaches nothing). The finish reminder (D75) for the linked item goes to the **run** session (not the source session).
- **The card** shows **Run** and the run session (a link with its live status dot and word: working / needs you / idle / done / failed / paused / closed); the sidebar lists the run session like any session.
- **Peers:** a paired machine's item runs **on that machine** (the route is on `PEER_API_ALLOW`, its answer mapped as `todo-run`: session and list namespaced, `runSessionId` and `todoLink.sourceSessionId` too). Devices (D73) may call it.

## Review (D76)
- A fourth state **`review`** between in progress and done (migration **0032**). When an item **with an active run** is marked done (by its run session's agent, by the source session's agent or by the developer's tick), it becomes **review**, not done: its run's work waits for the developer. Done from review (the tick, or the board's Done) is **done**. `PUT …/todos/{todoId}` takes `state: "review"` only for an item with a run (422 otherwise), and **`skipReview: true`** (the board's drag to Done): done means done.
- Review is **neither open nor done**: not in `openCount` (the sidebar's ☐, the Todos nav) or `doneCount`; `reviewCount` (new) counts it; it has no done time, so the done hour never removes it. The strip and the Todos page list it after the open items (an **IN REVIEW** label, a three-quarter box, the actuals); the header reads `1 open · ~30m · 1 in review · 0 done`.
- **Lane B's review queue** publishes **`reviewResolved`** `{ sessionId, outcome }` (`ReviewResolvedEvent`, `src/core/reviews.ts`; `outcome`: `merged` / `committed` / `discarded` / `sent-back` / `dismissed`) when a session's review card is resolved. **`TodoReviewLink`** (`src/server/todos/review-link.ts`, started with the app) moves that session's items in review: **merged / committed / dismissed → done**; **discarded → open** (the run is marked **`discarded`**: the link stays as history and shows "Run (discarded)", the item can run again, and done no longer means review); **sent-back → in progress** again (the run's start, a new span).

## Board (D77)
- The Todos page has **List | Board** (top right; remembered in this browser, `sb.todos.view`). The board (`src/web/views/TodoBoard.tsx`, rules in `src/core/todo-board.ts`) has four columns **Open · In progress · Review · Done** across every listed session (this machine's and the paired machines'), each card as on the list, compact, and labelled with its session (title · machine · where it works). Within a column: priority, then the sessions in the page's order (most recently active first), then the session's own order.
- **Filters:** priority, machine (shown when a paired machine has items; this machine or one paired machine), folder, session, and a search over the title, description and session title.
- **Drag a card into another column** to change its state (`boardDrop`): **Open ↔ In progress** marks it (nothing is sent: ▶ Start stays the way to send); **Done** means done (`skipReview`), also for an item with a run; **Review** only for an item with a run session (a refused column is dimmed, the drop does nothing); **Open** reopens. With the mouse a press becomes a drag after 4 px; on a touch screen the card lifts after D74's long press (~400 ms still, 8 px slop; a quick swipe scrolls) and its title follows the finger; the target column lights up. **⋯ → Move to ▸** (Open / In progress / Review (with a run) / Done) does the same without dragging.
- **Phones (≤ 767 px, ruling 2026-10-08): swipeable columns**: the four columns side by side, one per screen width (horizontal scroll snap), under a **tab strip** (the four names and their counts) that follows the swipe and scrolls to a column when tapped; the last column is remembered (`sb.todos.boardColumn`). A card moves with **⋯ → Move to**, or by a **long-press drag onto a tab** (the tab lights up; the drop moves it into that column). A card's ⋯ menu is placed in the window there (the sideways-scrolling strip would clip it) and closes when a scroll moves its ⋯. Tablets and short windows: the board scrolls as a whole (the four columns side by side, sideways inside the board when narrower than four); desktop unchanged.
- Under the board: **Actual vs. estimate (completed)**, one row per session with recorded actuals (below).

## Actual vs. estimate (D78)
- **Time** (`actual_ms`): the item's **in-progress spans**, from its first `in_progress` (`started_first_at`) to `done` or `review`; time back in **open** (and in review, or done) does not count; each span is added when it ends (`span_started_at`). ▶ Start of an item already in progress keeps its span.
- **Tokens** (`actual_tokens`, approximate): the turns of the session **working on it** (its run session's while the run is active, else its own session's) that **ended during a span**: each turn's `result` line's `usage` `input + cache creation + output` tokens (cache reads, the context re-read on every call, are left out; `resultTurnTokens`, recorded on the result event as `tokens`). A turn that began before the span counts whole; a hooked terminal session or a CLI whose result carries no `usage` adds nothing (Codex / OpenCode report none there yet).
- **On the card** (done or in review): `est ~45m · took 32m · 41k tokens` (`took <1m` under a minute; the estimate part only with an estimate, the tokens only when known).
- **Totals:** each Todos page group header shows its completed items' `est ~2h · took 1h 40m · 210k tokens (4 done)` (the estimate compared with the estimated items' time only); the board lists the same per session. They come from **`todo_actuals`** (one row per completed item, kept after the done hour removes the item; a reopened item loses its row until it completes again).
- **Calibration for agents:** `todo_add` / `todo_update` answers and the `todo_list` text end with one line once there are **≥ 3 completed items with estimates**: this session's last 10 (when it has three), else its folder's: `Calibration: your last 10 estimates (this session) were 1.4× too low on average.` (the summed actual time over the summed estimates; within 1.15× either way "about right").

## Quick capture (D81)
Developer rulings 2026-10-08 (`docs/decisions.md` → D81): a todo can be captured in a second (a title, optionally a note), and the session's agent fills in the rest when it is idle.

- **Three ways to capture** (all through `POST /api/sessions/{id}/todos/capture` `{ title, note?, from }`, `src/server/api/todo-capture.ts`, `TodoService.capture`):
  1. **⌘K palette** (`src/web/modals/palette.ts` → `paletteTodoEntries`): typing **`todo <text>`** (any case, a space after `todo`) turns the results into capture targets. In a session the first row is **Add "<text>"** *to <this session>*, then the other open sessions (**Add to <session>**), most recently active first; outside a session the rows are the open sessions to pick, recent first (`captureTargets`). Enter or a click saves it there, closes the palette and shows a toast (**Added to todos**; **Open** when it went to another session). The **Add todo…** action (after New session) types `todo ` for the title; `todo ` alone shows one row asking for the title (nothing to pick). A text over 120 characters (or with a line break) gets a title cut at a word (`captureTitle`) and keeps the whole text as the note. A refusal shows above the results; the palette stays open.
  2. **Select text in the chat → Add to todo** (`src/web/capture/SelectionCapture.tsx`): a selection wholly inside the conversation (a mouse drag, the keyboard, or a touch long-press selection) shows a small floating **＋ Add to todo** under its last line (under, so a touch device's own callout above the selection stays free), centred and kept inside the window, above the selection when there is no room below (`floatPlace`). It waits for the selection to settle (180 ms), hides when the conversation scrolls or the selection goes, and pressing it keeps the selection. It opens a small popover (`role="dialog"`, so Esc there never stops a running turn) with the **title** (generated: the selection's first non-empty line, spaces collapsed, clipped to 80 characters at a word with `…`) and the **description**: the selection as a Markdown quote (`> ` lines, `quoteNote`), both editable; Save (⌘ / Ctrl + Enter) captures it (`from: selection`) and clears the selection; Esc, Cancel or a click outside closes it. Not offered for an unreachable machine's session.
  3. **Phone share sheet** (`docs/devices.md` → *Share to Switchboard (D81)*): on the device origin the app is a Web Share Target; a share opens `/share` (**Add to which session?**, `src/web/capture/SharePage.tsx`): the shared title (editable; else the text's first line, else the link) and the note (the text and the link), the open sessions (this machine's and the paired machines'), recent first; a tap saves it (`from: share`).
- **Saved bare:** the title, the note as the description, plan `No plan`, priority medium, no estimate, added by the developer (`addedBy: developer`), `capturedFrom` = the way, and, when **Settings → Sessions → Let the agent fill in captured todos** (`sessions.todoEnrich`) is on (default), **`needsEnrichment`**. Off: the item stays bare and unmarked (nobody is asked).
- **The card** shows **✎ waiting for the agent to fill in** after its labels while the item is marked (open items only: an item started or done does not show it).
- **The agent fills it in when idle** (`src/server/todos/enricher.ts`, `TodoEnricher`): when the session's agent is idle (status `idle` / `done`: not running, not waiting on the developer) Switchboard sends it **one** message (origin `service`, `todoEnrichMessage`):
  `The developer added todo [<id>] '<title>' (<note if any>). Fill in its description, handover plan, priority and estimate with todo_update — don't start it.`
  Several pending captures go in **one** message (`The developer added todos [<a>] '<A>', [<b>] '<B>' (…). Fill in their description, … — don't start them.`); a note is one line, its `> ` marks removed, cut to 200 characters. Checked at every change of the session's list (so a capture into an idle session asks at once) and every `sessionUpdated` of it while idle; one check at a time per session. Each item is asked **at most once** (`enrich_asked_at`), even if the agent does not fill it in. Not for closed, paused or detached sessions; a **hooked** terminal session only while its waiter is held (else nothing is recorded and a later check asks); a paired machine's session is asked by its own machine (the capture goes there through the peer proxy). A session at `done` without a live process is resumed by the message, like any message.
- **The mark is cleared** by the agent's **`todo_update`** on the item (any field), and by the developer's own edit of the description, plan, priority or estimate (they filled it in themselves; a title-only edit keeps it). Marking it in progress (also the agent's `todo_start`) or done does not clear it, but it shows only on open items and the agent is asked only about open ones.
- **Storage:** migration **0035** (`docs/database.md`): `needs_enrichment`, `captured_from`, `enrich_asked_at`, added with `ALTER TABLE … ADD COLUMN` (no rebuild).
- **Peers and take-over:** the capture route is on `PEER_API_ALLOW` and the devices' allow-list. A paired machine before D81 has no such route: the UI then adds the item the plain way (title and note as the description), bare and unmarked. Items carry `needsEnrichment` / `capturedFrom` to a paired machine's UI; a take-over does not carry the mark (the item arrives bare: ASSUMED D81-takeover).
- **Rules** in `src/core/todo-capture.ts` (pure, shared): `paletteTodoText`, `captureTitle`, `quoteNote`, `sharedCapture`, `todoEnrichMessage`, `captureTargets`, `ENRICH_WAITING_LABEL`.
- **Tests:** `tests/server/todos/capture.test.ts` (0035, the rules, the route, the mark, the enricher, the allow-lists, the share target on both listeners), `tests/web/capture.test.ts` (palette rows, the floating action's place, the selection's bounds), `tests/e2e/capture.spec.ts` (⌘K in and outside a session, the agent's one message and its `todo_update`, the selection popover, the share page at 360 px), `tests/e2e/devices.spec.ts` (the share target on a paired phone).
