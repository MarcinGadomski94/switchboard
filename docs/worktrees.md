# Worktree manager (M2.2)

`src/server/worktrees/manager.ts` (`WorktreeManager`) owns every git worktree Switchboard creates: creation per session and solution, the registry in the `worktrees` table, pull request state through `gh`, the removable flag, removal, the "Move … to worktree" operation and the session diff. The pure rules (naming, diff parsing, gh output, the move message) are in `src/core/worktrees.ts`; D32's ticket branch rules in `src/core/ticket-branch.ts` (*Ticket branches (D32)* below). Gaps #1, #2, #3 and #10 in `docs/decisions.md` are the spec, with D32 on top of gap #1's branch name.

**What it never does.** No `git stash`, `reset`, `checkout`, `switch`, `restore`, `clean`, `commit`, `push`, `pull`, `merge`, `rebase`, `branch -D`, `--force` or `--hard`, in any repository. D40 adds `git fetch origin` (only the remote-tracking refs change) and `git ls-remote --symref origin HEAD`, bounded by their own timeout (*Epic/task branching (D40)* below). D47 adds `git for-each-ref refs/remotes/origin/` (listing origin's branches for a typed parent) and, once a stacked worktree's parent merged, `git merge-base --is-ancestor` (read-only) after a `git fetch origin --prune` (*Stacked task branches (D47)* below). The developer's main checkout is only read (`rev-parse`, `symbolic-ref`, `show-ref`; D38: `worktree list --porcelain`) and gets a sibling folder from `git worktree add`, which does not touch its working tree or index. Every git and gh call is `spawn(cmd, args, { shell: false })` (`src/server/exec.ts`) with `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0` (so `git status` never takes the index lock of a tree someone is working in), and `GH_PROMPT_DISABLED=1`. The tests run git through a logging wrapper and assert that none of the calls above ever happen.

## Which folder a solution is
A solution name resolves **in a folder** (D14, `docs/folders.md`): `resolveRepo(solution, folder)`, where the folder is the session's own (`folderOfSession`: its stored `root` + `root_kind`), never a global root.
- **Workspace folder:** the router layout: a relative path (`other/switchboard`) is taken as is; a bare name is `<root>/<name>` (e.g. `mobile`) or `<root>/<group>/<name>` for `microfrontends`, `nugets`, `microservices`, `functions`, `other`. The folder must be a main checkout: `.git` is a directory. A `.git` file (a worktree or submodule, gap #16) is not a solution, so `web-front-wt-x` never resolves. `deprecated/…` and `infrastructure` are refused as read-only. No match is `solution-not-found`; two matches (e.g. `mobile` and `nugets/mobile`) is `solution-ambiguous`.
- **Repo folder:** its one solution is the repo itself, named after its folder; any other name is `solution-not-found`, and so is a folder that is no longer a main checkout.
- A folder that is gone from disk is `folder-missing` (409).

## Create (gap #1)
`createForSession(name, solutions, folder, sessionId?, { branch? })`, one worktree per solution of that folder:
- branch `{branch}` (D32: the developer's ticket branch, the same in every repo), else `session/{name}` (scheduled runs, teleports), from the repo's **current HEAD commit**, folder `../{repo}-wt-{name}` (a sibling of the repo folder: `microfrontends/web-front-wt-free-talk`, `mobile-wt-free-talk`; always the short name, never the branch): `git worktree add -b <branch> <path> <HEAD sha>`, run in the repo;
- `base_ref` = the branch HEAD was on (`main`, `dev`, …), or the commit itself when HEAD was detached. The diff and the unpushed check use it;
- the row stores `repo` = the solution name as given, `repo_path`, `branch`, `base_ref`, the canonical `path`, `session_id`.

It is all or nothing. Every precondition is checked for every solution before anything is created: the solution resolves, the folder does not exist and is not registered, the repo has a commit, and the branch does not exist yet (an existing branch is never reused, since it may hold someone's work: `409 branch-exists`, "`<repo>` already has a branch `<branch>`", naming the repo that has it; D40: a new session's task branch goes through `createTaskWorktrees` instead, which reuses it, *Epic/task branching (D40)*). A git failure part-way (e.g. a stale ref lock) undoes what the call made: `git worktree remove` (no `--force`) and `git branch -d` of the branch it had just created (safe delete; it points at the HEAD it came from). The rows are marked removed.

**New sessions.** `POST /api/sessions` with `worktrees: true` (D32: and the required ticket `branch`) creates the worktrees **before** the process starts, then `SessionSupervisor.start(…, { beforeSpawn })` links them to the new session id between storing the session and spawning `claude`, so the first tool result can already be attributed to a worktree branch (`docs/derivations.md` → *Artifacts*). In a **workspace** folder the process still runs in the workspace root (ARCHITECTURE: the router applies) and the worktree paths reach the agent in its first message (M5.2); in a **repo** folder (D14) the process runs in the worktree itself and its first message carries only the worktree note. A refusal answers before any session exists: `422 {error:"invalid", errors:[{field:"solutions", …}]}` for a solution that is not a repo or is read-only (D32: `{field:"branch"}` for a missing branch or one that is not a ticket branch), `409 {error:<code>, message}` otherwise (`branch-exists`, `path-exists`, `no-commits`, `git-failed`, `folder-missing`). If the session cannot start after the worktrees were made, they are discarded the same way.

**No solutions picked (D38).** A workspace session started with `solutions: []` (the agent determines them) gets **no worktree up front**, even with `worktrees: true`; the session stores its branch instead (`sessions.branch`: the ticket branch, `session/{name}` for a scheduled run), and its first message tells the agent to create one worktree per solution it changes on that branch at `<repo>-wt-<name>` (`docs/new-session.md` → *First-turn payload*). Those worktrees become the session's by adoption (*Adopted worktrees (D38)* below).

**Teleports (D25).** `POST /api/sessions/teleport` makes a repo folder's worktree the same way (`../{repo}-wt-{name}`, branch `session/{name}` from HEAD: a clean tree for `claude --teleport`), links it before the spawn, and discards it (worktree and `session/{name}` branch) when the teleport is refused. The CLI then fetches and checks out the remote session's branch **in the worktree** (its `git fetch origin <b>:<b>` + `git checkout <b>`; the manager itself still never runs checkout); once the local copy reported its session, `checkedOutBranch(path)` (`git rev-parse --abbrev-ref HEAD`; `null` when detached) gives that branch and it replaces the row's `branch`, so the pull request check (`gh pr view <b>`), the unpushed count and the diff's branch label follow it. `session/{name}` stays in the repo, unused (`docs/supervisor.md` → *Teleport*).

## Epic/task branching (D40)
A new session's worktrees under the ticket rule (`POST /api/sessions` with `worktrees: true` and D32's `branch`, a workspace or a repo folder) follow the epic/task model, **lazily** (`docs/decisions.md` → D40): `WorktreeManager.createTaskWorktrees(name, solutions, folder, { task, branching })`, the rules in `src/core/branching.ts`. Scheduled runs (`session/{name}` from HEAD), teleports and "Move … to worktree" keep `createForSession` unchanged.
- **The model:** `origin/<base>` (default `dev`) → the epic `feature/<KEY>-<Summary>` (`epicBranchName`: the summary's casing kept; developer ruling 2026-09-29: only letters, digits, `-`, `_` and `.` are kept, anything else is a separator, runs of `-` merged, trimmed: `[FE] Login & signup` → `feature/<KEY>-FE-Login-signup`; editable in the form) → the task branch (D32). `NewSession.branching` (additive) carries `{ epic?: { key, summary?, branch? }, base?, bases?, dropped? }`; a body without it is a **task without an epic**.
- **Per repo, planned before anything is made** (all or nothing, like gap #1): the path must be free; an existing local task branch checked out in another worktree is `409 branch-checked-out`; then `git fetch origin` (one network call per repository at a time, `timeouts.fetch`, default 60 s; failure = `409 fetch-failed`, nothing created) and the **cut point** (`cutPoint`): `origin/<epic>` when the epic is on origin, else `origin/<base>` (the repo's override when set); without an epic the override, else the origin default branch (`refs/remotes/origin/HEAD`, else `git ls-remote --symref origin HEAD`). A missing one is `409 base-missing` ("`<repo>`: origin/dev does not exist: drop it from the task or use another base"). Never a local `master`.
- **Creation:** a new task branch `git worktree add --no-track -b <task> <path> refs/remotes/origin/<cut>` (no upstream until the agent's `git push -u`); an existing one is **reused** (replacing D32's `branch-exists` for new sessions): the local branch as it is (`git worktree add <path> <task>`; kept when the start is undone), else `git worktree add --track -b <task> <path> origin/<task>`. The row's `base_ref` is `origin/<cut>`, so the Diff and the unpushed count compare with it; the first message names it (`(branch <task>, from origin/dev)`).
- **A repo without an `origin` remote** is cut from its current HEAD as before (D32), an existing task branch still reused.
- **Dropped repos** (`branching.dropped`) get no worktree and leave `Session.solutions`; the branching is stored (`sessions.branching`, migration 0012).
- **Never** creates the epic branch (locally or on origin) and **never pushes**: the agent does both, only in a repo it changes, at its first change (the Rule line of the answers block, `docs/new-session.md` → *First-turn payload*).
- **Adoption (D38) of a branching session** stores as `base_ref` the origin branch the agent's worktree was cut from by the same rule, read in the worktree itself (no fetch): `origin/<epic>` when present, else `origin/<base>` / the override, without an epic `origin/HEAD`'s branch; else the main worktree's branch as before.
- **Preflight** (`preflight(folder, input)`, `POST /api/branching/preflight`): per repo in parallel, `git fetch origin --prune`, then `origin/<base>` (override / epic base / origin default), the epic on origin and `git rev-list --count origin/<epic>..origin/<base>` (commits it is behind), the task branch on origin and locally, and the cut point; a repo that does not resolve, has no origin or cannot be fetched is a row with its `error`. Nothing is created.
- Tests: `tests/server/worktrees/branching.test.ts` (temp repos cloned from local bare origins: the rows, the cut points, reuse, drops, refusals, nothing pushed, the first message), `tests/core/branching.test.ts`, `tests/e2e/branching.spec.ts`.

## Stacked task branches (D47)
A new session's task may be **stacked** on an earlier, still unmerged task branch, its **parent** (`docs/decisions.md` → D47): `NewSession.branching.parent` (additive), the rules in `src/core/stacking.ts`.
- **The parent** is typed by the developer: a task key (`PROJ-3013`) or a full branch name (a valid git branch name; a leading `origin/` is dropped). Switchboard never lists or searches sibling branches. Validation (`branchingOf`, 422 on `branching.parent`): not the task branch, not the task's own key, not the epic's base; the epic branch itself (or blank) means "not stacked" and is not stored. Stored as `sessions.branching.parent` (the 0012 JSON; absent when not stacked, so D40's rows are unchanged).
- **Per repo** (`#planTask`, after `git fetch origin --prune`): the origin branches (`git for-each-ref refs/remotes/origin/`) the parent names (`parentMatches`: a key → every branch starting with `<KEY>-`, the task branch left out; a name → that branch). `resolveRepoBase`: one match → cut from `origin/<parent>`, PR target the parent; several → `409 parent-ambiguous` ("`<repo>`: PROJ-3013 matches 2 branches on origin (…): type the parent's full branch name"), nothing created; none → D40's cut point (`origin/<epic>` when on origin, else the override or `origin/<base>`; without an epic the override or `origin/HEAD`'s branch), PR target the epic branch (created lazily) or, without an epic, the branch cut from. A repo without `origin` is cut from its HEAD as before (no parent there). Reuse of an existing task branch is D40's.
- **The parent's PR** (`gh pr view <parent> --json number,state,url,baseRefName,headRefOid`, in the repo) is read at Start for each repo that has the parent; a gh failure never blocks the start. The worktree row stores it (migration 0013): `parent_branch`, `parent_pr_number` / `_url` / `_state`, `parent_base` (its `baseRefName`), `parent_head_oid` (gh's `headRefOid`, else the commit `origin/<parent>` was at when the worktree was cut). The row's `base_ref` is `origin/<parent>`.
- **The first message** carries the stacked Branching lines (`stackedLines` via `handoffLines`; `docs/new-session.md` → *First-turn payload*), with each repo's resolved base and PR target and the parent's PR states.
- **Adoption (D38)** of a stacked session: a worktree whose repo has exactly one matching origin branch (read in the worktree, no fetch) gets `base_ref` `origin/<parent>` and `parent_branch`; its PR is read by the next poll.
- **Preflight** (`POST /api/branching/preflight` with `parent`): always `git fetch origin --prune`; each row gains `parent` (`typed`, `branch`, `matches`, `error` for several matches, the parent's `pr` / `noPr` / `prError` from gh, asked only where the parent is on origin) and `prTarget`; `cutFrom` is `origin/<parent>` where it is found. Non-stacked rows carry `parent: null` and the D40 `prTarget`.
- **When the parent merges (rule 5):** `checkPullRequests` also runs `gh pr view <parent_branch> --json number,state,url,baseRefName,headRefOid` for every live row with `parent_branch` and no `parent_merged_at`, stores what it reports (no PR or a gh failure changes nothing), and when the state is `MERGED` with a known base: `git fetch origin --prune`, then `git merge-base --is-ancestor <parent_head_oid> origin/<parent_base>` → `parent_merge` `merge` (exit 0) / `squash` (exit 1) / `unknown` (fetch failed, commit unknown); `parent_merged_at` is set and `base_ref` becomes `origin/<parent_base>` (where the branch is rebased to). `onParentMerged` listeners fire once per row. `SystemItemService` (`src/server/inbox/system-items.ts`) turns that into the **Parent … merged** Inbox item (kind `parent-merged`, one per worktree, open or closed; `sync()` also raises it for rows it missed) and, only when it raised the item and the session is not closed, sends the session `parentMergedMessage` through the supervisor (`sendMessage`, origin `service`: a paused session is resumed); when that is refused (the session continues in a terminal, the service is closing) the message waits in its outbox (`pending_messages` kind `parent-merged`). A closed session gets only the item, whose detail says so. Switchboard itself never runs `gh pr edit`, a rebase or a push.
- Tests: `tests/core/stacking.test.ts`, `tests/server/worktrees/stacking.test.ts` (temp repos cloned from local bare origins; fake-gh per-repo PRs: the preflight columns, cut points, refusals, nothing pushed, the hand-off, squash and merge-commit merges, the item and message once, a closed session), `tests/server/inbox/parent-merged.test.ts` (sync, outbox fallback, closed), `tests/web/branching-form.test.ts`, `tests/e2e/stacked-branches.spec.ts`.

## Adopted worktrees (D38)
A worktree the session's **agent** created itself (D38: a session started without picked solutions, told to `git worktree add -b <branch> <repo parent>/<repo>-wt-<name>`) is registered as the session's exactly like one `createForSession` made: the same `worktrees` row with `session_id` set, so the Diff tab, the pull request checks, removal (gap #3) and the Solutions view's branch chips follow it.
- **When** (`WorktreeAdoption`, `src/server/worktrees/adopt.ts`, created by `buildApp` next to the loop tracker; it listens to the supervisor's `event` notifications):
  - right after a **main-agent** `Bash` tool result without an error whose command adds a worktree (`addsWorktree` in `src/core/derive/artifacts.ts`: it contains `git worktree add`, or a statement is `git [-C <dir>] [-c <k=v>] [--opt…] worktree add …`; a subagent's command waits for the sweep);
  - on a **sweep at each turn's end** (every `result` event) while the session (Worktrees on) names a solution in `Session.solutions` that has no worktree of the session yet (`sameSolution`: a name and its relative path match).
  Workspace sessions only (a repo folder's worktree is made up front, D14). Runs asynchronously, one adoption at a time (the manager serializes them across sessions, since two sessions may share a branch).
- **What** (`WorktreeManager.adopt(session, repos)`): the repositories are the folder's writable solutions that are, or hold, a git main checkout (`WorkspaceScanner`, `scannedRepos`). In each (once per canonical path) it runs `git worktree list --porcelain` **in the main checkout, the only git call made there** (read-only; `parseWorktreeList` in `src/core/worktrees.ts`) and adopts every other listed worktree that is on a branch (not detached, not bare, not `prunable`) and whose **branch is the session's** (`sessions.branch`) **or whose folder is `<repo>-wt-<name>`** (`<repo>` = the repository's folder name or the solution's name, `<name>` = the session's short name; `isSessionWorktree`). A path that already has a live row (the session's own, an up-front one, or **another session's**) is never registered again or taken over, so every call is idempotent.
- **The row:** `repo` = the solution's name (`web-front`, `mobile`), `repo_path` / `path` canonical, `branch` = the listed branch, `base_ref` = the main worktree's branch at that moment (else its commit), `session_id` = the session. Then `SessionSupervisor.addSolutions` adds the solution to `Session.solutions` (if missing) and publishes `sessionUpdated` either way, so the Diff tab and the Solutions view reload (`docs/derivations.md` → *Session solutions (D38)*).
- A repository git cannot list is skipped (reported through `onError`); nothing is ever created, moved or removed by an adoption.
- Tests: `tests/server/worktrees/adopt.test.ts` (the triggers), `tests/server/sessions/agent-solutions.test.ts` (real git: the sweep and a `git worktree add` by the fake, the row, the Diff, idempotence, another session's worktree untouched, only `worktree list` in the main checkout), `tests/core/session-solutions.test.ts` (parsing and matching), `tests/e2e/agent-solutions.spec.ts` (real path through the UI).

## Isolate (gap #2)
`isolate(repo, sessionId, { branch? })`, served as `POST /api/solutions/{repo}/isolate` `{ sessionId, branch }` → `Worktree` (201 when created). D32: the route requires `branch`, a ticket branch (422 on field `branch` before anything else happens; the UI asks for it in the card's confirm step, `docs/solutions.md` → *Conflicts*). It:
1. refuses an unknown session (404 `session-not-found`) and a detached one (409 `detached`, the terminal owns it) before anything is created;
2. returns the session's existing live worktree for that repo unchanged (200, nothing else happens), so a double click cannot pause the session twice;
3. creates the worktree exactly as above (on `{branch}` from the repo's current HEAD, folder `../{repo}-wt-{session name}`; `repo` resolved in the session's own folder, D14; a branch the repo has already is `409 branch-exists` and nothing is paused), linked to the session;
4. pauses the session when it has a live process (the D7 stop), then sends the move message through `SessionSupervisor.sendMessage`, which resumes it with `--resume <id>` and that message instead of "Continue.". A session with no live process (paused, failed) is resumed the same way.

The move message (`moveToWorktreeMessage`) names the worktree path, the branch and its base, tells the agent to make every further change there, and says that what it already changed in the main checkout was left in place: it should re-apply what it still needs inside the worktree (e.g. by copying the files it edited) and never stash, reset or check out anything in the developer's tree. Switchboard itself moves no files. If the message cannot be sent (the service is closing), the worktree stays registered and the route answers the supervisor's error.

## Ticket branches (D32)
Whenever the developer creates a worktree (a new session with Worktree on, in a workspace or a repo folder, or "Move … to worktree"), they name its branch after the ticket: `src/core/ticket-branch.ts`.
- **The rule:** `TICKET_BRANCH = /^[A-Z][A-Z0-9]*-[0-9]+-[a-z0-9]+(?:-[a-z0-9]+)*$/`: the Jira-style key (upper case), its number and a kebab-case description, with no `session/` prefix (`PROJ-0001-test-branch-name`, `PROJD-0001-test-ticket-name`). Any such name is a valid git ref (no `/`, `.`, `@{`, spaces).
- **`checkTicketBranch(value)`** → `{ ok: true, name }` (trimmed) or `{ ok: false, message }`: missing or blank → `BRANCH_REQUIRED` ("name the branch after its ticket: the key, its number and a short description, e.g. PROJ-0001-short-description"), anything else → `BRANCH_RULE` ("the branch must be a ticket key, its number and a short kebab-case description, e.g. PROJ-0001-short-description"). The server checks exactly what it gets (trimmed, never tidied): these are its 422 messages on field `branch`.
- **`tidyTicketBranch(text)`** (the UI, on blur): trimmed, accents dropped, each run of anything but a letter or a digit one `-`, none at either end; when the text starts with a key and a number (`proj-1984`, `PROJ 1984`), the key is upper-cased and the rest lower-cased: `proj-1984 Purchase Complete!` → `PROJ-1984-purchase-complete`. Text without a key keeps its letters' case (it is not a ticket branch either way, and the check says why).
- **`branchFromTitle(title)`**: the tidied title when it starts with an upper-case ticket key and its number (leading brackets or spaces allowed: `[PROJ-12] Fix` → `PROJ-12-fix`), else `null`. `PROJ-1984 Purchase complete` → `PROJ-1984-purchase-complete`; a title that is only a key gives the key (`PROJ-1984`: the field then says what is missing). A lower-case start (`mobile-360 layout`, a kebab session name) suggests nothing.
- **Where:** `NewSession.branch` / `NewRepoSession.branch` (required with `worktrees: true`, not read without; `src/server/sessions/validate.ts`, rule `ticket`) and `IsolateRequest.branch` (`src/server/api/solutions.ts`). The worktree record stores the branch, so everything that shows it (the answers block and the repo worktree note of the first message, the move message, the Diff tab, Solutions' branch chips and cards, Artifacts, the right panel, toasts, the "PR merged" Inbox item, the pull request check `gh pr view <branch>`) names the ticket branch without further change.
- **Unchanged:** the worktree folder (`../{repo}-wt-{name}`, the short name), scheduled runs (`startNewSession(…, { worktreeBranch: 'session' })`: every run gets its own `session/{run name}`; a schedule template's `branch` is dropped when it is saved) and teleports (D25: `session/{name}`, then the CLI checks out the remote branch).

## Remove (gap #3)
`remove(worktreeId)` (the Inbox "Remove worktree" action, M3.3):
- **uncommitted** = any line of `git status --porcelain --untracked-files=all` in the worktree (modified, staged or untracked) → refused, `409 uncommitted`;
- **unpushed** = commits reachable from the worktree's HEAD or its branch that are on no remote-tracking ref, not on its upstream, not on the base branch (`base_ref`) and not on the PR's head commit: `git rev-list --count HEAD refs/heads/<branch> --not --remotes <base> <upstream> <PR head>` > 0 → refused, `409 unpushed`. The PR head (`headRefOid` from `gh pr view <number>`) is only asked for when the rest says "unpushed" and the row has a PR number: after a squash merge GitHub may delete the remote branch and a `fetch --prune` drops `origin/<branch>`, but the commits are on GitHub as the PR head. Commits that were already on the base branch when the worktree was made are the developer's, not the session's, so they never count;
- otherwise `git worktree remove <path>` (never `--force`; git itself also refuses a dirty or locked worktree) in the repo, and the row gets `removed_at`. **The branch is kept.** A worktree folder that was deleted by hand just leaves the registry (no git call).

`inspect(worktreeId)` returns the same numbers without removing anything.

## Pull requests and "removable"
`checkPullRequests()` runs `gh pr view <branch> --json number,state,url,headRefOid` (`SWITCHBOARD_GH_BIN`) in each live worktree (in the repo when the folder is gone; D47: a stacked worktree's parent PR too, *Stacked task branches (D47)*):
- a PR: `pr_number`, `pr_url`, `pr_state` **verbatim** (`OPEN`, `CLOSED`, `MERGED`) and `pr_checked_at` are stored; PR artifacts with the same URL get the lower-cased state as their meta (`open`, `merged`: the prototype's Artifacts column);
- gh's `no pull requests found`: only `pr_checked_at` changes (earlier PR data is never erased);
- any other gh failure (not signed in, offline, unexpected output): the row is left as it was and the result carries the error.

`removable` = the PR is `MERGED` **and** removal would be allowed right now (no uncommitted changes, nothing unpushed, the PR head counted as pushed), or the folder is already gone. It is re-evaluated on every check, so a leftover file keeps it off until it is gone. When it turns on, the manager emits `worktreeRemovable` with the contract's `Worktree` payload, once per transition: M2.3 forwards it on `/hub`, M3.3 turns it into the "PR merged" Inbox item whose "Remove worktree" action calls `remove`. `CLOSED` is never removable (whether abandoned work can go is the developer's call).

The real service (`src/server/main.ts`, not in demo mode) polls: first check 15 s after start, then every 5 minutes (`startPolling`), one run at a time (a manual `checkPullRequests()` during a run shares it), stopped before the database closes. Only registered worktrees are checked, so an install without worktrees never runs gh.

## Diff (gap #10)
`WorktreeManager` is the real `DiffProvider` (`providers.diff`, wired in `main.ts`; `SessionDetail.files` uses it, M4.5 serves `GET /api/sessions/{id}/diff`). For a session:
- each live worktree: against the **merge-base of `base_ref` and the worktree's HEAD**, so commits the base branch gets later are not in it, while the session's commits, staged and unstaged changes are. If `base_ref` no longer resolves, only the uncommitted changes (against HEAD) are shown;
- each solution in scope without a worktree (in place): against **HEAD** of its main checkout, resolved in the session's own folder (D14; a session without a folder has no in-place targets) (uncommitted changes only; in place they may include the developer's own edits, which is what gap #10 asks for). A solution that does not resolve to a repo is skipped;
- **untracked** files (`git ls-files --others --exclude-standard`) are listed as new files with every line added; binary content (a NUL byte in the first 8000 bytes, git's rule) and files over 1 MiB get no lines; a symlink shows its target.

**Uncommitted flag (M4.5).** Each `FileDiff` carries `uncommitted`: `true` while the working tree or index still changes the file compared with HEAD (`git diff --name-only -z --no-renames HEAD`), or the file is untracked; `false` when all of its changes are in commits of the session branch (a worktree diff against the merge-base lists those too). An in-place diff is against HEAD, so every file there is uncommitted; so is every file of a worktree whose branch has no commits yet. The Diff tab shows "Not committed. Commit only when you approve." while the selected file is uncommitted (`docs/derivations.md` → *Diff tab*).

**Route (M4.5).** `GET /api/sessions/{id}/diff[?file=<path>]` (contract) returns `providers.diff.diff(id, file)`: 404 `{error:"not-found"}` for an unknown session, 422 `{error:"invalid", errors:[{field:"file"}]}` when `file` is empty, repeated, absolute, a drive path, contains NUL or a `..` segment, and `[]` without a diff provider. `file` is one solution-relative path as `FileDiff.path` names it; with several solutions it can match one file in each.

`git diff` runs with `--no-color --no-ext-diff --no-textconv --no-renames --src-prefix=a/ --dst-prefix=b/` and `core.quotePath=false`, so user config (external diff tools, `diff.noprefix`, colors) cannot change the output. A rename shows as a deletion plus an addition. `FileDiff.lines` keeps only hunk body lines (`+`, `-`, space); the `@@` headers and `\ No newline at end of file` markers are dropped (the provisional wire type); a trailing CR is cut. `file` narrows to one solution-relative path (a literal pathspec). Files are sorted by path per solution; `branch` = the worktree branch, or the current branch of an in-place checkout (`null` when detached).

## Fake gh (tests)
`tools/fake-gh/main.ts`, started through `fakeGhCommand()` / `fakeGhBinEnv()` (`tools/fake-gh/command.ts`) like fake-claude. It answers `--version`, `auth status` (exit 1 with gh's signed-out text when `FAKE_GH_SIGNED_OUT=1`, for M5.3) and `pr view [<branch>|<number>] --json <fields>` from the JSON file in `FAKE_GH_PRS` (`{"<branch or number>": {number, state, url, headRefOid}}`, re-read per call; no entry → `no pull requests found for branch "<b>"`, exit 1; D47: a key `<repo>:<branch>`, where `<repo>` is the folder name of the cwd's repository (its main checkout, also from a worktree), wins over `<branch>`, so each repo can have its own PR for one branch name; fields such as `baseRefName` are printed when asked for). `FAKE_GH_FAIL=<text>` fails every `pr` call with that text; `FAKE_GH_LOG=<file>` logs `{argv, cwd}` per call. Anything else exits 1.

`tests/helpers/git.ts` builds a temp workspace (its `folder` is the `FolderRef` the manager resolves in) with real repos (`microfrontends/web-front` with a bare `origin`, `mobile` without a remote) and an isolated git environment (`GIT_CONFIG_GLOBAL` = an empty temp file, `GIT_CONFIG_NOSYSTEM=1`, a fixed author), so the developer's git config and hooks never apply. `tests/helpers/git-spy.ts` wraps git to log every call.
