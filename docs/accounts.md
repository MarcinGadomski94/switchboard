# CLI accounts and automatic switching on usage limits (D63)

Each CLI (Claude Code, Codex CLI, OpenCode) can have **more than one subscription login**, called an **account profile**. When a session hits its **session (5-hour) or weekly limit**, Switchboard moves it to the next account that still has allowance and it carries on, in the same chat and folder. Everything is controlled in **Settings → Accounts**; signing in and out is done from the same page. Switchboard never reads, stores or logs a token: the sign-in is the CLI's own (`docs/security.md` → *Accounts*).

Built from the CLIs' own behaviour (Claude Code 2.1.285 read from its binary; Codex and OpenCode from their source / OpenAPI, as D62), never against a real login: tests drive the fakes (`docs/fake-claude.md`, `docs/fake-codex.md`, `docs/fake-opencode.md` → *Accounts*). `docs/spike-providers.md` lists the probes to run with real accounts.

## Profiles
- **Default** (one per CLI, built in): the developer's own login, no folder override (the CLI's own `~/.claude`, `~/.codex`, OpenCode's data). It can be ordered, enabled / disabled and checked here, and renamed (D67: its name is only a label; it stays the built-in account, and the hints that mention it use its current name), but **not signed in or out or deleted** here: it is the developer's own login, managed in a terminal (ASSUMED D63-default-readonly). Its folder is never touched or deleted.
- **Other profiles** (Add account): a name (1–40 characters, unique per CLI) and a folder Switchboard creates, `<dataDir>/profiles/<cli>/<id>` (mode 0700). A process of the profile runs with the folder in its environment: `CLAUDE_CONFIG_DIR` (Claude Code), `CODEX_HOME` (Codex), `XDG_DATA_HOME` (OpenCode: its data folder is `<dir>/opencode`; its *config* in `~/.config/opencode` is shared by itself, ASSUMED D63-opencode-data).
- Why a folder per account works on Claude Code: **VERIFIED** (2.1.285 binary, read-only) with `CLAUDE_CONFIG_DIR` set, the macOS Keychain service name carries a suffix `-<first 8 hex of sha256(config dir, NFC)>` (`CLAUDE_SECURESTORAGE_CONFIG_DIR` overrides the folder used for the hash), so each folder holds its own subscription login; transcripts live under `<config dir>/projects/<cwd slug>/<session id>.jsonl`.
- **Priority order** per CLI (↑ ↓ buttons or drag and drop); **Enabled** toggle (a disabled profile is never a target and cannot be picked for a new session); **Delete** (confirm; refused for a Default or while a process runs on it; its sessions go back to the Default; its folder stays unless "Delete and remove its folder", and only a folder inside `<dataDir>/profiles/` is ever removed; its login is not signed out; a paused session whose conversation lives only in that folder should be switched to another account first, ASSUMED D63-delete).
- **Status** per profile: signed in / signed out / unknown with the account the CLI reports (Claude Code: `claude auth status --json` → email and plan; Codex: the line of `codex login status`; OpenCode: the credentials count of `auth list`; a non-Default OpenCode profile with none is signed out), the latest usage reading (`5h 62% · week 10%`, windows that have not reset), when it is spent ("Out of usage until 14:05 (session limit)") and how many open sessions run on it. **Check** (and **Check all**) runs the status commands again (cached 60 s otherwise).

### Sharing the Default's settings
Option per profile, **on by default** (a switched session must behave like the one before; ASSUMED D63-share-default-on). `src/server/accounts/share.ts`:

| CLI | Shared from the Default's folder (symlink; a copy where links are refused) | Never |
|---|---|---|
| Claude Code | `settings.json`, `CLAUDE.md`, `agents/`, `commands/`, `skills/`, `keybindings.json`; the user-level **MCP servers**: only the `mcpServers` key of `<config dir>/.claude.json` is **merged** into the profile's own `.claude.json` (the profile's own servers win) | `.credentials.json`, `projects/`, the account identity in `.claude.json`, anything else |
| Codex | `config.toml` (its `[mcp_servers]` too), `AGENTS.md`, `prompts/`, `skills/` | `auth.json`, `sessions/` |
| OpenCode | nothing to link: only the data folder is overridden, its config is shared already | its `auth.json`, SQLite store |

Existing files in the profile are never overwritten; turning the option on later links what is missing; `POST …/sync-settings` does it again after the Default changed. (Symlinks are followed by the CLIs; the MCP merge is a copy, so a server added to the Default later needs a sync.)

## Signing in and out from Settings
`src/server/accounts/signin.ts` → `SignInManager`; routes below. Sign-in runs the CLI's **own** login with the profile's folder in the environment:

| CLI | Sign in | Sign out |
|---|---|---|
| Claude Code | `claude auth login --claudeai [--email <optional email field>]` (**VERIFIED** options; output lines "Opening browser to sign in…", "If the browser didn't open, visit: <url>", "Paste code here if prompted > ", then "Login successful.") | `claude auth logout` |
| Codex | `codex login`; the **use a device code** checkbox adds `--device-auth` (the one-time code is shown with the verification page) | `codex logout` |
| OpenCode | an `opencode serve` on the profile's data folder and its provider OAuth routes (**VERIFIED** OpenAPI v1.18.34: `GET /provider/auth`, `POST /provider/{id}/oauth/authorize` → `{url, method: auto \| code, instructions}`, `POST /provider/{id}/oauth/callback`); or an **API key** field for providers that use keys (`PUT /auth/{id}` to that server only: never stored or logged) | the same server: `DELETE /auth/{id}` for every connected provider |

- **The page opens in a new tab** (D61's pattern): the click opens `about:blank`, the server answers with the URL the CLI printed (the first page URL that is not the CLI's own `http://localhost:<port>` callback server), the tab is pointed at it; the panel also keeps an "Open the sign-in page again" link. `BROWSER=true` is set on the login process so the CLI does not open a second tab by itself (best effort, ASSUMED D63-browser-env).
- **Progress and completion:** "Finish the sign-in in the tab that opened"; the page polls the sign-in every second; completion is **the CLI's status command** (every 2 s; for a re-sign-in of an account that was already signed in, the CLI's exit instead), or the login's exit 0 checked against the status. A signed-out answer after exit 0 is a failure.
- **5-minute limit:** then the login is stopped and the panel says "The sign-in was not finished in 5 minutes", with the terminal command and **Copy terminal command** (`CLAUDE_CONFIG_DIR=<dir> claude auth login --claudeai`, `CODEX_HOME=<dir> codex login`, `XDG_DATA_HOME=<dir> opencode auth login`), then **Check**. The command is shown from the start of the sign-in too.
- **A paired machine's profiles** (the page's *Machine* picker, through the D48 peer API): the login runs on that machine, the tab opens here, and when the browser cannot reach that machine's localhost callback the panel offers the **paste-back**: the address the browser ended on (a `http://localhost:…` redirect, delivered to the CLI's callback server **from that machine**; only loopback URLs are ever fetched) or the code (written to the CLI's stdin, or to OpenCode's `code` callback); Codex's device code needs no paste. (ASSUMED D63-paste-back: Claude Code takes the pasted code at its "Paste code here" prompt as printed; the redirect-URL delivery is the same path for Claude Code and Codex.)
- **Sign out** asks first, then runs the CLI's logout for that profile and checks the status again.

## Rules (all in Settings → Accounts)
Stored in the `accounts.settings` setting (`src/core/accounts.ts` → `AccountSettings`):

| Rule | Default |
|---|---|
| Switch accounts automatically (master) and per CLI | on, on (ASSUMED D63-defaults: adding a second account is the opt-in; a single login is never touched, see *Dormant*) |
| Switch earlier, before the limit error: **5-hour %** and **weekly %** (separate), on / off | on, 98 % and 98 % |
| After a reset: *Stay on the current account* or *Switch back to the first account* (an idle session on a lower-priority account returns to a higher one that has allowance again) | stay |
| ~~New sessions start on: *the first account with allowance* or *a fixed account* (per CLI)~~ D138: replaced by **Account for sessions** (the overall choice, *Choosing the account*); a stored fixed account reads as the choice | Automatic |
| When every account of a CLI is out of usage: *Stop and notify* (an Inbox item) or *Switch to another CLI* (the D62 handover, CLI chosen) | stop and notify |
| Cooldown between two threshold / reset switches of one session (seconds; API only) | 120 |
| D103: When every account is out of allowance: *Use credits* or *Pause new turns until an account resets* (*Credits (D103)*) | use credits |

**The decision** is the pure `decideAccountSwitch` (`src/core/accounts.ts`, tested exhaustively in `tests/core/accounts.test.ts`):
- **limit error** (always acts, cooldown or not): the profile is marked **spent until its reset** and the session goes to the first *other* profile with allowance (enabled, not signed out, not spent, under the thresholds; failing that just under 100 %); none left → the "every account is out of usage" rule;
- **threshold**: the profile is past a threshold → a profile under the thresholds, never a stop; nothing happens when there is none (the real limit error is the next trigger);
- **reset**: only for "switch back", only for an idle session;
- a **pinned** session never switches (a limit error still marks its profile and raises an Inbox item saying the session is pinned); toggles off → nothing;
- **no loops**: a profile known spent is never a target until its reset, and the periodic switches keep the cooldown.

**Limit detection** (`parseLimitError`): the **CLI's own error text** of a failed turn, plus the usage readings for the thresholds. Claude Code: "You've hit your session limit · resets 2pm" / "… weekly limit …" / "… Opus limit …" (**VERIFIED** strings in the 2.1.285 binary; its own `rate_limit` error kind); a monthly-spend, team-budget or credits message is *not* a plan limit and is left alone. Codex: "You've hit your usage limit … try again at …" (`usage_limit_reached`). OpenCode reports no plan windows, only the provider's 429 / quota error (ASSUMED D63-oc-limit). The **reset time** is read when the text has one ("resets 2pm", "resets Oct 5, 9am", "try again at 3:20 PM", "in 3 hours"; a time of day is read in this machine's zone, the next such time: ASSUMED D63-reset-zone); otherwise the usage reading's reset, otherwise a fallback by window (session 5 h, weekly 24 h, unknown 1 h: ASSUMED D63-reset-fallback).

**Dormant:** a CLI with a single enabled account is never touched: no marks, no switches, no Inbox items (unless "Switch to another CLI" is the rule, which then also works for a single login). The 30-second periodic check (thresholds, resets) runs only for live sessions and reads each profile's sign-in status first (cached 60 s), so a profile that is signed out is never a target.

**Every switch** is logged (`switchboard accounts: <session> switched account (<reason>)`), shown in the chat as a divider, and a **failed** switch (or "every account spent", or a pinned session at its limit) raises an **Inbox item** ("Could not switch the account of …", "Every Claude Code account is out of usage"; dismiss-only, once per session and reset).

## Per session
- **New-session forms** (Simple and Full): an **Account** select next to the CLI choice, shown when the CLI has more than one enabled account ("Account: automatic" = the rule, D138: the overall choice first; a spent account is listed marked, it can still be picked). `NewSession.profileId` (422 for another CLI's, disabled or unknown profile).
- **Header:** the account the session runs on, as a picker (**Switch account**: asks first, then the switch), and a **Pin** toggle (aria-pressed) that stops automatic switching for the session. Shown when the CLI has more than one account. While a switch runs: "Switching account…" (`Session.accountSwitching`); messages, Resume and Attach answer 409 `switching`.
- The session's profile is `sessions.profile_id` (NULL = the Default of its CLI); `GET /api/sessions` carries `profileId`, `profileName`, `profilePinned`. A mid-session **CLI** switch (D62) picks the new CLI's profile by the rule and clears the pin.

## Switching (`SessionSupervisor.switchAccount`)
Stop the process (D7's stop: interrupt, EOF, exit), **copy (never move)** the CLI's own conversation to the new profile's folder, record the new profile, spawn with the new folder, record the divider **"Switched account: A → B (session limit, resets 14:05)"** (lifecycle action `account-switched`, `fromProfile`, `toProfile`, `reason`):
- **Claude Code:** `projects/<cwd slug>/<id>.jsonl` and the `projects/<cwd slug>/<id>/` folder (subagents, tool results) are copied from the old folder to the new one, then `--resume <id>` with the new `CLAUDE_CONFIG_DIR`. The original stays (the old profile can resume it).
- **Codex:** the thread's rollout file is copied to the same `sessions/YYYY/MM/DD/` place under the new `CODEX_HOME` and `thread/resume` follows (**ASSUMED D63-codex-resume**: resume reads the rollout by thread id from its own home; unverified). If the copy fails, the D62 handover inside Codex is the fallback.
- **OpenCode:** its storage (SQLite) is not safely copyable: the D62 handover inside OpenCode (the chat exported under `<dataDir>/handovers/<session>/…-opencode-to-opencode.md`, a **new** OpenCode session on the new data folder reads it first).
- **A conversation that cannot be carried over** (any CLI) takes the same handover path (Claude Code starts a fresh conversation with the session's id and reads the exported chat), with a note in the chat saying why.
- **The interrupted turn is lost** (the turn the limit ended, or one the switch stopped): after the resume the session gets a short service message, "Continue where you left off: the account changed because of a usage limit, and the turn that was running was interrupted." (ASSUMED D63-continue; nothing is sent after a switch of an idle session or of a paused one).
- A **paused** session only changes profile (the divider is recorded, nothing starts; the next resume runs on the new profile). A switch that fails records an error step, brings the session back up on the account it had and leaves it there.

## Usage per account
- Claude Code readings carry their profile (`usage_readings.profile_id`; every earlier reading is the Default's). `UsageMeter` reads each enabled profile: a **live session of it between turns** answers `get_usage` (≤ 1 per minute); a profile with no live session is read by the **poller** with its `CLAUDE_CONFIG_DIR` (≤ 1 per 5 minutes, only while a `/hub` client is connected, as D17); `rate_limit_event`s of its turns bring free readings. One reading per tick.
- The meter's bars (`usagePct`, `usageWindows`) are the **active account's** (the one a new session would start on: the first with allowance, else the first enabled).
- **D66: the footer's usage grid** shows **one line per account**: a small `5h` / `Week` header, then per line a `●` on the active account (only while its CLI has more than one), the label (a Claude Code account by its profile name, another CLI's by its short label and the account's name: `Codex Work`; developer ruling 2026-10-04: also with a single account, `Default`), and a mini-bar with its % for the 5-hour and the weekly window (`—` while unknown). A spent account shows "out until 14:05" across its bars. The line's tooltip has each window's reset, the pace (Claude Code accounts keep D23 / D46's colors and marker on their bars) and each model's weekly limit in use. A click opens Settings → Accounts. Lines all have one height; with a single account overall the grid is one line.
- Where the lines come from: `SystemInfo.accountUsage` (only while a CLI has more than one enabled account), each row with its own `windows` (D66, additive): a Claude Code profile's from its own readings through the meter (`UsageMeter.profileWindows`: Session, Week and the model limits in use, read like `usageWindows`), a Codex profile's from the windows its sessions' bridges reported (`recordProviderUsage`); the active Claude Code account's bars are `usageWindows`. A CLI with a single account gets one line instead, named after it by `SystemInfo.activeAccounts` (`{ cli, profileId, name }` per CLI, sent also with one account; "Claude" / "Codex" while unknown, e.g. in demo mode): Claude Code from `usageWindows` (always listed), Codex from `cliUsage` (its windows carry `key`: `session` / `week`) while it has any. Every enabled account of a CLI with several has a line, `—` for a window that is unknown (ruling 2026-10-04); OpenCode reports no limits, so it has no line.

## Shared across paired machines (D98)
Developer request (2026-10-13): with Switchboards paired (D48, `docs/peers.md`), the accounts are shared between them, and the same account on two machines is merged. Ruling: `docs/decisions.md` → D98; choices: `.loop/questions.md` → *D98 · Accounts shared across paired machines*. Code: `src/core/shared-accounts.ts` (pure: identity, merge, prefs), `src/server/accounts/shared.ts` (`SharedAccounts`, the exchange), `AccountService` (`identityOf`, the merged `list` / `snapshots`), `src/server/usage/wire.ts` (the footer rows), Settings → Accounts.

- **Never credentials.** Only names, the identity the CLI reports, usage readings and spent marks travel. No `.credentials.json`, token, `auth.json` or config folder; each machine signs in on its own.
- **Identity** (`accountIdentity`): what the CLI's status says about the login. **Claude Code:** the email of `claude auth status --json` (`claude:<email>`, lower case; the plan is only shown). **Codex:** `codex login status` says only how it is signed in ("Logged in using ChatGPT", read on codex-cli 0.160.0): too weak to tell two accounts apart, so Codex accounts are **never merged** (ASSUMED D98-codex-identity). **OpenCode:** no identity, never merged. Each profile's last identity is kept in the setting `accounts.identities` (a sign-out forgets it, an unknown answer keeps it), so it is known after a restart without running the status command.
- **The exchange** (`POST /api/accounts/shared`, on the peer allow-list): every 30 s, at once when a machine comes online, and 300 ms after a local change (a rename, a reorder, a spent mark, a profile added / removed / enabled, an identity learned), each **online** paired machine gets this machine's accounts (its own facts only) and shared prefs, and answers with its own. Both ends keep the other's accounts (in memory, last known) and merge the prefs. Before the first exchange each enabled Claude Code profile whose identity is not known yet is checked once. An unreachable machine is simply not asked (10 s limit), never blocking anything.
- **Same account = one row.** A profile with the same identity as an account on a connected paired machine is shown once: Settings → Accounts says "Same account on Desk + Studio · its name, order and usage are shared" (`AccountProfile.elsewhere`), the footer grid has one line with both machines (`docs/usage.md` → *Shared across paired machines*). Its usage is the **newest reading from any machine** (`usageFrom` names the machine; "5h 62% · week 10% (from Studio)"), because the limits belong to the account. A different identity, or none, is its own row; a paired machine's account that is not here is listed under **On other machines** in Settings → Accounts (read-only: name, account, machines, usage, spent; **Manage on <machine>** opens it in the *Machine* picker) and as a footer line (only when signed in there, and for Codex with a known window). A machine that is away drops out of both lists.
- **Names and order** (setting `accounts.shared`: `{ names: { [identity]: { name, at } }, order: { [cli]: { identities, at } } }`): a rename here records the account's name with the time; a reorder records the CLI's identities in the new order. Merging is **last writer wins** per identity's name and per CLI's order (equal times: by value, the same on both ends). A name or order that came from the other machine is applied to the same accounts here directly (no new time, so nothing echoes): a rename, unless another account of that CLI here already has the name (kept, logged); an order moves only the accounts both machines have, among their own slots, every other account keeps its place (`applySharedOrder`). Nothing is applied until someone renames or reorders after D98 (ASSUMED D98-first-merge).
- **Limits across machines.** A spent mark (a limit error) on one machine reaches the others with the next exchange (300 ms after it is set), and so does a reading at the limit (with the next exchange, at most 30 s): `AccountService.snapshots` gives the switcher the latest "spent until" of the account from any machine and its newest reading, so the automatic switcher (*Rules*) skips it until that reset, a new session starts on another account, and a live session on it is moved by the periodic check before a turn fails on it (the threshold check now moves a session off an account known spent, to one with allowance, also with early switching off; never a stop). A spent mark of a machine that went away still counts until its reset (it is the account's). Settings shows it as "Out of usage until 14:05 (session limit, found on Studio)".
- **An older peer** (a Switchboard before D98) answers 403 `peer-forbidden` to the exchange: its accounts are read with `GET /api/accounts` instead (allow-listed since D63) and shown **unmerged** (no identity is taken from it, nothing is applied from it), labelled with its machine. It keeps working as before.
- **A paired machine's request** (`GET /api/accounts` through the Machine picker) answers that machine's own facts only (no merge, no other machines): no chains.
- **Limits:** the shared data is kept in memory (a restart starts empty until the first exchange); live changes need the other machine's listener on (each sends over its own outbound connection; without it, a machine's changes arrive when the other one asks, at most 30 s later). Names and order of Codex / OpenCode accounts are not shared (no identity).
- **Tests:** `tests/core/shared-accounts.test.ts` (identity; merge by identity, different and no identity; an older peer; newest reading; spent marks and the switch decision; names and order, last writer wins, the order of the shared slots), `tests/server/accounts/shared.test.ts` (scripted peers: the exchange carries no credentials, an older peer unmerged, an unreachable one, the merged list and footer rows, a machine going away, spent marks skipped by the pick and sent at once, names and order applied, a taken name, a malformed message), two processes `tests/server/peers/shared-accounts.test.ts`, `tests/web/accounts.test.ts` → *D98*, E2E `tests/e2e/shared-accounts.spec.ts`.

## Credits (D103)
Developer request (2026-10-14): show when an account runs on **credits** (paid extra usage, because its 5-hour or weekly window is at 100 % and it still answers), how much is left (in the account's currency), and prefer subscription allowance over credits. Ruling: `docs/decisions.md` → D103; the signals: `docs/usage.md` → *Credits (D103)*; choices: `.loop/questions.md` → *D103*.

- **The state** (`AccountProfile.usage.credits`, `src/core/credits.ts`): `onCredits` (until its `until`, the reset of the full window), `enabled`, `currency`, `limit` / `used` / `left` (major units: `12.4` = €12.40), `resetsAt` (the credit period), `limitReached`. `null` fields are unknown. It travels with the reading in the D98 exchange, so a paired machine's newer reading of the same account counts here.
- **Settings → Accounts:** the account's credits line under its head: an amber "€ on credits" badge and "On credits until 13:00 · €12.40 left of €50 · credits reset 1 Nov"; while not in use "Credits: €12.40 left of €50 · credits reset 1 Nov"; nothing while its credits are off or unknown.
- **Allowance first** (`decideAccountSwitch`, `pickProfileForNewSession`): an account on credits has no allowance (its window is at 100 %); it can take work **at cost** (`canUseCredits`: enabled, not signed out, not known spent, on credits or with credits on and not used up).
  - a new session starts on the first account with allowance; none: the first that can pay from credits ("use credits"), else the Default as before;
  - a limit error moves the session to an account with allowance; none: "switch to another CLI" when that is the rule, else an account that pays from credits ("…; no account has allowance, using credits on Work"), else the every-account-out rule;
  - the 30-second check moves a live session whose account is on credits to the first account with allowance as soon as one has it (a reset, here or read by a paired machine), **only between turns**: a running turn is never interrupted, the next check after it moves it. Also with early switching off; a pinned session stays; the cooldown holds. Divider: "Switched account: Work → Private (moved off credits: Private has allowance again)". No account has allowance: the session stays on credits.
- **When every account is out of allowance** (setting `outOfAllowance`): **Use credits** (default) or **Pause new turns until an account resets**: while no enabled account of the CLI has allowance (and automatic switching is on for it), a new turn **waits in the session** instead of running on credits (developer ruling 2026-10-14; nothing is refused, the earlier 409 `credits-paused` is gone):
  - a message (typed, a loop's firing, a todo or plan start, any service message) is recorded as a user message with `queued: "credits"` and never written to the CLI: its bubble shows the D44 clock and the line "Waiting for an account with allowance — Private back at 23:30" with **Edit** (the text, and its attachments, go back into the composer) and **Remove** (`POST /api/sessions/{id}/events/{eventId}/withdraw`; the message gets D50's `withdrawn` and never goes out). A message sent while earlier ones still wait waits behind them, so the order is kept;
  - a new session (a plan / todo-run start too) starts idle and its first message waits the same way;
  - no pile-up: a loop's firing (D94) waits once per loop, and a service message with the same text that already waits is not held again;
  - **release** (`AutoSwitcher.releaseHeld`, in the 30-second check): once an account of the CLI has allowance (a window reset here, or a paired machine's newer reading, D98; or the setting is changed / switching turned off), an unpinned session on an account without allowance first switches to the first that has it ("moved off credits: Private has allowance again"), then its waiting messages go out by themselves, oldest first, each in its own bubble (the D44 queue keeps them in order behind the turn they start);
  - held messages are kept in the events, so they survive a restart; their attachments are kept in memory only (after a restart a held message goes out with its text: ASSUMED D103-held-attachments). Also with a single account: the setting is an explicit choice (ASSUMED D103-pause-single).
- **Notices** (`AutoSwitcher`, every 30 s, independent of the switching toggles): an Inbox item "Work is using credits" (once per account and per time it goes on credits, keyed by the reset that ends it) and "Work: credits running low" when less than 20 % of the credit limit is left (once per credit period). Dismiss-only; a new Inbox item is announced to paired devices by D73's push under the **Inbox** toggle.
- **Tests:** `tests/core/accounts.test.ts` → *D103*, `tests/server/accounts/credits.test.ts` (on credits with the money left; new sessions prefer allowance; the move at the turn boundary, not mid-turn; all out stays on credits; with "pause" messages are held, not refused, and go out in order on the account that resets; Edit / Remove of a held message; a new session, loop firings and repeated service messages wait without duplicates; the notices fire once; shared with a paired machine), `tests/web/accounts.test.ts` → *D103* (the held bubble), `tests/web/chat.test.ts` (the clock's tooltip), `tests/e2e/credits.spec.ts`.

## Choosing the account (D138)
Developer request (2026-10-27): "Make it possible to choose the account for running every project, and to switch between accounts overall." Ruling: `docs/decisions.md` → D138. Code: `src/core/accounts.ts` (pure: `resolveAccountPreference`, `selectSessionsToMove`, `moveConfirmText`, `pickProfileForNewSession`'s `preferred`, `decideAccountSwitch`'s `preferredId`, `chosenOutLabel`), `src/server/accounts/choice.ts` (`AccountChoice`), `src/server/api/accounts.ts` (the routes), plans.db migration 6 (`plans.accounts`), `src/web/api/account-choice.ts`, `src/web/v2/shared/AccountChoice.tsx`.

- **Precedence (one function, `resolveAccountPreference`):** a session's own **pin** > its **Project's** account (v2 calls plans "Projects") > the **overall choice** > the **automatic rules**. An account that is gone, disabled or of another CLI counts as Automatic at its level.
- **The overall choice** (per CLI: Automatic or an account; the setting `accounts.settings` → `choice`). It is set in the v2 status pill's details (also on a phone), Settings › Usage & accounts (*Account for agents*) and classic Settings → Accounts (*Account for sessions*). Choosing account B: new sessions start on B, and the **live sessions (idle and running) move to B now** through `switchAccount` (same conversation; a running turn is interrupted, then continued with "Continue where you left off: the account changed because a different account was chosen, …"), except **pinned** sessions and sessions whose **Project has its own account**. Before moving, the confirm gives the counts: "Move 5 agents to B? 1 running turn will be interrupted." (`POST /api/accounts/choice/preview`); nothing to move = no question. Automatic moves nothing. Moves run one after another in the background; the divider says "Switched account: A → B (overall choice)".
- **It replaced "New sessions start on: a fixed account".** One concept: `choice`. `newSessions` stays in the settings as its mirror for older clients; a stored `newSessions.rule: fixed` (an install from before D138) is read as the choice (nothing is moved on upgrade; the one difference: the fixed account is now a preference, so while it is out of allowance new sessions start on the automatic pick instead of on it); an older client's `PUT … { newSessions }` still sets the choice (without moving sessions).
- **A Project's account** (per CLI, `plans.accounts` in plans.db; "Automatic" default = the overall choice): set in the Start dialog (v2 and classic) and later in the Project's ⋯ → **Account…** (v2) or the plan's limits dialog (classic; an "Own account" chip shows it is set). Every step's run session starts on it (for the run's CLI after D82's Model by task routing; a Project account wins over a rule's account) and so does the Project's own session: a Start, or a change on a running Project, moves its live sessions (its own and its steps', pinned ones excepted) to it, after the same confirm (a draft has nothing to move). Back on Automatic, they move to the overall choice when there is one. A Project is a plan that is not done or cancelled; a session in several takes the newest with an account.
- **When the chosen account runs out** (the Project's or the overall one), the automatic rules take over as before: the choice is the switcher's **preferred** account, not a pin (`decideAccountSwitch`'s `preferredId`: the first target while it has allowance). Leaving it is said in the chat: "B is out of usage until 14:05; switched to A" (or "B is near its limit (session at 98 %); switched to A" at an early-switch threshold). New sessions start on the automatic pick while B is out, and on B again once it has allowance. Running sessions do **not** jump back unless *Switch back after a reset* is on; with a choice, switching back goes to the chosen account (not to the first in order), and never away from it.
- **Where it shows:** `Session.accountChoice` (`source`, the account, the Project); v2's agent header chip "Account: B (from project)" / "(overall choice)" / "(pinned)" (only when it is not automatic), its ⓘ popover and side panel; `accountChoiceChanged` on `/hub` refreshes the pickers.
- **Per computer.** Profile ids and the `accounts.settings` setting belong to one machine, and D98 shares only names, order, usage and spent marks, so the overall choice applies to **this computer's** sessions only; a paired computer's sessions are never moved by it. Classic Settings → Accounts with a paired machine in its *Machine* picker saves that machine's choice through its settings (new sessions there), without moving its running sessions. Paired phones (D73) may set this computer's choice (the routes are on `DEVICE_ALLOWED`).
- **Not moved:** paused / stopped sessions (they resume on their account; the automatic rules apply), hooked terminal sessions, sessions in a switch, sessions already on the account.

## The account needs you (D139)
Found on the developer's install (2026-10-27): every step session of a Project started on its own account died within a second, `code: 1`, with Claude Code's stderr "[ACTION REQUIRED] An update to our Consumer Terms and Privacy Policy has taken effect on October 8, 2025. You must run `claude` to review the updated terms." The chat said only "claude exited unexpectedly (code 1)", the plan kept starting its next steps on the same account (each failing), and automatic switching did nothing (it is not a limit). Ruling: `docs/decisions.md` → D139. Code: `src/core/accounts.ts` (pure: `parseAccountAction`, `accountNeedsYouTitle`, `accountStoppedLabel`, `accountFixCommand`, `readAccountBlocks`, `ProfileSnapshot.blocked`), `src/server/accounts/needs-you.ts` (`AccountNeedsYou`), `AccountService.block` / `unblock` / `blockOf`, `SessionSupervisor.restartStopped`, the Plans environment (`accountBlockOf`, `restartSession`, the hold in `usageHeld`).

- **Recognised from the CLI's own words** (`parseAccountAction`, after `parseLimitError`: a limit stays a limit) in a process exit's stderr / message (D7's `failed`) or a failed turn's error text. Kinds: `terms`, `login`, `action`. Every wording is **VERIFIED** (read-only `strings` of the installed binaries, nothing run against a login): Claude Code 2.1.311: "[ACTION REQUIRED] … Consumer Terms … review the updated terms" (`terms`, also the incident's text verbatim), any other "[ACTION REQUIRED]" line (`action`), "Please run /login" / "(run /login to renew)" / "API Error: 401 Invalid API key · Please run /login" / "OAuth token has expired" / "OAuth token revoked" / a line starting "Not logged in" (`login`); Codex CLI 0.160.0: "Your access token could not be refreshed …" and "please re-run `codex login`" (`login`). OpenCode: none (its errors are the provider's; not read, so never guessed). Not matched on purpose: the advance notice "… will take effect on …" (no `[ACTION REQUIRED]`), "Invalid API key format" (a settings mistake), ordinary errors, limits.
- **The account is blocked** ("needs you"): the setting `accounts.blocked` (`{ [profileId]: { kind, text, since, command, sessionIds } }`, no migration; it survives a restart). One per profile: a second failure only adds its session. `GET /api/accounts` carries it as `AccountProfile.needsYou`. Also with a single account (unlike D63's *Dormant* rule: it is not a switch, and the developer needs to know).
- **Cleared** when a turn of any session on that profile ends well (its first successful `result`; the Inbox item closes as `resolved`), or when the developer chooses **Retry stopped agents** (they did what the CLI asked). Dismiss only closes the item: the account stays blocked until one of those.
- **One Needs-you item per block** (kind `account-needs-you`, both themes' Inbox / v2 Needs you, label "Account needs you"): "Work (Claude Code) needs you: accept Anthropic's updated terms" (`login`: "sign in again"; `action`: "open the CLI with this account"), the CLI's text, and the command, copyable (`InboxItem.command`): `CLAUDE_CONFIG_DIR="<the profile's folder>" claude`, just `claude` for the built-in Default (the CLI's own text says "run `claude`"). Codex / OpenCode: only for `login`, their D63 terminal sign-in (`CODEX_HOME="<dir>" codex login`, `XDG_DATA_HOME="<dir>" opencode auth login`); otherwise no command and the item says "Open <CLI> with this account". **Retry stopped agents** unblocks the account and starts every session it stopped again (still failed, not live, not closed) through `restartStopped`; **Dismiss**. Paired phones see it with the command (read-only text) and may Retry (the Inbox action route is on `DEVICE_ALLOWED`). A new item is announced by D73's push like every Inbox item.
- **The stopped session's chat** gets the divider "Stopped: the account Work needs you — accept Anthropic's updated terms" (lifecycle `account-needs-you`, with the CLI's words and the command, copyable) under D7's "claude exited unexpectedly".
- **`restartStopped` (Retry, a step's Restart):** the same session starts again. Its messages the CLI never took up (`delivered: false`: a process that died before `init` took up none) go out again in order, else D7's "Continue."; a Claude Code conversation that was never written (no transcript) starts as new with the session's own id instead of `--resume`. The earlier, undelivered bubble stays in the chat (ASSUMED D139-resend: the message shows twice rather than being rewritten).
- **Precedence with a blocked account (D138):** the automatic pick and the **overall choice** treat it like a spent account (`hasAllowance` / `canUseCredits` are false; `pickProfileForNewSession` takes the first other account with allowance, also with automatic switching off; none: the blocked one, as nothing is better). A **Project's own account** that is blocked is never left for another: its steps **wait** (`usageHeld`: the plan's held reason "the account Work needs you", shown as "New steps wait: …" in v2 and "New starts held: …" in classic). A step without a Project account whose account (D76's source account, a D82 rule's) is blocked starts on another account with allowance when there is one, else waits the same way. A **pinned** session is never moved (D63); it stays stopped with its divider until Retry. Starting a session **explicitly** on a blocked account from the New forms is allowed with a warning under the Account select ("Work needs you: <the CLI's words> The agent may stop at once until that is done."; the option says "(needs you)").
- **Plans:** see `docs/plans.md` → *Stopped steps whose agent failed (D139)*.
- **Tests:** `tests/core/account-needs-you.test.ts` (the parser: the incident VERIFIED → `terms`, the other kinds, no false positives on errors, limits, the advance notice; titles and commands; the stored blocks; precedence: overall / automatic → another account, pinned stays, never a switch target), `tests/core/plans.test.ts` (a failed run session is `stopped` with `stoppedBy`), `tests/server/accounts/needs-you.test.ts` (fake-claude's `.fake-action-required`: a Project's steps stop starting after the first failure and wait with the reason; one Inbox item with the command; the divider; Restart refused while blocked; a new session on the overall choice goes elsewhere; Retry restarts the same session after the fake accepts and the block clears on its first good turn; an ordinary failure holds no slot and the Project's Resume restarts it), `tests/web/v2-projects.test.ts`, E2E `tests/e2e/account-needs-you.spec.ts` (v2 desktop, phone 390×844, classic).

## Limits and open points (see `.loop/questions.md` → *D63 · CLI accounts*)
- Threshold switching needs fresh readings: the poller reads only while a Switchboard tab is open; during turns `rate_limit_event`s arrive anyway. The limit error always acts.
- History's terminal-conversation listing and Workflow runs' files (D51) look in the Default's Claude Code folder only; sessions on another profile show in the chat as always, their transcripts are found for Attach / long-message restore / the context meter across every profile folder.
- OpenCode has no plan-limit reporting: its accounts switch on the provider's 429 / quota error only; a Codex account's windows are known only while one of its sessions has reported them.
