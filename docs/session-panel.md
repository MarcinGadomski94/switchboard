## Agent cards
One card per agent of the session, in creation order (the main agent first; agents = the main agent + one per Agent/Task call, gap #8, `docs/derivations.md` → *Agents*). D37: finished subagents are under the "✓ N finished" line (above). D36: the card of a subagent that has a chat (`hasSubagentChat`: started by an Agent / Task call Switchboard saw) is itself a link to that chat (`/sessions/{id}/agents/{agentId}`, tooltip "Open this subagent's chat", the same card with `--border-control` on hover; `docs/chat.md` → *Subagent chats*); the main agent's card and the demo's cards stay plain.

| Part | From |
|---|---|
| dot | the agent's status color (SPEC status tokens; `paused` → idle) |
| name | the agent's name (`orchestrator`, the solution's name in single-solution mode, `main`, or a subagent's `subagent_type`) |
| description | the agent's own (a subagent's Agent-call description); the main agent has none, so it shows **the first line of the session's task** |
| status copy | D19: while the agent is active in a running turn (it has an entry in `Session.activity.agents`), **its current action and time**: `Thinking…` / `Writing…` with the time since it became active (the turn, for the main agent: `12s`, `1m 23s`; the main agent thinks with the chat line's rotating verb, `Pondering…  1m 23s`, D21 ruling 2026-09-28), `Bash: npm test` with the time since the tool started (`0:42`), `Waiting for you` with the time since its request opened; D30: while no turn runs but the main agent's background work is pending, the chat line's wait (`Waiting for GitHub Actions: gh run view …  3:21`, `+N more`), with the card's dot and status in the running color; live from the `/hub` `activity` events, ticking locally (`AgentActivityText`, `src/web/activity/`; a long action is cut with `…` at 160px, the time always shows). Otherwise the agent's status text (a subagent's latest `task_progress` description) while it has one, else the status word: `needs you` · `running` · `done` · `failed` · `idle` · `paused` (the prototype's words). While the session is `paused`, an agent the pause cut off (`idle`) reads `paused` with the idle dot, as in the prototype |
| path | the solution folder the agent wrote into (below), else `workspace root`: every agent runs at the session's cwd, the workspace root; D14: a repo session's agents read the repo's name (`rootPath`), since they run in the repo or its worktree |
| ⎇ branch | the branch of the session's worktree the agent wrote into; no chip without one |

**Where an agent works** (server, `#placeAgent` in the recorder): the agent's first **successful** write (Write / Edit / MultiEdit / NotebookEdit) into a solution sets its `solutionPath` = the solution's workspace-relative folder (`solutionFolder` in `src/core/derive/artifacts.ts`, the prototype's form: `microfrontends/acme-app-front`, `functions/calendar-func`, `deprecated/<type>/<repo>`, `mobile/`, `infrastructure/`; a file in the session's worktree `<repo>-wt-<session>` maps to its repo's folder) and `branch` = the registered worktree that holds the file (M2.2), else none. Later writes into other solutions do not move it; a later write into the same solution's worktree fills a missing branch. Files at the workspace root (`contracts/…`) place nobody. D14: in a repo folder every write into the repo or its worktree places the agent in `<repo>/` (`sessionSolutionFolder`); an agent of a repo session without a write reads the repo's name instead of "workspace root" (its cwd is the repo or its worktree). The stream itself never says where an agent works, and its prompt is not read (no inference).

**Summary** (right of the header): `n agents · n solutions · n branches`, the prototype's `agentSummary` verbatim, plural words even for 1 (`1 agents · 1 solutions · 1 branches`): agents, distinct solution folders (not `workspace root` / `read-only`) and distinct branches of the cards. When it is long, the header wraps onto two lines exactly as the prototype's does.

## Terminal tail
`terminalLines(events, agents, status)`: the session's recent events (the detail's newest 200) in time order (`ts`, then id) turned into lines; the newest **8** are shown, the cursor included. It complements the chat, which already shows the conversation and the main agent's tool steps.

| Event | Line(s) |
|---|---|
| Bash call (any agent) | `$ <first line of the command>`, then the **last 3 non-empty output lines** of its result, verbatim, once it arrived |
| AskUserQuestion | `⏸ <label>` while its request is open, `✓ <label>` once answered (`✕` on an error result) |
| any other tool call of a **subagent** | `<label>` while it runs, `✓ <label>` done, `✕ <label>` failed |
| any other tool call of the main agent | none (the chat's step lines) |
| permission request | `⏸` open · `✓` allowed · `✕` denied, cancelled or stale, + its label |
| automatic denial | `✕ Denied · <tool>` |
| permission-mode mismatch | `⚠ <label>` |
| turn result | its text (the label: the result's first line, the process's output); `✕ <label>` when the turn failed |
| process lifecycle | its label (`Started`, `Paused`, `Continued in a terminal`, …); `✕ <label>` when it failed |
| user / assistant text, subagent prompts, anything else | none |

A subagent's lines start with `[<agent name>] ` (the prototype's `[web] $ dotnet test`). While the session's status is `run`, the last line is the cursor `▍`.

Line colors (prototype `lineColor`, on the text after an optional `[name] ` prefix): `$ …` #6d6c67 · `✓ …` oklch(0.78 0.12 150) · `⏸ …` / `⚠ …` oklch(0.8 0.13 70) · `✕ …` oklch(0.72 0.16 25) · anything else #bfbeb8. Lines are mono 11px/1.7, one line each, cut with an ellipsis; the box (bg-code, 1px #1f2024, 8px radius, 10/12px padding) is at least 150px high.

## Demo seed
The prototype's terminal lines are mock text that no real event produces. The seed (`src/server/demo/seed.ts`, `demoResult`) stores each line as a finished **turn result** whose text is the line (kind `ok`, `source: 'demo'`), which the tail shows verbatim and the chat does not show; the prototype's cursor line `▍` is not stored (the tail adds it for the two `run` sessions). So the demo goes through the same renderer as real sessions. button-rollout's tail also starts with `⏸ breaker: 2 consecutive ambiguous items`: M4.2's demo seed turned that chat line into an open permission request, which the tail shows like any open request.

## Loading a session (D45, developer ruling 2026-09-29)
Switching sessions shows a loading state, never the previous session's content. It covers the whole session view (header, chat, this panel). Code: `src/web/views/session/session-loading.ts` (pure: the cache, the delay, which parts wait), `useSessionData.ts` (the view's data hook and `usePlaceholderDelay`), `SessionSkeletons.tsx` + `session-loading.css` (the placeholders), wired in `SessionView.tsx`, `SessionHeader.tsx`, `ChatTab.tsx` / `SubagentChat.tsx` and `RightPanel.tsx`.

- **Before D45:** the view is keyed by the session id (`Shell.tsx`), so the old session's data was already dropped on a switch; but until the new detail and events arrived the view was a blank frame with the raw id as the title, `Diff · 0` / `Artifacts · 0`, an empty chat and an empty panel, and every visit refetched into that blank frame.
- **Data per session:** `useSessionData(sessionId, wantEvents)` loads `GET /api/sessions/{id}` (again on the session's `/hub` `sessionUpdated`, `event`, `questionBatch`, throttled to 500 ms, and after an action) and, while the chat tab is open, `GET /api/sessions/{id}/events` + the `/hub` `event` stream (events streamed while a fetch runs are merged in by id). Everything it holds is tagged with the session id: data of another id never renders, whether or not the view is remounted. The chat tab now receives its events from the view (the other tabs still load their own data).
- **Cache (instant revisit):** `sessionCache`, in memory for the page's life (one per browser tab), keeps the last loaded detail and the complete event list of the **20** most recently stored sessions (least recently stored goes first). A session opened before starts from it: rendered at once, no placeholder, no `aria-busy`, then refreshed in the background (the fetched list replaces the cached one, streamed events kept). Every load and every `/hub` update of the shown session is written back; `/hub` `event`s of other cached sessions are merged into their cached lists while any session view is open (never starting a list that was not fetched whole), so a revisit starts from the current conversation. A 404 drops the session from the cache.
- **Placeholders (no flicker):** a part waits while its data is missing: the header and the panel for the detail, the chat for the detail or the events (`loadingParts`). While anything waits the view has `aria-busy="true"`. Only when the wait has lasted **150 ms** (`PLACEHOLDER_DELAY_MS`, `PlaceholderDelay`; a new session or a new wait starts over) do the placeholders show, together with a visually hidden `role="status"` "Loading session…". Before that the parts are empty (no raw id). Shapes (skeletons on the SPEC tokens: `--bg-card` fill, 1 px `--border-row` line; a `--bg-selected-nav` band sweeping across in 1.6 s, static without the band under `prefers-reduced-motion`):
  - header: a 180×16 title bar where the title starts and a 240×11 root line block one row gap after it (4 px radius); the actions stay (disabled), no chips;
  - chat: four bubble shapes in the conversation's padding, alternating sides like messages (the developer's right, the agent's left; 12 px radius, the message gap); the composer stays; in a subagent's chat (D36) the same shapes;
  - panel: the overview's block (the overview table's x and width, 96 px, 8 px radius) and two one-line agent card blocks where the loaded cards start (the cards' x, width and 56 px height, 8 px radius, 4 px apart).
- **Errors:** a failed load waits no more, so no placeholder ever sticks: a 404 shows the missing state (`no such session`, the id as the title); any other failure shows the header's error line (`session-error`, the service's message, else "Switchboard is not reachable." / "The request failed (HTTP n)."), the id as the title and an empty chat and panel; failed events leave the chat without placeholders (as before, an empty conversation). A failed background refresh keeps what is shown.
